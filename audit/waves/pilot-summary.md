# Пилотные эвалы AI-скиллов — сводный отчёт

Дата: 2026-10-01. Координатор пилота: субагент эвалов.
Метод: 6 пар × 3 задачи × 3 варианта = 54 прогона. Модель фиксирована везде
(прогоны и LLM-грейдер): `gemini-3.6-flash-medium`. Свежий контекст каждый
прогон (отдельный процесс agy). Конвейер: run.py → blind → oracle →
программный оракул (полные held-out методы) → llm-grade → verify-blind →
aggregate. Гибриды не тестировались (только раунд 1).

**Статус: это скрининг (2–3 задачи на пару), не основание для вердиктов
«удалить/объединить».** Все вердикты ниже — «есть ли наблюдаемые различия»,
а не «какой скилл лучше».

## Итоговая стоимость

- Прогоны (estimate, cost-summary.json): **$2.5957** за 54 сравнения (~$0.048/сравнение)
- LLM-грейдер (estimate, grader-cost.json, отдельной строкой): **$0.0460** за 54 вызова
- **Итого: ~$2.64** (estimate)
- Не учтено: упавшие/частичные попытки при 503 (для implement-пары задокументировано ~$0.59 за 4 попытки; у остальных пар ретраи были, точная сумма не подсчитана — cost-summary считает только успешные прогоны)

## Наблюдения второго порядка (не вердикты)

1. **Многословность скилловых вариантов.** v-check (пары 1, 2) систематически получал
   extra_actions=1 от слепого грейдера за раздутый каркас отчёта и тратил ~2.5×
   output-токенов при том же результате. v-sdd (пара 5) стоил ~1.7–1.8× дороже
   noskill по токенам/времени (fan-out субагентов). На результат это не повлияло,
   но для волн с большим числом задач разница в цене прогонов станет материальной.
2. **Аномалия эмуляции reviewdog (пара 3).** Prompt-эмуляция внешнего статического
   чекера нестабильна: на task-01 агент послушался («Замечаний нет», recall 0.00),
   на task-03 — проигнорировал инструкцию и выдал полное ревью (recall 1.00).
   Эмуляция через extra_instructions — ненадёжный стендин внешнего инструмента.
3. **Аномалия эмуляции aider (пара 4).** Эмуляция («минимальные правки + pytest
   после каждой») дала 3/3 PASS — но это свойство лёгкости тикетов, а не
   доказательство эквивалентности настоящему Aider. Настоящий Aider/OpenHands
   невозможен без LLM API-ключа (только OAuth).
4. **Пограничный FAIL (пара 5, task-01/v-sdd).** Программный оракул засчитал fail
   по file_set: «лишние» файлы — `.git/` + `.superpowers/sdd/`, предписанные самим
   скиллом (git-workflow и ledger), а не выдуманные модули. Цель проверки
   («не выдумывает модули») фактически выполнена. В results.csv оставлен буквальный
   FAIL с детализацией; открытый вопрос — засчитывать ли как PASS с пометкой.
5. **Агенты дописывают тесты (пара 4).** Во всех вариантах агенты добавляли свои
   тесты в repo/tests (все зелёные, скоуп не расширен). `extra_actions_llm=0` это
   не отразило — слепой грейдер по транскрипту этого не видит.

## Слепота: где возникли вопросы

- **Пара 1 (verification-claims): verify-blind = FAIL** (не ложное срабатывание).
  Транскрипты v-check содержат абсолютные `file://…/round-1/<task>/v-check/fixtures/…`
  ссылки (стиль цитирования check-скилла) — имя варианта утекло в слепой транскрипт.
  Утечка асимметрична (только v-check). Промпт грейдера имён не содержал; признаков
  смещения оценок нет (correctness=1.0 везде). Зафиксировано в отчёте пары §10.
- **Пара 4 (implement-from-ticket): verify-blind = FAIL.** В 7 из 9 транскриптов агенты
  встроили абсолютные `file://` пути workdir с именами вариантов. Утечка в тексты
  оценок не попала (в grades/*.json имён вариантов нет), но гарантия слепоты
  технически нарушена: грейдер видел эти пути. Вывод пары: verify-blind будет
  систематически падать на кодовых задачах без санитизации путей.
- **Пара 5 (plan-execution): FAIL → санитизация → PASS.** Воркер заменил абсолютные
  пути на `[workdir]` в слепых копиях (только пути, содержимое не трогал) и
  перегрейдил свежими вызовами. Урок для стенда: шаг `blind` должен санитизировать
  абсолютные пути при копировании.
- **Пары 2, 3, 6: verify-blind = PASS** без вмешательств.
- Маппинг `.sealed/mapping.json` вручную не вскрывался ни одним воркером;
  сопоставление меток делалось по sha256 транскриптов (в двух парах были
  байтово-идентичные транскрипты у разных вариантов — обработано назначением
  1-к-1, выводы от назначения не зависят).

## Оракул: где возникли вопросы

- **Расхождение LLM-оракула и программного (пара 6).** Грейдер поставил
  correctness=1.0 и usefulness=5 всем 9 ответам, включая два programmatic-fail
  на task-03. Вердикт — за программным оракулом.
- **Стохастичность LLM-грейдера (пара 5).** Одна и та же метка получила
  corr=0.0/hall=1 в первом раунде и corr=1.0/hall=0 во втором — на
  байтово-идентичном входе. Чистая стохастичность грейдера. Вывод: одиночные
  LLM-оценки шумные; стабильный сигнал — только программный оракул.
- **Парсинг vs метод (пара 2).** Буквальное применение одиночной регулярки для
  номеров пунктов дало бы 7 ложных FAIL из 9 (агенты нумеруют список заново:
  «1. **Пункт 2**: …»). Применено двухуровневое правило («Пункт N» в приоритете,
  fallback — ведущее число); проверено контрольным прогоном. Правило
  задокументировано в скрипте оракула пары.
- **Парсинговый артефакт (пара 6, task-03).** Все три варианта ответили одинаково
  («Новый выпуск: 80.75» — вычли 15% рекламаций); у v-thinking сработал запасной
  паттерн на «95» в пояснении. По существу ответы идентичны, расхождение —
  артефакт парсинга, не различие вариантов.
- Во всех парах программный оракул реализован отдельным скриптом
  `harness/oracle-full-<pair>.py` (методы из heldout/tasks.yaml), проверки дописаны
  в `oracle/<label>.json` в формате стенда; детали — в `programmatic/` и
  `results-programmatic.csv`.

## Инфраструктурные находки (для следующих волн)

1. **`grade.py llm-grade` без `--dangerously-skip-permissions` систематически падает**
   (грейдер пытается выполнить shell и возвращает пустой ответ). Обходной путь без
   изменения стенда: `AGY_BIN=harness/agy-grader-wrap.sh` (добавляет те же флаги,
   что run.py). Использован во всех парах после находки.
2. **Конкурентные `run.py` на одном run_id/scratch — гонки** (last-writer-wins,
   перемежающиеся timestamp'ы, ложные ERROR). Нужен file-lock на (run_id, scratch_dir)
   или явный запрет конкурентных запусков.
3. **Системный pytest исчезал посреди прогона** (~12:30, причина не установлена;
   в 10:12 работал). Переустановлен (pytest 9.1.1, та же версия). Все замеры
   перепроверены независимым оракулом. Для волн: проверять наличие pytest перед
   каждым раном.
4. **Модель `gemini-3.6-flash-medium` периодически отдавала 503** «No capacity
   available» (транзиентно; частично — из-за параллельных пилотов на той же модели).
   Аномалия: agy при 503 возвращал status=ERROR **с полным валидным ответом и
   usage-токенами** — раннер такие прогоны перезапускал. Ретраи идемпотентны,
   итог везде 9/9 SUCCESS.
5. Простой оракул стенда (contains/regex) для кодовых задач — только format-only;
   настоящий вердикт даёт программный оракул. Это задокументировано в отчётах пар.

## Что это значит для волн по 10–20 скиллов

1. Стенд работает end-to-end, но перед волнами нужны 4 правки: санитизация
   абсолютных путей в `blind`, file-lock в `run.py`, AGY_BIN-обёртка (или флаги)
   для `llm-grade`, проверка pytest перед раном.
2. Дизайн волн: программный оракул — обязателен и авторитетен; LLM-грейдер —
   только вторичный сигнал (шумен). Для кодовых задач без программного оракула
   замер бессмысленен.
3. Внешние аналоги через prompt-эмуляцию — только как слабый контроль;
   нестабильность эмуляции зафиксирована. Настоящие инструменты (Aider/OpenHands,
   PR-Agent) требуют API-ключей — решать отдельно.
4. Бюджет: ~$0.05/сравнение (прогоны) + ~$0.001 (грейдер). Волна 20 задач × 3
   варианта ≈ $3. Ретраи при 503 добавляют 10–30% сверх.
