Parallel fix implementation: split by files so no file is touched by two agents.
SSH operations on a remote host and local code edits — always parallelize, they are independent.
Auditing a large codebase: 5+ agents with non-overlapping roles. Phase 1 = bugs, Phase 2 = improvements.

Multi-agent context OR goal='fresh main' + dirty/shared checkout → FIRST `git worktree add <path> -b <branch> <clean-base>`, THEN the first edit. Never edit a feature in a shared working tree: other agents write there too, edits interleave (one file — two packets), commit attribution is lost. One packet = one worktree = one branch = one agent. Before dispatch check active peers (claude-peers `list_peers`/`set_summary`). Source: 5-agent collision in one tree, nikita-video-engine 2026-06-04 (release_gate.py hit by PR2+PR5 simultaneously).

IMPORTANT: Worktree created → every Edit/Write by absolute path MUST point into the worktree (`.../wt-<name>/...`), not the main checkout (`.../<repo>/...`). The Edit tool is NOT bound to cwd — it's easy to edit the main copy when path tails look alike. Symptom: verification in the worktree (`cd wt-... && pytest/grep`) doesn't see your edits although Edit returned success; `git status` shows the diff in the main tree while the worktree is clean. If caught: `cp main/<file> wt/<file>` → `git checkout -- <file>` in main (restore cleanliness) → continue in the worktree. Prevention: the first Edit of a worktree task — verify via `wc -l`/unique marker that the edit landed in the worktree path. Source: NVP-ASSET-PIPELINE-PARALLEL-01 2026-06-12 (edited `video-engine/asset_pipeline.py` instead of `wt-asset-parallel/...`, caught at 993 vs 783 lines).

IMPORTANT: In a worktree NEVER `git add -A` / `git add .` — explicit paths only (`git add src/foo.py tests/test_foo.py`). Reason: a symlink/venv slips past the dir form of `.gitignore` — the pattern `.venv311/` (with slash) ignores the DIRECTORY but NOT a same-named symlink file. `git add -A` stages such a symlink; a later `git merge --ff-only` in the main checkout overwrites the real venv with the symlink (self-referential `.venv311 -> .../.venv311` → "too many levels of symbolic links") and DELETES the venv. Prevention: explicit paths on add + both forms in `.gitignore` (`.venv311` AND `.venv311/`). Recovery: untrack the symlink (`git rm --cached`), rebuild the venv (`python3.11 -m venv .venv311 && pip install -e .[dev] pytest ruff`). Source: visual-relevance wave 2026-06-13 (PR #162 committed the `.venv311` symlink via `git add -A` in wt-eval-main → ff deleted the venv).
