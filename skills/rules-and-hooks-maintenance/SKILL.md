# Обслуживание правил и хуков

## 1. Контракт написания хуков

Каждый новый или изменённый хук в `~/.claude/hooks/` обязан выполнять пять условий:

1. **≥4 фикстуры** в `~/.claude/hooks/tests/` на каждый хук:
   pass (легитимная команда → exit 0) · violation (WARN → exit 0 + stderr; ENFORCE=1 → exit 2) · override-ack (ENFORCE=1 + ACK → pass) · fail-open (мусорный/пустой stdin → exit 0). Хук гоняется subprocess-ом с JSON на stdin — ровно как его зовёт Claude Code.
2. **Fail-open обязателен.** Любая внутренняя ошибка хука → exit 0. Гейт не имеет права ломать turn владельца из-за собственного бага.
3. **Phase 1 WARN ≥2 недели.** Новый гейт по умолчанию только предупреждает (stderr + exit 0). Перевод в BLOCK (`<NAME>_ENFORCE=1`) — только при <2 ложных срабатываний в неделю за период наблюдения.
4. **Override:** env `<NAME>_ACK` ≥12 символов с осмысленной причиной (не «yes»/«ack»). ACK печатается в stderr, чтобы причина попала в лог.
5. **Трёхслойное доказательство «хук работает»:** конфиг есть (запись в settings.json + валидный JSON) → smoke-тест (`echo '<json>' | python3 hook.py`; проверить exit code) → live-fire (реальное событие через Claude Code). `hook_not_observed` — повод фальсифицировать, а не считать успехом. Proof = команда + exit code + stdout/stderr, не «должно работать».

Реестр: `python3 ~/.claude/hooks/gen_hook_registry.py` — таблица хук | событие | есть тест. Красный маркер = долг по фикстурам.

EXPIRES: 2026-10-30
EVIDENCE: ≥1 пойманное по делу срабатывание нового хука ИЛИ ≥1 регрессия, пойманная фикстурой из tests/.

## 2. Приёмка правок правил от внешнего агента

Внешний агент (Grok, Codex, agy, другая сессия) поправил `~/.claude`, `~/.codex` или `.claude/rules/` проекта → ПЕРВЫЙ шаг после его отчёта: `git status` + `git diff` в этом репозитории. Проверить четыре вещи:

1. **Полнота коммита** — отчёт «закоммичено» ≠ закоммичено; половина файлов обычно висит untracked/modified.
2. **Дублированные секции** — агент вставляет свой блок, не найдя существующий: одно правило появляется 2-3 раза (SKILL.md + references + повтор в теле).
3. **Чужая терминология** — агент называет сущности из своего контекста («PlanKing» вместо goal-king), ломая greppability и маршрутизацию.
4. **Молчаливые правки вне скоупа** — settings.json, глобальная модель, конфиги, о которых отчёт молчит.

**Почему:** сессия Grok 2026-07-09 — все четыре класса за один прогон: 3 копии одного блока, «PlanKing», незакоммиченные delegate/cheatsheet, молчаливый `"model": "sonnet"` в settings.json (дефолт для ВСЕХ сессий).

**Как применять:** починить ошибки локально + починить БРИФ на правку правил (требовать: grep-дедуп перед вставкой, точные имена сущностей, чистый `git status` в приёмке, запрет трогать settings).
