# Верификация

**Bias-линза (§3.6, бывший `/anti-bias`, влит 2026-10-01) — применяй к своим выводам до verdict.**

## 0. Expected State FIRST

Перед чтением фактов и запуском проверок выпиши 3-7 наблюдаемых ожиданий. Это Точка G: что должно быть истинно, чтобы результат можно было принять.

| E-ID — название | Что должно быть истинно | Где подтверждать | Next action if unmet | Actor | Effort (0-100) |
|---|---|---|---|---|---|
| E01 — ... | ... | файл / команда / лог / screenshot | ... | agent / owner / both | ... |

Правила:
- Ожидания формулируются ДО actual evidence, не после.
- Каждое ожидание проходит camera test: его можно подтвердить файлом, командой, логом, screenshot или явным output.

## 0.5 Проверка ожиданий на искажения (expectations-review, из /anti-bias)

Каждое ожидание из §0 прогони до сбора evidence:

| E-ID | Bias risk | Missing baseline/data | Counterexample | Rewrite |
|---|---|---|---|---|
| E01 | confirmation / attribution / survivorship / anchoring / false model | ... | ... | ... |

Обязательные вопросы:
- Есть ли baseline? «На 30% лучше» — откуда стартовая точка?
- Достаточен ли sample size и период наблюдения?
- Какой counterexample сломает ожидание?
- Не станет ли ожидание true само из-за нового ритуала измерения?
- Где окно незнания: сколько дней/кейсов нужно до честного verdict?
- Если ожидания невозможно сформулировать, STOP: уточни задачу или прогони §3.6 как discovery-step.

## 1. Выпиши тест-кейсы ДО проверки

Три корзины:
- **Positive** — что должно работать
- **Negative** — что должно отваливаться правильно
- **Edge** — граничные случаи (null, пусто, overflow, concurrent, malformed)

Без тест-кейсов проверка = вранье.

## 2. Открой каждый артефакт лично

Не предполагай. Читай файл, запускай команду, смотри output. Пройдись по тест-кейсам, для каждого пиши PASS / FAIL.

Если файл не прочитан или команда не запускалась — пиши `NOT CHECKED`.
Не описывай содержимое файла, результаты тестов, версии, логи или поведение parser/server/UI как факт без реального наблюдения в этой сессии.
Следуй `standards/no-fabricated-evidence.md`.

**Проверяешь коллекцию (батч, датасет, N файлов, N строк) — сэмплируй хвосты, не середину.** Открой первый item, последний item и самый странный (пустой / самый длинный / с не-ASCII / с null). Spot-check по happy-path середине прячет ровно те падения, ради которых проверка и делается.

## 3. Challenge

- Что получилось?
- Что не учёл?
- Что будет непонятно менеджеру / разработчику / команде?
- Фальсифицируй вывод — 3 способа доказать что ты неправ.
- **Blind Handoff Test:** применишь ли ты сам через месяц результат по одной команде
  без пояснений? Нет → handoff не готов.

**Хорошая новость подозрительна.** Тест прошёл слишком легко, прогон вышел полностью чистым, all-clean sweep без единого warning — считай верификацию сломанной, пока не объяснишь ПОЧЕМУ результат настоящий. Проверь, что тест реально исполнился (не skip, не 0 collected, не пустой вход, не замоканный целевой вызов). Чистый результат без объяснения = `NOT CHECKED`, не PASS.

**Проверяешь чужую работу (исполнитель, агент, свой прошлый прогон) — пройди
[references/fraud-table.md](references/fraud-table.md):** ослабленные тесты →
ложная завершённость → scope creep → предательство спеки. Конфликт код/спека/тесты
решается по authority order: явное намерение пользователя > спека > тесты > текущее
поведение.

## 3.5 Content-depth gate

Ячейка «actual» обязана содержать **конкретные значения из источника**, а не пересказ.
«62 теста прошли», «данные на месте», «токены корректны» — это `NOT CHECKED`, не PASS.

Минимум 3-5 конкретных значений на ожидание: имена тестов (и что каждый проверяет),
id, hex/rgba, числа, цитаты кода, имена записей. Источник содержит 33 записи — назови 5
с точными полями. Пересказ вместо значений = проверка невалидна.

## 3.6 Bias-линза (влит /anti-bias, 2026-10-01)

Применяй к своим выводам до verdict. Тривиальная задача — пропусти.

**Эпистемологические теги** — для каждого утверждения в выводе:
- **[O]** Observation — наблюдение из данных/кода
- **[I]** Inference — вывод из наблюдений
- **[S]** Speculation — предположение без прямых данных
- **[A]** Assumption — принятое допущение

Source не прочитан — claim о его содержимом не может быть `[O]`; помечай `[S]`/`[A]`.

**Чеклист искажений:**
- [ ] **Confirmation bias:** искал опровержения, или только подтверждения?
- [ ] **Survivorship bias:** что НЕ вижу? Какие данные отсутствуют? (сначала сырьё без дефолтных лимитов — скрытый `limit=10` = survivorship bias)
- [ ] **Anchoring:** не зацепился ли за первое найденное решение?
- [ ] **Attribution error:** это свойство X или свойство контекста, в котором X встретился?
- [ ] **False mental model:** проверил реальную структуру данных (`isinstance`), а не предполагаемую?

**Операциональные правила:**
1. **Counter-evidence:** гипотеза кажется очевидной → сгенерируй хотя бы один пример, где она ломается.
2. **Alternatives:** нашёл подтверждение → добавь альтернативную гипотезу и тест, который их различит.
3. **Noise:** паттерн редкий и яркий → «возможно шум», пока не повторится.
4. **Long context:** вывод опирается на последние токены → перечитай начало последовательности.
5. **Ignorance:** нет данных → не делай негативный вывод. Пиши «не знаю» / «не проверено».
6. **Ошибки — данные:** edge cases и исключения собирай как источник информации о структуре, не `except: continue`.
7. **Независимая валидация:** проверь находку 2-3 методами; разошлись — нужен доп. анализ.

## 4. Gap Analysis

Заполни таблицу минимум одной строкой. Если gaps не найдены — строка `G00 — gaps not found`.

| G-ID — название | E-ID ref | Expected | Actual | Root Cause | Fix / Next action | Actor | Effort |
|---|---|---|---|---|---|---|---|
| G01 — ... | E01 | ... | ... | ... | ... | agent / owner / both | ... |

Независимый cross-check обязателен.

**Δ-таблица после реализации:** `колонка | ожидание | факт из реального прогона | match/partial/falsified`.
Любой falsified = возврат на доработку. Каркас таблицы — [references/05-gap-table.md](references/05-gap-table.md).

## 4.5 So-What: outcome или checkpoint

Каждый заявленный результат прогнать через «и что с того для следующего оператора?».

| Уровень | Что это | Verdict |
|---|---|---|
| L0 — действие | файл создан, команда выполнена, коммит сделан | не результат |
| L1 — checkpoint | тест зелёный, страница открывается, PR создан | не результат, нужен ещё один «и что?» |
| L2 — outcome | поведение изменилось, ручной шаг исчез, цикл стал короче | результат |

L0/L1 → задать «и что с того?» ещё раз и вывести на L2. Итог — одна строка
**«Итоговый outcome: {что изменилось для следующего оператора}»**. Если итоговый
outcome не совпал с целью задачи из §0 — это gap, завести строку в таблицу §4.

Типичный L0: файл создан · данные выгружены · тикет обновлён · источник прочитан.
Типичный L1: тест прошёл · PR создан · страница открывается.
Типичный L2: ручной шаг X исчез · цикл короче на N шагов · следующий агент стартует
с подтверждённой точки, а не с восстановления · клиент видит результат без сборки.

**Симметрия языка (owner-facing строки).** «Чего нет» (gap), «что хочу» (jtbd), «что
появится» (output), «что получу» (outcome), «что делать сейчас» (next action) — один
референт с пяти сторон, и все пять пишутся на ОДНОМ языке владельца. Gap/jtbd/outcome
— чистый язык владельца (рубли, часы, клиенты, доверие), без механизма. Output и
next action — рамка владельца + фальсифицируемый механизм хвостом через ` = `
(«Открыть pipeline команде = push в main + пинг в чат, 5 мин»). Технический gap
(`git commit`, `Counter API`) при outcome на языке владельца = остаточный разрыв,
который сгенерирует переделку; стерильный next action без механизма = непроверяемо.
Внутренние dev-таблицы (debug-trace, schema, API-контракт) под это правило НЕ подпадают
— там технический язык и есть точность.

## 5. Negative Space

Чего НЕТ? Тесты для нового кода? Миграция для изменённой схемы? Обработка ошибок? `.env.example`? Логирование? Индекс?

Пиши явно: отсутствует и нужно / отсутствует и не нужно (с причиной).

## 6. Калибровка

**Уверенность: [до]% → [после]% — [причина].**

## 7. Артефакты

Явно ссылки на всё проверенное — пользователь должен открыть сам.

## 7.5 Квитанция-доказательство (обязательна в отчёте)

Отчёт о приёмке несёт **машинную строку-квитанцию**, а не слово «сделано». Строка —
`ключ=значение` через пробел, значения берутся из реального прогона, не из головы.

```
bounds_fail=[] console_errors=0 HTML/JS PASS
represented_files=N total_files=N junk_or_duplicates=0
```

Правила: счётчик расхождений обязан быть в строке и равен нулю при PASS · пустой
список пишется как `[]`, а не опускается · нет прогона → `NOT CHECKED`, квитанция не
выдумывается. Формат под задачу свой, но всегда парсится глазами за секунду.

## 8. Owner effort digest (последний блок ответа)

Дедуп всех Next action из §0 и §4 в одну таблицу — сколько работы остаётся на владельце.

| Приоритет — суть шага | Next action | усилие владельца (0-100) | делаю сам | только владелец |
|---|---|---|---|---|

Шкала: **любой клик, ответ или решение владельца = минимум 50.** Ноль — только когда
агент делает всё сам и владелец не участвует. Оценивается усилие человека, не сложность задачи.

Открытых шагов нет → строка **«Нет шагов для человека»** + одна фраза причины
(не `N/A`, не пустая ячейка).

Цель блока — минимизировать правую колонку от прогона к прогону. Шаг, помеченный
«только владелец», требует одной строки почему агент не может это сделать сам.

## Output Shape

Полный шаблон — default для отчёта о верификации. **Но если задача навязывает
свой строгий формат ответа — не ломай его шаблоном** (урок эвалов 2026-10-01:
verbose-шаблон, конфликтующий с форматом, даёт FAIL за форму при верном содержании).
В этом случае сведи отчёт к квитанции §7.5 + Verdict одной строкой; остальные
разделы держи в рабочей памяти, не в ответе.

```text
CHECK
Expected State FIRST:
Test cases:
Evidence observed:
Gap table:
So-What (L0/L1/L2):
Negative space:
Receipt:
Confidence:
Verdict:
```

## FORBIDDEN

- Отчёт о приёмке без квитанции §7.5 (слово «сделано» вместо машинной строки).
- Начинать проверку без §0 Expected State FIRST.
- Давать verdict по памяти агента без файла, команды, лога, screenshot или output.
- Писать «всё ок» без test cases, gap table и negative space.
- Подменять missing data уверенностью.
- Придумывать actual evidence, логи, содержимое файлов или результаты команд.

## Hard fail

- Нет §0 Expected State FIRST — проверка невалидна.
- Нет Positive / Negative / Edge тест-кейсов — проверка невалидна.
- Нет Gap table хотя бы с `G00 — gaps not found` — проверка невалидна.
- Нет калибровки уверенности — проверка невалидна.
- Есть invented evidence — проверка невалидна.
- «actual» — пересказ без 3-5 конкретных значений из источника (§3.5).
- Результат заявлен на уровне L0/L1 без вывода на L2 (§4.5).
- Нет Owner effort digest (§8), включая явную строку «Нет шагов для человека».
- Нет квитанции §7.5 или её значения не из наблюдённого прогона — проверка невалидна.
