# Оси аудита — шаблоны промтов

Плейсхолдеры: `{REPO}` — имя/путь репо, `{ЯКОРЬ}` — факт из facts pack (§2),
`{LIVE}` — папки живых прогонов (если есть), `{REPORT}` — имя файла отчёта.
Каждый шаблон уже содержит инварианты: эталон, запреты, acceptance.

Формат finding общий для всех осей:

```
## F-NN: <название>
- Code: <путь>:<строка>
- Evidence [O]: <цитата/цифра из артефакта или кода>
- Severity: P0 / P1 / P2 + почему
- Hypothesis: <механизм дефекта, 1-2 строки>
- Fix direction (НЕ реализовывать): <1 строка>
```

## A1 silent-fallbacks — тихие деградации

```
Репо: {REPO}. Задача READ-ONLY: аудит тихих деградаций. Никаких правок — только отчёт.

КОНТЕКСТ: {ЯКОРЬ: известный прошлый кейс тихого fallback этой системы}.

ЗАДАЧА:
1. Найди: except с pass/continue/log-без-re-raise; fallback на fake/offline/placeholder
   без записи деградации в итоговый отчёт/manifest; return None/пустой объект вместо
   raise при ошибке внешнего вызова.
2. Особое внимание: адаптеры внешних провайдеров, retry/failover, отчёты качества.
3. Для каждого: может ли итоговый артефакт пройти проверки, будучи фактически
   деградированным?

ЭТАЛОН: {заполненный F-01 на реальном якоре}

ЗАПРЕТЫ: не менять код; один файл отчёта {REPORT}; не запускать пайплайн;
не трогать .env; не трогать {LIVE}.

ACCEPTANCE: ≥8 findings с file:line, у каждого оценка «видима ли деградация
в итоговых проверках», ранжировано по severity.
```

## A2 inert-wiring — запись без читателя

```
Репо: {REPO}. Задача READ-ONLY: найти поля/артефакты, которые producer пишет,
а runtime-consumer не читает. Никаких правок.

КОНТЕКСТ: {ЯКОРЬ: прошлый inert-wiring инцидент — поле писалось, никто не читал}.

ЗАДАЧА:
1. Список полей ключевых артефактов-контрактов: {перечислить: manifest, handoff,
   отчёты — конкретные имена файлов системы}.
2. Для каждого поля grep'ом найди читателя в runtime-коде (не в тестах).
   Нет читателя ИЛИ читатель только в тестах → кандидат.
3. Env-флаги и конфиг-ключи, которые парсятся, но ни на что не влияют.
4. Для кандидата: заготовка «на будущее» (git log — свежее добавление) или
   сломанный контракт (consumer читает другое имя)?

ЭТАЛОН:
## F-01: <поле>
- Producer: <путь>:<строка>
- Consumer: НЕТ / только тесты / читает другое имя <путь>:<строка>
- Вердикт: broken contract / dead feature / заготовка
- Severity: P0 (контракт сломан, фича молча не работает) / P1 / P2

ЗАПРЕТЫ: не менять код; один файл {REPORT}; не запускать пайплайн; не трогать {LIVE}.

ACCEPTANCE: ≥10 проверенных полей, включая вердикты «wiring OK» (отрицательный
результат тоже результат); у кандидатов file:line ОБЕИХ сторон seam.
```

## A3 deferred-debt — отложенный долг

```
Репо: {REPO}. Задача READ-ONLY: инвентаризация отложенного долга. Никаких правок.

КОНТЕКСТ: в {пути к прошлым аудитам/докам} лежат items со статусом
deferred/skipped. Часть могла быть починена попутно, часть жива. {ЯКОРЬ}.

ЗАДАЧА:
1. Прочитай все файлы {docs/audits/ и аналоги}. Выпиши каждый deferred/skipped item.
2. Для каждого проверь ПО ТЕКУЩЕМУ КОДУ: жив ли дефект? Вердикт:
   ЖИВ / ПОЧИНЕН (commit если нашёл) / НЕ ПРОВЕРЯЕМ СТАТИЧЕСКИ.
3. Собери TODO/FIXME/HACK/XXX в src/ с контекстом. Отметь TODO без причины.

ЭТАЛОН:
## D-01: <item>
- Источник: <docs/...> или <путь>:<строка TODO>
- Статус тогда: deferred | Статус сейчас: ЖИВ — доказательство <путь>:<строка>
- Severity сейчас: P0/P1/P2/умер

ЗАПРЕТЫ: не менять код; один файл {REPORT}.

ACCEPTANCE: покрыты ВСЕ файлы аудит-доков; каждый item с вердиктом и
доказательством; TODO-инвентарь полный (число = grep -rc TODO src/).
```

## A4 defect-matrix — по реальным артефактам (ТОЛЬКО локальный исполнитель)

```
Рабочая директория: {REPO}. Задача READ-ONLY: defect-таблица по завершённому
прогону {путь к артефактам прогона}. Никаких правок, перезапусков, трат.

ЗАДАЧА:
1. Для каждого item прогона: прочитай отчёты ({перечислить имена}), проверь
   плеябельность/валидность итогового артефакта инструментом ({ffprobe/парсер}).
2. Таблица: item | стадия падения | точный симптом (цитата) | итог | стоимость.
3. Сгруппируй симптомы по seams: {список seams системы}.
4. Ранжируй по частоте × severity. Назови ОДИН bottleneck первым и почему.
5. Сверь с отчётами статических осей (если уже есть) — совпадают ли seams.

ЗАПРЕТЫ: ничего не писать в папки прогонов; отчёт только {REPORT};
не запускать рендер/пайплайн/платных провайдеров.

ACCEPTANCE: все items прогона в таблице; каждая строка цитирует путь
артефакта-доказательства; выбран ровно один bottleneck.
```

## A5 contract-drift — схема vs реальность

```
Репо: {REPO}. Задача READ-ONLY: дрейф контрактов между schema/validator и
фактическими producer/consumer. Никаких правок.

КОНТЕКСТ: {ЯКОРЬ: прошлый кейс — schema требовала X, producer писал Y}.

ЗАДАЧА:
1. Найди все schema/validator артефакты ({json-schema, pydantic-модели, пути}).
2. Для каждой схемы: сверь с фактическим producer — пишет ли он поля, которых
   нет в схеме? Не пишет ли обязательные? additionalProperties гейты?
3. Сверь с consumer: валидирует ли он вход схемой или парсит «на доверии»?
4. Версионирование: есть ли поля, которые схема разрешает, но семантика
   разошлась (переименования, deprecated без удаления)?

ЭТАЛОН: {F-01 на реальном якоре с тремя сторонами: schema:line, producer:line,
consumer:line}

ЗАПРЕТЫ: не менять код и схемы; один файл {REPORT}; не трогать {LIVE}.

ACCEPTANCE: каждая найденная схема покрыта вердиктом (drift / OK);
у drift-findings file:line всех сторон.
```

## A6 test-blindspots — слепые зоны тестов

```
Репо: {REPO}. Задача READ-ONLY: где тесты зелёные, а реальный путь голый.

КОНТЕКСТ: {ЯКОРЬ: прошлый кейс — синтетическая фикстура маскировала content-баг}.

ЗАДАЧА:
1. Найди пути кода, исполняемые только при real/live-режиме (env-гейты,
   provider!=fake) — какие из них НЕ имеют integration-теста?
2. Синтетические фикстуры: где тест кормит тон/нуль/заглушку туда, где прод
   получает реальный широкополосный контент? (кодеки, DSP, парсеры медиа).
3. module-scoped autouse-фикстуры: какие моки прячут реальные вызовы, и есть
   ли тест БЕЗ мока на тот же путь?
4. Ranked-список: топ-5 самых опасных непокрытых real-путей.

ЭТАЛОН:
## T-01: <путь кода>
- Code: <путь>:<строка> (real-only ветка)
- Покрытие: unit с моком <тест>:<строка> / integration НЕТ
- Риск: <что сломается молча>
- Severity: P0/P1/P2

ЗАПРЕТЫ: не менять код и тесты; один файл {REPORT}; тесты можно ЗАПУСКАТЬ
только read-only подмножество без сети/трат: {команда}.

ACCEPTANCE: ≥5 real-путей с вердиктом покрытия; топ-5 ranked; file:line у каждого.
```

## Подсказки сборки

- Якорь [O] в КОНТЕКСТ каждой оси — обязателен (SKILL.md §2).
- Облачным агентам: имя отчёта в корне репо (`SILENT_FALLBACKS_AUDIT.md` и т.п.).
  Локальным: в `docs/reports/<audit-name>/`.
- Типовой набор при «система падает в прогонах»: A4 (локально) + A1 + A2 (облако).
- Типовой набор при «долго не аудитили»: A3 + A5 + A6.
