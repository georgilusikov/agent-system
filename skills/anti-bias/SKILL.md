# Anti-Bias Protocol

## 0. Bounded Outcome / RAT Preflight (только если приёмка или evidence неочевидны)

Тривиальная задача — пропусти этот блок.

1. Сформулируй предварительный outcome, видимый владельцу.
2. Прочитай МИНИМУМ источника, достаточный чтобы опознать реального потребителя.
3. Зафиксируй критерий успеха и путь до evidence ДО исполнения — но не вердикт.
4. Выбери одно самое рискованное допущение, один самый дешёвый фальсифицирующий
   тест и одно явное стоп-условие.
5. Бери минимальный представительный сэмпл через реальный путь потребителя. Скажи,
   что он доказывает и что нельзя обобщать; масштабируй только после PASS.
6. Как только выбранный тест отвечает на решение — прекрати расширять research.
7. Проверка приёмки поддерживает продуктовый claim, только если она способна упасть
   ровно на нежелательном outcome. Security / regression / safety-гейты обязательны
   независимо от релевантности жалобе.
8. Жалоба владельца закрывается исполняемой проверкой или явным human review.
   Не закрыта → PASS блокируется, и повторяются затраты, а не исследование.

## 1. Эпистемологические теги

Для каждого утверждения в выводе укажи тип:

- **[O]** Observation — наблюдение из данных/кода
- **[I]** Inference — вывод из наблюдений
- **[S]** Speculation — предположение без прямых данных
- **[A]** Assumption — принятое допущение

Если source/file/report не прочитан — claim о его содержимом не может быть `[O]`; помечай `[S]` или `[A]` и следуй `standards/no-fabricated-evidence.md`.

## 2. Чеклист искажений

- [ ] **Confirmation bias:** Искал ли опровержения, или только подтверждения?
- [ ] **Survivorship bias:** Что НЕ вижу? Какие данные отсутствуют?
- [ ] **Anchoring:** Не зацепился ли за первое найденное решение?
- [ ] **Attribution error:** Это точно баг в коде, а не в моих предположениях?
- [ ] **False mental model:** Проверил ли реальную структуру данных, а не предполагаемую?

## 3. Операциональные правила (применяй до вывода)

1. **Attribution:** Вывод о X — это свойство X или свойство контекста, в котором X встретился?
2. **Counter-Evidence:** Гипотеза кажется очевидной → сгенерируй хотя бы один пример, где она ломается.
3. **Alternatives:** Нашёл подтверждение → добавь альтернативную гипотезу и опиши, каким тестом различить их.
4. **Noise:** Паттерн редкий и яркий → помечай "возможно шум", пока не повторится.
5. **Long Context:** Вывод опирается на последние токены — перечитай начало последовательности.
6. **Ignorance:** Нет данных → не делай негативный вывод. Пиши "я не знаю" или "не проверено".
7. **Honest delivery:** Может ли пользователь получить output без доп. действий, или нужно ещё запустить/проверить/открыть?

## 4. Принципы работы с данными

- **Сначала сырьё.** Анализируй ВСЕ записи без дефолтных лимитов и фильтров. Скрытый `limit=10` = survivorship bias.
- **Никаких предположений о типах.** Определяй тип поля по значению (`isinstance`), а не по имени (`field.startswith("_FLD")`).
- **Анализ исключений.** Ошибки и edge cases — источник информации о структуре, а не шум. Собирай их, не `except: continue`.
- **Независимая валидация.** Проверяй находки 2-3 методами. Совпали — доверие растёт, разошлись — нужен доп. анализ.

## 5. Dual Check

- **INT (внутренний):** Логика и согласованность вывода
- **EXT (внешний):** Проверка по реальным данным/коду/выводу

## 6. Expectations-review mode (optional)

Этот скилл остаётся standalone: его можно запускать до гипотезы и без Expected State.

Если вход содержит expectations из `/check` или `/falsify`, проверь каждое ожидание:

| E-ID | Bias risk | Missing baseline/data | Counterexample | Rewrite |
|---|---|---|---|---|
| E01 | confirmation / attribution / survivorship / anchoring / false model | ... | ... | ... |

Обязательные вопросы:
- Есть ли baseline? Если ожидается "на 30% лучше", откуда стартовая точка?
- Достаточен ли sample size и период наблюдения?
- Какой counterexample сломает ожидание?
- Не является ли ожидание метрикой, которая сама станет true из-за нового ритуала?
- Где окно незнания: сколько дней/кейсов нужно до честного verdict?

## 7. Калибровка

**Уверенность: [до]% → [после]% — [причина корректировки]**

Если уверенность < 60% — укажи явно и предложи способ повысить (доп. данные, тесты, ревью).

## 8. Запрещённые формулировки

Без реальной проверки не пиши: "успешно извлечено", "найдено N записей", "всё работает", "завершено", "готово", "судя по тестам/докам", "по идее должно работать".
