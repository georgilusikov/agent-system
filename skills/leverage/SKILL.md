# Leverage — поиск горлышек, рычагов и слепых зон

Discovery-протокол: строит карту ограничений работающей системы и находит точки,
где малое усилие даёт большой сдвиг. Отличие от соседей: `/debug` копает ОДНУ ошибку
вглубь, `/debug` выбирает между гипотезами ИЗВЕСТНОЙ проблемы, `/prioritize`
ранжирует УЖЕ найденное. `/leverage` работает раньше всех — когда проблема ещё
не сформулирована: «растём медленно», «что-то буксует», «что мы не видим».

## Назначение (claim formats)

Skill нужен когда user уже утверждает что-то вида:
- `система нормальная, просто надо больше ресурсов / трафика / агентов`
- `рост упёрся, не понимаю во что`
- `надо ускорить этап X` (когда X может быть не горлышком)
- `мы всё учли`

и надо проверить систему целиком вместо защиты этих claim.

## When to Use

- `найди рычаги / точки рычага`
- `где бутылочное горлышко / узкое место`
- `слабые места системы / проекта`
- `что мы упускаем / о чём не подумали`
- `почему буксует` (без конкретной ошибки)

## When NOT to Use (anti-scope-creep)

- Конкретная ошибка / traceback / падение → `/debug`
- ≥3 конкурирующих гипотезы ОДНОЙ известной проблемы → `/debug`
- Готовый список идей, нужен порядок → `/prioritize` (ISRICE)
- Свои процессные пропуски в задаче → `/pizdej`
- Профилирование кода одного процесса → профайлер (py-spy, flamegraph), не skill

## Input checklist (лёгкий — discovery type)

- [ ] Названа система и её граница (что внутри, что снаружи)
- [ ] Есть цель системы / метрика потока (что считаем «выходом»)
- [ ] Доступ хотя бы к одному источнику [O]-данных (код, логи, метрики, артефакты)

Нет цели → сначала §1, не скипай: без цели «горлышко» не определено.

## Что ищем / stop-criteria (вместо Expected State — discovery)

Ищем три типа узлов:
1. **Bottleneck** — узел, ограничивающий поток (TOC): перед ним копится очередь,
   после него — простой.
2. **Leverage point** — узел, где вмешательство меняет систему непропорционально
   затратам (лестница Meadows, §4).
3. **Blind spot** — узел, которого НЕТ на карте пользователя: незаданный вопрос,
   неизмеряемая величина, неуслышанный участник.

Stop, когда выполнено ЛЮБОЕ:
- ≥1 bottleneck с [O]-evidence ИЛИ с дешёвым discriminating probe
- ≥3 кандидата-рычага на РАЗНЫХ ярусах Meadows + ≥2 blind spots
- Честный вердикт «потолок системы»: поток равномерный, несколько независимых
  улучшений дают одинаково малый прирост → горлышка внутри нет, ограничение
  снаружи границы системы (см. Грабли)

## Протокол (КАК)

### §1. Система, цель, единица потока
Зафиксируй в 3 строках: границы системы; цель (ради чего существует);
единица потока (заявка, видео, PR, клиент, рубль). Всё дальнейшее — про то,
что мешает потоку этой единицы к цели.

### §2. Карта потока
Выпиши этапы, через которые проходит единица потока, от входа до выхода.
Для каждого этапа собери [O]-признаки (не мнения):
- **очередь ДО этапа** (backlog, WIP, unread, pending)
- **время ожидания vs время обработки**
- **утилизация** (этап всегда занят = кандидат; этап простаивает = не горлышко)

Источники: код, логи, git history, метрики, файловая система, беседы. Каждому
признаку — тег [O]/[I]/[S]/[A].

### §3. Bottleneck scan (TOC)
Constraint = этап с максимальной очередью ДО и простоем ПОСЛЕ. Классифицируй:
- **физический** (мощность: CPU, люди, деньги, лимиты API)
- **процессный** (порядок шагов, ручной гейт, ожидание апрува)
- **policy** (правило/привычка: «делаем по одному», «только я могу»)
- **знание** (никто не умеет / не знает как)

Policy-горлышки чинятся дешевле всех — их ищи особенно. Помни TOC: улучшение
любого узла НЕ на constraint даёт нулевой прирост потока.

**Линза Effort₁/Effort₂:** горлышко — это Effort₁ (мало рук, долго делать) или
Effort₂ (много согласований, уточнений, удержания контекста)? Лечатся по-разному:
первое — ресурсом/делегированием, второе — упрощением интерфейса/правила.

### §4. Leverage scan (лестница Meadows, сжатая до 6 ярусов)
Для каждого кандидата поднимись по лестнице — чем выше ярус, тем сильнее рычаг:

| Ярус | Что менять | Пример |
|---|---|---|
| 1. Параметры | числа, лимиты, бюджеты | +2 воркера, таймаут 30→60 |
| 2. Feedback loops | усилить/ослабить петлю, убрать задержку | ретро раз в день, а не месяц |
| 3. Информационные потоки | кто ЧТО видит и когда | метрика на дашборд владельцу |
| 4. Правила | инцентивы, гейты, права | merge без апрува при зелёном CI |
| 5. Цель системы | ради чего оптимизируем | retention вместо installs |
| 6. Парадигма | из чего цель выросла | «это не продукт, а канал» |

Находка только на ярусе 1 = слабый результат. Ищи минимум до яруса 3.

### §5. Blind-spot scan (о чём не думали)
Четыре обязательных прохода:
1. **Negative space:** чего НЕТ на карте §2? Не измеряется, не логируется,
   не обсуждается? Отсутствие метрики на этапе — само по себе находка.
2. **Assumptions audit:** что принимается как данность? («клиенты хотят X»,
   «этот этап нельзя убрать»). Каждое допущение → тег [A] + стоимость проверки.
3. **Pre-mortem:** «прошёл год, система умерла». Напиши 3 некролога с РАЗНЫМИ
   причинами. Причина, не покрытая картой §2 → blind spot.
4. **Неуслышанные:** кто сталкивается с системой, но не участвует в её
   обсуждении (юзер, оператор, будущий maintainer)? Что бы он назвал первым?

### §6. Мульти-ролевой режим (опционально, для больших систем)
Если система > 1 проекта или анализ упёрся — dispatch 3-5 параллельных
субагентов с ролями из [references/roles.md](references/roles.md):
Constraint Hunter, Systems Cartographer, Pre-mortem Prophet, Naive Outsider,
Data Skeptic. Правила синтеза (обязательны):
- Роли получают ОДИН контекст (§1-§2), но непересекающиеся вопросы
- Агенты завышают severity в ~30% случаев → каждый Critical перепроверь сам
  через Read/данные до включения в карту
- Raw output агента ≠ finding. В карту попадает только после верификации
- Дубли между ролями склей, источник укажи

### §7. Leverage Map (output)

| ID | Узел | Тип | Evidence | Ярус | Probe (дешёвая проверка) | Стоимость probe |
|---|---|---|---|---|---|---|
| L1 | ... | bottleneck / leverage / blind-spot | [O]/[I]/[S]/[A] + факт | 1-6 | что сделать чтобы подтвердить | 5 мин / 1 час / день |

После таблицы:
- **Blind spots** — отдельным блоком, минимум 2 (или честное «не нашёл + где искал»)
- **Verdict:** горлышко найдено / потолок системы / нужны данные (что именно)
- **Next:** топ-3 probe. Ранжирование полного списка → handoff `/prioritize`

Skill выдаёт КАРТУ и PROBE. Фиксы — отдельная задача после подтверждения probe.

## Definition of Done (binary)

- [ ] §1 зафиксирован: система + цель + единица потока (3 строки)
- [ ] Leverage Map содержит ≥5 узлов, у каждого evidence-тег и probe
- [ ] ≥1 узел на ярусе Meadows ≥3 (не только «подкрутить параметр»)
- [ ] Blind-spot блок: ≥2 кандидата, отсутствующих в исходном запросе user
- [ ] Каждый Critical имеет [O]-evidence или probe ≤1 дня
- [ ] Verdict присутствует и один из трёх допустимых
- [ ] Leverage Map в ответе содержит ≥5 строк с ID `L<n>` (таблица, не эссе — проверяемо глазами в чате)
- [ ] Self-test skill: `grep -q '^## FORBIDDEN' ~/.claude/skills/leverage/SKILL.md && echo OK`

## Известные грабли (anti-recurrence)

- **Оптимизация не-горлышка:** улучшил этап не на constraint → поток не вырос,
  время потрачено → защита: §3 сначала, любое улучшение проверяй «это constraint?»
- **Потолок системы принят за горлышко модели:** 3+ независимых подхода дают
  одинаковый прирост ≤ε → это потолок данных/рынка, не внутреннее горлышко →
  защита: вердикт «потолок», ограничение ищи снаружи границы §1 (сессии ML:
  vision/text/geo давали одинаковые ≤0.01)
- **Симптом спутан с constraint:** жалобы и боль видны ПОСЛЕ горлышка, очередь
  копится ДО → защита: ищи очередь, не жалобы
- **Мульти-агентный аудит без верификации:** субагент назвал Critical, я
  транслировал → защита: §6 правила синтеза, Read перед включением в карту
- **Рычаг из головы:** «очевидно, надо менять X» без [O] → это мнение → защита:
  Hard fail на карту из одних [A]

## Связанные скиллы

- `/prioritize` — ранжировать Leverage Map после построения (ISRICE)
- `/debug` — если probe породил ≥3 конкурирующих объяснения
- `/debug` — глубокий RCA подтверждённого горлышка
- `/check` — верификация фикса, когда рычаг применили
- `/anti-bias` — при подозрении, что карта подтверждает заранее любимую гипотезу

## FORBIDDEN

- Объявлять bottleneck по одному [A]-допущению без probe
- Чинить найденное в этом же прогоне — skill выдаёт карту, не патчи
- Передавать raw output субагента в карту без собственной верификации
- Выдавать карту только с ярусом 1 Meadows («добавь ресурсов») — это не анализ
- Fabricated evidence: выдуманные метрики, несуществующие логи, «Status: Verified»
  без команды (см. `~/.claude/standards/no-fabricated-evidence.md`)
- Пропускать blind-spot scan §5 потому что «и так всё нашли»

## Hard fail

- Output без Leverage Map таблицы → это эссе, не анализ
- Все узлы карты = [A] и ни одного probe → карта мнений, невалидна
- Blind-spot блок отсутствует или пуст без «где искал» → главная цель skill
  не выполнена
- Вердикт «горлышко найдено» при равномерном потоке без [O]-очереди → false positive
