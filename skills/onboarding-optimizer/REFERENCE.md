# Onboarding Optimizer — Reference

## Cycle Time (Время цикла сделки)

**Определение:** Общее время от момента, когда пользователь взял продукт «в работу», до получения первого реального результата (value).

```
Cycle Time = Time to First Value
= Регистрация + Обучение + Первая активация + Получение результата
```

**Компоненты:**
1. **Время на обучение** — изучение продукта
2. **Время простоя** — пользователь ничего не делает
3. **Активное время** — взаимодействие с продуктом

**Ключевой инсайт:** Большая часть Cycle Time уходит на «простой» — пользователь не понимает что делать или отвлекается.

**Паттерн в реальных процессах:**
- Типичное соотношение: 10% активной работы, 90% простоя
- Задача в разработке: 1 день в работе, 9 дней в ожидании
- Пользователь в продукте: 5 минут регистрации, 2 дня «подумает»

## Learning Tax (Налог на обучение)

Чтобы получить пользу от продукта, пользователь должен сначала научиться им пользоваться. Это создаёт «отрицательную зону» в начале пути.

```
User Value = Value from Product − Learning Cost − Time Cost

Где:
- Learning Cost = время на обучение продукту
- Time Cost = время на прохождение онбординга

Если User Value < 0 в первые 5 минут → пользователь уйдёт
```

**Формула Learning Tax:**
```
Learning Tax = (Время на обучение + Время на понимание интерфейса) / Общее время

Если Learning Tax > 30% → слишком сложный онбординг
```

## User Journey vs JTBD Scenarios

| Измерение | User Journey | JTBD Scenario |
|-----------|-------------|---------------|
| Фокус | Полный путь пользователя | Конкретный сценарий «хочу сделать X» |
| Масштаб | Дни, недели, месяцы | Минуты, часы |
| Границы | От первого касания до оттока | От триггера до результата |
| Содержание | Все касания с продуктом | Только один сценарий |

**Когда что использовать:**
- **User Journey** — оптимизация всего пути (Cycle Time, retention, LTV)
- **JTBD** — улучшение конкретного сценария (активация, фича)

> «Мы смотрим на одного и того же слона с разных сторон. Можно смотреть на продукт через фичи, а можно — через процесс пользователя. Какой взгляд более полезный? На пользователя, а не на продукт.»

## User-Centric vs Feature-Centric View

**Feature-Centric (плохо):**
- «У нас есть фича X, фича Y, фича Z»
- «Мы добавили новую функциональность»
- «Мы улучшили процесс регистрации»

**User-Centric (хорошо):**
- «Пользователь хочет сделать X»
- «Пользователь получает ценность, когда...»
- «Мы устранили барьер на пути пользователя к ценности»

> «Нам продукт вообще не интересен. Практически не интересен. Нам интересен пользователь.»

**Пример «холодильника»:**
- Разработчики: «Есть фреон, компрессор, терморегулятор»
- Пользователи: «Два ящика сверху, пельмени заморозились»

### Проблема Gap (Разрыва)

```
До фичи: Пользователь делал X способом
После фичи: Пользователь должен делать Y способом
Gap: пользователь должен:
1. Узнать про фичу
2. Понять, зачем она нужна
3. Научиться ей пользоваться
4. Изменить привычку
5. Получить ценность

Каждый шаг — потенциальная точка оттока
```

> «Любая фича не встраивается в процесс пользователя автоматически. Между процессом пользователя и фичей всегда есть дырка (gap). В эту дырку ложатся дополнительные задачи для пользователя.»

## Внутренние продукты (B2E)

**Определение:** Продукты для использования внутри компании.

**Особенности:**
1. **Принудительный характер** — пользователей «заставляют» использовать
2. **Нет конкуренции** — не могут уйти к конкуренту
3. **Язык «Фреона»** — разработчики говорят на языке бизнеса, не пользователей

**Типичные проблемы:**

| На языке «Фреона» | Что на самом деле |
|---------------------|-------------------|
| «Снизить затраты на выполнение задач» | «Я просто хочу быстрее закончить работу» |
| «Повысить эффективность процесса» | «Это бардак, который я не понимаю» |
| «Увеличить автоматизацию» | «Мне приходится делать лишние действия» |

> «Люди не проснутся утром с мыслью "Я хочу снизить затраты на выполнение задач". Это язык бизнеса, а не язык пользователя.»

**Реальные запросы пользователей:**
- «Хочу быстрее закончить работу и уйти домой»
- «Хочу не делать лишних действий»
- «Хочу чтобы было понятно, что делать»

**Как проверить ценность:**
1. «Если бы продукта не было, как бы вы решали задачу?»
2. Насколько продукт проще альтернатив (Excel, бумага)?
3. Используют ли без принуждения?

**Метрики:**
- Activation Rate — начали использовать добровольно
- DAU — используют ежедневно без напоминаний
- Time Saved — сколько экономит
- Complaint Rate — количество жалоб

## Детальные чек-листы по этапам раскадровки

### Этап 1: Первый экран (Первое впечатление)
- [ ] Привлекает ли внимание?
- [ ] Понятно ли, какая выгода от продукта?
- [ ] Вызывает ли желание продолжить?
- [ ] Коммуницируется ли ключевая функция продукта?

### Этап 2: Авторизация / Регистрация
- [ ] Объясняется ли, зачем запрашиваются данные?
- [ ] Не запрашивается ли лишнее на этом этапе?
- [ ] Есть ли возможность пропустить (для быстрого старта)?
- [ ] Вовремя ли запрашивается телефон/адрес?
  - Лучше взять телефон в начале (пока есть доверие и энергия)
  - Не берите данные в самом конце (пользователь устал)

### Этап 3: Обучение / Онбординг
- [ ] Рассказывается ли о пользе фич, а не о самих фичах?
  - Плохо: «В приложении можно делать закладки»
  - Хорошо: «Сохраняй интересные книги и возвращайся к ним»
- [ ] Нет ли формального/скучного онбординга?
  - Если пользователь хочет пропустить → это плохо
  - Кнопка «Пропустить» — маркер проблемного онбординга
- [ ] Понятно ли, что делать дальше?

### Этап 4: Первый целевой экшн
- [ ] Видит ли пользователь, что он должен сделать?
- [ ] Понятна ли ценность этого действия?
- [ ] Обработаны ли возражения?

## Стратегии оптимизации Cycle Time

### Стратегия 1: Устранить лишние шаги
- Плохо: «Регистрация → подтверди email → заполни профиль → настрой → начни»
- Хорошо: «Регистрация → начни (настройка позже)»

### Стратегия 2: Сместить обучение на позже
- Не учите всему сразу — учите по мере необходимости
- Slack не объясняет все фичи при регистрации
- Trello показывает подсказки контекстуально

### Стратегия 3: Сократить время простоя
- Если пользователь ушёл «подумать» → он не вернётся
- Сделайте так, чтобы ценность была за одну сессию
- Не требуйте загрузку фото профиля в первой сессии

### Стратегия 4: Быстрый win
- Маленькая ценность как можно быстрее
- «Твой первый отчёт готов за 30 секунд»
- «Первый результат уже здесь»

## Метрики для отслеживания

| Метрика | Формула | Целевое значение |
|---------|---------|-----------------|
| Time to First Action | Первое действие − Регистрация | < 1 минута |
| Time to First Value | Первая ценность − Регистрация | < 5 минут |
| Idle Time Ratio | Время простоя / Общее время | < 20% |
| Activation Rate | Активировавшиеся / Зарегистрировавшиеся | > 40% |

**Связь с Unit Economics:**
```
Короче Cycle Time → выше Activation Rate → выше LTV → ниже допустимый CAC
```

**Пример из курса (B2B SaaS):**
- Было: Cycle time = несколько недель, низкая активация
- Стало: Cycle time сокращён, больше продаж в первую неделю
- Результат: $150 → $300,000/месяц (13x рост)
- Ключ: ноль новых фич — все улучшения процессные/коммуникационные

## Примеры из курса

### Доставка еды
**Сценарий:** Пользователь хочет заказать еду на сейчас.

**Ошибка 1:** Запрашивают телефон в конце онбординга
- Почему плохо: пользователь устал, может не дойти
- Как правильно: запрашивать в начале, пока есть энергия

**Ошибка 2:** Не показывают время доставки
- Почему плохо: для «прямо сейчас» это критично
- Как правильно: показывать время доставки на первом экране

### Аэропорт (метафора)
**Сценарий:** Человек впервые в новом аэропорту.

**Ожидание:**
- Понять, куда идти (навигация)
- Узнать, что он получит (вылет/прилет)

**Перенос на продукт:**
- Первый экран = «Куда идти» (что делать)
- Очевидная ценность (что я получу)

### Стриминг-сервис
**Ошибка:** Сразу запрашивают телефон.
- Почему плохо: не встроено в сценарий использования
- Сравнение: мессенджер (телефон встроен) vs стриминг (не встроен)

## Методология создания гайда

1. Собрать операционную память экспертов
2. Верифицировать на кейсах с цифрами
3. Протестировать на других экспертах
4. Публиковать небольшими частями (не одним документом)
5. Обновлять по мере появления новых данных

### Чек-лист для гайда
- [ ] Информация верифицирована на нескольких кейсах
- [ ] Есть цифры, подтверждающие рекомендации
- [ ] Указаны исключения (когда правило не работает)
- [ ] Есть примеры «Как плохо» и «Как хорошо»
- [ ] Формат удобен для периодического обращения
- [ ] Получена обратная связь от экспертов
