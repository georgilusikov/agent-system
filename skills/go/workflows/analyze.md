# Analyze: проверка согласованности PRD ↔ plan ↔ issues

Ты получил 3 артефакта из предыдущих workflow:
- PRD (из write-a-prd)
- План (из prd-to-plan) — если был
- Issues (из prd-to-issues) — если были

## Принцип

Ищи **структурные пропуски**, а не стилистические придирки. Если story упомянута в issue хотя бы косвенно (через связанный шаг плана или общий AC) — считай покрытой. Твоя задача — поймать **потерянные story и непокрытые NFR**, не оценить качество формулировок.

## Шаг 1. Извлеки список

Из PRD: все user stories (с их ID) + NFR (из раздела "NFR" или "Non-functional").
Из плана: все фазы/шаги.
Из issues: все задачи с их "Blocked by".

## Шаг 2. Проверки

### 2.1. Stories → Plan/Issues coverage (🔴 GAP)

Для каждой user story из PRD:
- Найди **хотя бы одно** упоминание в плане ИЛИ в issues (по ключевым словам story, названию фичи, core action).
- Если нашёл — **покрыта**, никаких претензий к полноте AC.
- Если НЕ нашёл ни в одном артефакте — 🔴 GAP "Story X не покрыта".

### 2.2. NFR coverage (🔴 GAP только для явных пропусков)

Для каждого NFR из раздела PRD "NFR":
- Найди хотя бы один issue или шаг плана, явно адресующий этот NFR по ключевому слову (security → auth/jwt/permission; observability → log/audit/metric; performance → latency/cache/index; accessibility → wcag/contrast/a11y; validation → validate/400/schema).
- Если нашёл — покрыт.
- Если НЕ нашёл — 🔴 GAP "NFR Y не покрыт".

**Важно:** не считай "подразумевается", "имплементация неявна", "может быть сделано в X" за покрытие или за gap. Либо есть явное упоминание → покрыто. Либо нет → gap.

### 2.3. Orphan issues (🟡 WARN — только настоящие сироты)

Для каждого issue:
- Если он привязан к хотя бы одной story, одному NFR, или одному шагу плана — **не orphan**, пропусти.
- Если issue **не упомянут ни в одной из user stories по смыслу**, ни в одном NFR, ни в одном шаге плана, и его поле `Phase:` пустое или "не указано" — 🟡 WARN "Orphan issue X".

**Признак настоящего orphan:** issue вводит **новый scope**, которого нет в PRD (например, "Redis caching" при том что в PRD нет performance-NFR и в плане нет кэша). Несовпадение стиля AC или гранулярности — НЕ orphan.

### 2.4. Dependency sanity (🔴 GAP)

В issues:
- Нет циклов в "Blocked by".
- Нет ссылок на несуществующие issue ID.

### Что НЕ считать GAP или WARN

- Неявная или подразумеваемая валидация/логирование/обработка ошибок.
- Минорные различия формулировок AC между PRD и issues.
- "Возможный пробел", "риск пропуска", "неоптимальная гранулярность".
- Отсутствие отдельного test-issue при наличии AC в main issue.

Если не уверен — **не записывай**. WARN должен быть конкретным и неоспоримым.

## Шаг 3. Отчёт

Формат:

```
## 🔴 GAPS
- [список конкретных story/NFR ID, которых нет ни в плане, ни в issues. Или "Нет"]

## 🟡 WARNS
- [список orphan issue IDs с указанием, какой scope они вносят сверх PRD. Или "Нет"]

## ✅ Coverage
- Stories: N / M
- NFR: K / L

## Verdict
[✅ PASS | 🟡 WARN | 🔴 FAIL]
```

- **🔴 FAIL:** есть хотя бы один 🔴 GAP. СТОП, не уходим в имплементацию.
- **🟡 WARN:** есть 🟡 WARN, но нет 🔴. Можно идти в имплементацию, но лучше обсудить orphans.
- **✅ PASS:** нет ни того, ни другого.
