# Switching Triggers — анализ переключения на продукт

> **Источник:** `_agent_shared/external_agents/archived_original/jtbd_scenario_analyzer/AGENT.md` (lines 33-200, 393-421).
> **Связь:** дополняет `jtbd-core-principles.md` §3 (Точка А → Точка Б) — фокус на ТРИГГЕРЕ, который запускает переключение.

---

## 🎯 Главный принцип

**Люди НЕ меняют решения без причины.** Инерция привычки огромна. Нужен сильный триггер.
**Обстоятельства >>> осознанность.** В большинстве случаев человек переключается не потому что "решил", а потому что произошёл триггер.

---

## 1. Три типа switching-триггеров

### External Event (внешний триггер)
**Суть:** что-то случилось снаружи — новый контекст, новая ситуация.

**Примеры:**
- "Начал проект с командой → нужен мессенджер"
- "Купил квартиру → нужен ремонт"
- "Переехал в другую страну → нужен другой банк"

### Internal Frustration (внутренний триггер)
**Суть:** "Мне надоело" — достигнут предел терпения по предыдущему решению.

**Примеры:**
- "Skype зависал и глючил → перешёл в Zoom"
- "Gmail вечно забывал отвечать → Superhuman"
- "Excel разваливался на больших данных → Notion"

### Social Influence (социальный триггер)
**Суть:** другие люди заставили — явное или неявное давление окружения.

**Примеры:**
- "Начальник сказал: ставь Slack"
- "Команда перешла в Linear → пришлось"
- "Друзья в Telegram → я тоже"

---

## 2. Уровень осознанности решения

**Спрашивай:** "Почему вы начали использовать [продукт]?"

**Распределение в реальности:**
- **10-20%** → осознанное решение ("сравнил, выбрал")
- **80-90%** → обстоятельства / другие люди / случайно

**Вывод для маркетинга и landing:**
- Перестать писать про "осознанные потребности"
- Писать про **ситуации** (когда X случилось → нужен Y)

---

## 3. Switching Effort — формула барьера переключения

```
Switching_Effort = (Learning + Setup + Risk) × Habit_Strength
```

- **Learning** — стоимость освоить новое решение (минуты-дни)
- **Setup** — миграция данных, настройка, интеграции
- **Risk** — что если новое окажется хуже (репутация, потеря работы, деньги)
- **Habit_Strength** — насколько глубоко въелась старая привычка

**Применение:**
- Если Switching_Effort > Trigger_Strength → переключения не будет
- Снижай Effort (импорт данных в 1 клик, free trial, гарантия возврата)
- Усиливай Trigger в коммуникации (показывай ситуацию, не фичи)

---

## 4. Headline-формула: Ситуация + Триггер + Решение

**Не работает:** "Наш продукт — лучший планировщик ремонта."
**Работает:** "Когда купил квартиру в новостройке (ситуация), и не знаешь с чего начать ремонт (триггер) — мы найдём топ-10 проверенных бригад (решение)."

**Все три элемента в заголовке. Триггер в центре.**

---

## 5. Кейс Boomplanner (8.5× CR)

**Ситуация:** человек купил квартиру в новостройке.
**Триггер:** "Надо сделать ремонт."

**Что хочет (по JTBD):**
- Хороший ремонт
- В срок
- Без косяков при приёмке
- Топ-10 проверенных исполнителей

**Чего НЕ хочет (а команда проецировала):**
- "Простейший путь к интерьеру" (ничего не значит)
- "Защита от мошенников" (страх команды, не клиента)

**Изменение:**
- Заголовок → "Делаем ремонт в новостройках. Превращаем в уютную квартиру."
- Прямые ответы на вопросы пользователя
- Убрали проекцию страхов команды
- Только выгоды, минимум "налога" на чтение

**Результат:** **0.2% → 1.7% CR** (8.5× рост).

## 6. Сегментация сообщений по типу триггера

| Сегмент | Сообщение |
|---|---|
| Осознанные | "Вы ищете решение для [ситуация]? У нас [выгоды]" |
| Вынужденные (соц.) | "Заставили использовать [конкурент]? Вот почему [мы] удобнее" |
| Случайные | "Попали сюда случайно? Вот что мы делаем: [объяснение]" |
| Фрустрированные | "Надоело [проблема]? Решение: [продукт]" |

---

## 7. Когда применять в VANECHKA workflow

**Workflow #2 "Лендинг не конвертит":**
1. Граф работ показывает ГДЕ разрыв (см. `jtbd-core-principles.md §4`)
2. Switching-triggers показывают **ПОЧЕМУ** клиент переключился (или не переключился)
3. Headline-формула применяет триггер в Hero-секции

**Без анализа триггера лендинг описывает фичи. С триггером — описывает ситуацию клиента.**
