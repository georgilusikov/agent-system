# 📋 Phase 5: AUDIT, AFD & NEXT

> **Цель:** провести финальный аудит принятых решений, проверить ограничения и допущения, сформировать план экспериментов и зафиксировать Risk Register. Здесь также проводится диверсионный анализ (AFD) для выявления потенциальных отказов. В конце — CORE‑PIZDEJ self‑check, оценка Confidence/Robustness, Score, Verdict, Hypotheses и Next Actions.

## 📌 Артефакты Phase 5

### 5.1 Constraints Spec (Refined)

Соберите все ограничения из предыдущих фаз и классифицируйте их:
- **Hard Constraints** (нельзя нарушать): регуляторные, технические, ресурсные, временные.
- **Soft Constraints** (желательно соблюдать): UX‑политика, приёмлемый риск, privacу‑trust trade‑off.
- **Unknown Constraints** (надо выяснить): записи «не знаю, разрешено ли …» → план исследования.

Используйте таблицу для каждой категории, укажите источник, кандидаты, которые нарушают ограничения, и последствия. Это даст вход для фильтра в Phase 4.

### 5.2 Assumption Ledger & Experiments

Соберите все предположения ([ASSUME]) из отчёта. Для каждого:
- Определите влияние, если предположение ошибочно (impact high/medium/low).
- Предложите эксперимент: метод, размер выборки, критерий успеха, владелец, срок.
- Определите приоритет выполнения.
 - Укажите **маркер** (что должно наблюдаться, если предположение верно) и **фальсификацию** (что увидим, если неверно).

Составьте Top‑3 эксперимента для критических допущений (value, feasibility, legal/privacy) и привяжите их к Hypotheses.
Незакрытые [ASSUME]/[SPEC] → penalty к Confidence, cap при 2+ критических.

### 5.3 AFD Analysis (Anticipatory Failure Determination)

Используйте `@diversion_analysis` (AFD) для выявления потенциальных отказов и диверсий.

Чтобы AFD был похож на реальные дефекты, применяйте “чёрный прогноз”:
- Диверсия должна **выглядеть как разумная оптимизация** (экономия/ускорение/“лучше KPI”), пройти проверки/QA/приёмку и проявиться в реальных режимах (пик, износ, редкие условия).
- Для “серьёзного” чёрного прогноза разберите систему “по косточкам”: узлы/функции/интерфейсы и прогоните AFD по каждому критичному узлу.

После этого предложите контрмеры и тесты контрмер. Это помогает дополнить Risk Register.

### 5.3.1 Advocate Pass (режим “защитника идеи”)
Для каждой найденной диверсии дайте 3 способа “спасти” идею. Контрмеры должны быть проверяемы: ресурс/ограничение/тест.

### 5.3.2 7‑Level Protection (структура защит)
Для каждой ключевой уязвимости выберите уровень защиты:
1) Исключение, 2) Блокировка, 3) Компенсация, 4) Раннее обнаружение, 5) Управляемый кризис, 6) Защита от дурака, 7) Врождённая безопасность.
Укажите выбранный уровень в Risk Register как “Protection Level”.

### 5.4 ICE Scoring

> **🧮 QUANTITATIVE VERIFICATION (MATH CHECK):**
> Для оценки `Impact`, стоимости экспериментов (в Assumption Ledger) и финансовых/физических рисков **ЗАПРЕЩЕНО** угадывать параметры "на глаз". Вы **ОБЯЗАНЫ** использовать инструмент `run_command` с Python (или code interpreter) для проведения расчетов (Fermi Estimates, юнит-экономика, пропускная способность). Приведите результаты вычислений в отчёте как "Quantitative Proof".

Оцените Top‑3 кандидата по Impact (влияние на KPI), Confidence (достоверность данных) и Ease (сложность реализации). Вычислите ICE Score = I×C×E. Ранжируйте кандидатов и выберите рекомендованный.

### 5.4.1 Продуктовая петля (Hypothesis → Experiment → Metric → Re‑score)
- Свяжите ключевые гипотезы/риски с экспериментами и метриками успеха (минимум 3 эксперимента).
- После планирования экспериментов покажите, как изменится Confidence/Score при успехе/провале (дельта).
- Отметьте, какие эксперименты разблокируют Bear‑сценарий или “переезд”.

### 5.5 Risk Register (Full)

Сформируйте окончательную таблицу рисков (продолжение из Phase 2) с обновлённой оценкой вероятности/влияния, ранними сигналами и планом смягчения. Укажите владельца риска.
Свяжите риски с Assumption Ledger (какие риски снимаются экспериментами), и с Constraints Spec (какие риски проистекают из жёстких ограничений).
Для каждого критичного риска добавьте **порог/триггер** (что должно перейти границу, чтобы риск включился).

### 5.5.1 Проверка отдалённых последствий (Кобра‑эффект / “благими намерениями…”)
Эта проверка нужна, чтобы не принять “красивое” решение, которое ухудшит систему через 1–3 шага адаптации акторов.

**Когда запускать:** на Top‑3 решения (Phase 4) и/или на меры, которые меняют стимулы/правила игры (цены, штрафы, льготы, ограничения, модерация, KPI, комплаенс). Для чисто локальных технических микрофиксов можно сократить.

**4 обязательных вопроса:**
1) **Вакуум:** если мы “убираем X (плохое)”, кто/что займёт освободившуюся нишу и станет “новым X”?
2) **Стимульный откат:** как систему будут “геймить”, чтобы получить выгоду/отчитаться, **не достигая сути**?
3) **Перенос/утечка:** если мы запрещаем/ограничиваем “здесь”, куда это переедет (канал/рынок/юрисдикция/подрядчик) и станет ли там хуже?
4) **Ловушка процесса:** кто заинтересован, чтобы “борьба с проблемой” продолжалась (бюджеты, бюрократия, монополия), и как он будет сопротивляться результату?

**Выход:** таблица 2–3 порядка, ранние сигналы и контрмеры, привязанные к экспериментам.

| Мера/решение | 1‑й эффект (что улучшаем) | Реакция акторов (кто и как адаптируется) | 2‑й эффект (откат/побочка) | 3‑й эффект (дальше) | Ранний сигнал (что измерять) | Контрмера/ограничение | Эксперимент/проверка |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

**Правило:** если найден 2‑й/3‑й эффект уровня “критично” — добавьте это как отдельный риск в Risk Register (с сигналом и защитой), а не оставляйте “в тексте”.

### 5.5.2 Готовность надсистемы (Эффект "Бурана")

Эта проверка блокирует "мёртвые прогнозы", когда идеальная технология прогнозируется для среды, не способной её переварить (кейс космического корабля "Буран" — технически совершенен, но надсистема не потянула затраты на инфраструктуру).

Для каждого из Top-3 кандидатов (Phase 4) оцените 3 ресурса надсистемы:
1. **Физическая инфраструктура:** Есть ли сети/каналы/розетки/логистика требуемой пропускной способности?
2. **Финансовая просадка:** Потребует ли внедрение перестройки смежных индустрий или бюджетов?
3. **Регуляторная "липкость":** Насколько сильна бюрократия в этой доменной зоне?

Если пропускной способности среды не хватает — **заблокируйте немедленный GO** для этого решения, даже если оно технически идеально. Вынесите это в главный риск.

### 5.6 Pivot Cascade (если рекомендован Pivot)

- Мини Phase 2: S-curve стадия (минимум 3 факта или [ASSUME]+тест), Base/Bull/Bear (укороченные, с вероятностями и KPI‑диапазонами), Success Conditions.
- Оцените ориентировочный Score/Confidence/Robustness для Pivot (быстрая оценка).
- Сравните с исходными: показать дельту Score/Confidence и главный риск/ограничение Pivot.
- В отчёт: краткая сводка Pivot (таблица), при этом основная часть отчёта остаётся по исходной системе.

### 5.7 Confidence & Robustness

Рассчитайте **Confidence in Analysis** (качество данных и логики) и **Robustness** (устойчивость решения к Threats/Branches). Используйте базовую формулу и penalties; отдельно укажите penalty за ASSUME без тестов, пропущенных стейкхолдеров, незаполненные секции и дрейф. Робастность снижайте, если сценарии с высоким риском имеют большую вероятность или если решение зависит от хрупких факторов.
Penalties (пример):
- Отсутствуют Evidence tags у ключевых выводов → -15%
- >2 критических [ASSUME]/[SPEC] без эксперимента → cap Confidence 50%
- Нет основного ограничения/лимита → -20%
- Нет связи риска с mitigation/экспериментом → -10%

### 5.8 Score & Verdict

Соберите итоговый Score по 4 категориям (по 0–25, суммарно /100):
1) **Ясность задачи (Job Clarity):** понятен ли MPV/JTBD, кому и за что платят.
2) **Тайминг (Market/Tech Timing):** стадия S‑curve/готовность инфраструктуры/регуляции.
3) **Дифференциация (Differentiation):** чем принципиально отличаемся (PoA/канал/данные) и почему это защищаемо.
4) **Риск (Risk):** насколько риски управляемы (есть пороги/ранние сигналы/контрмеры/эксперименты).

#### Raw Score (обязательный)
`Raw Score` — базовая оценка “в среднем по рынку/контекстам”, без оптимистичных допущений.
- Если нет данных → снижайте Confidence, а не “додумывайте” баллы.
- Сильные утверждения без [DATA]/[OBS] → либо [ASSUME]+тест, либо penalty.

#### Context-fit Score (опциональный, но строго по правилам)
`Context-fit Score` разрешён **только если** выполнены все условия:
1) В Phase 2 выписаны **Условия успеха** (контекст/канал/аудитория/режимы) и они проверяемы метриками.
2) Есть минимум **1 эксперимент** (или план эксперимента с критерием), который верифицирует ключевые условия.
3) Показано, **какие риски исчезают** в этом контексте и какие остаются.

Если хоть одно условие не выполнено — ставьте `Context-fit Score = N/A`.

#### Verdict
Сформируйте Verdict (GO / CAUTION / STOP) на основе `Raw Score`, `Confidence`, `Robustness`:
- **GO:** Raw Score высокий и есть управляемый план экспериментов.
- **CAUTION:** есть ценность, но слишком много незакрытых [ASSUME]/рисков/неясен тайминг → работать через эксперименты или переезд.
- **STOP:** нарушены hard constraints/нет ценности/тайминг плохой и нет разумного переезда.

Для `CAUTION/STOP` обязателен **Pivot Option** (минимум 1 маршрут “переезда”), а при явной смене SUA/KPI — `Pivot Lock` + `Pivot Cascade`.

### 5.9 Hypotheses & Next Actions

Если Verdict ≠ STOP, сформируйте минимум 3 гипотезы: “убить работу X” / “изменить канал Y”. Каждая гипотеза должна иметь механизм, Gap, ICE‑Score, Next Step, Success Metric, Timeline. Затем опишите Next Actions – кто, что, когда, как измерить успех. Укажите критический путь.

## Machine Gate (ОБЯЗАТЕЛЬНО — самый последний блок отчёта)

После отчёта выведи JSON-блок в fence ```json с фактическими числами из ЭТОГО отчёта (не целевыми):

```json
{"phases_completed": 0, "supersystems_count": 0, "subsystems_count": 0, "scenarios_count": 0, "scenarios_probabilities_sum_100": false, "analogs_count": 0, "candidates_count": 0, "litvin_protocol_candidate_present": false, "risk_register_rows": 0, "confidence_decomposed": false, "verdict": "GO|CAUTION|STOP", "quick_kill_triggered": false}
```

Сверка минимумов (из фаз и Depth Adapter): `phases_completed` = 6 (Phases 0–5); `supersystems_count` / `subsystems_count` ≥ depth.min (quick ≥3/≥3, standard ≥6/≥5, deep ≥8/≥6 — Phase 1); `scenarios_count` = 3 (Base/Bull/Bear — Phase 2.4); `scenarios_probabilities_sum_100` = true только если сумма вероятностей сценариев = 100% (Phase 2.4); `analogs_count` ≥ 2 (Phase 2.4.4); `candidates_count` ≥ depth.min (quick ≥5, standard ≥8, deep ≥10 — Phase 4); `litvin_protocol_candidate_present` — минимум 1 кандидат по Протоколу Литвина (Phase 4); `risk_register_rows` ≥ 3 (Phase 5.5); `confidence_decomposed` — таблица 5.7.1 заполнена; `verdict` — одно из GO/CAUTION/STOP (5.8); `quick_kill_triggered` — сработал ли ранний STOP (Phase 0.0.3 / Phase 1.9).

Числа обязаны сходиться с разделами выше. Расхождение = отчёт невалиден.
