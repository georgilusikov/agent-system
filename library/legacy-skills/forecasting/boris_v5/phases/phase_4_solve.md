# 🔧 Phase 4: TRIZ SOLVE & ALTERNATIVES

> **Цель:** выявить корневую блокировку (Root Blockade), сформулировать техническое и физическое противоречия, использовать подходящие TRIZ‑инструменты для генерации не менее 8 кандидатов решений и выбрать Top‑3 по разным принципам действия (PoA). Также необходимо построить морфологическую матрицу и применить фильтр жёстких ограничений.

---

## 💡 Эвристики Phase 4 (metodolog.ru)

**Критерий приоритизации противоречий:** Чем сильнее отрицательная корреляция между параметрами A и B у товаров-лидеров на рынке — тем важнее устранить это противоречие. Рынок уже разделился по этому конфликту, и его разрешение даст прорыв.

**Directed Evolution (DE):** Метод прогнозирования и управления развитием системы. Включает:
1. Прогноз альтернативных вариантов развития
2. Выбор предпочтительного пути
3. Превентивное решение проблем, которые возникнут на этом пути
4. Синтез изобретательских задач для достижения целевого состояния

**Anti-pattern: ступор от противоречий:** Жёсткая формулировка противоречия может блокировать поиск решений. Если "застряли" — переформулируйте задачу через ресурсы или функции вместо противоречий.

## 4.0 Выбор вектора эволюции (ОБЯЗАТЕЛЬНО — ДО генерации кандидатов)

> Прежде чем решать ЧТО делать, определите КУДА система движется по законам TRIZ. Это превращает генерацию кандидатов из мозгового штурма в направленную эволюцию.

### Шаг 4.0.1: S-curve → ZRTS Gate

| Стадия S-curve (из Phase 2) | Приоритетный закон | Направление |
| --- | --- | --- |
| Stage I (Infancy) | Полнота/жизнеспособность | Достроить недостающие подсистемы |
| Stage II (Growth) | Mono → Bi → Poly | Объединять, усиливать, расширять диапазон |
| Stage III (Maturity) | Macro → Micro + Trimming | Свёртывать, переходить на микроуровень |
| Stage IV (Decline) | Смена PoA + Надсистемный переход | Искать альтернативную S-кривую |
| Все стадии | Согласование/Рассогласование (Злотин) | Проверить рассогласованность свойств/ритмов/форм между элементами |
| Все стадии (обязательно) | **Намеренное рассогласование** | Целенаправленно рассогласовать параметры для создания новой функции (пример: активная подвеска = намеренный «конфликт» пружины и демпфера) |

### Шаг 4.0.2: Resource Exhaustion Check (Злотин-Зусман)

Проверить три уровня ресурсов. Для каждого указать не только статус, но и **механизм исчерпания** (почему ресурс больше не даёт результата):

| Уровень | Статус | Механизм исчерпания (ПОЧЕМУ?) | Скрытый ресурс в самом пределе | Следующий уровень |
|---|---|---|---|---|
| **Макро** (конструкция, компоновка, материал целиком) | исчерпан / частично / доступен | *Какой причинно-следственный механизм привёл к пределу?* | *Что этот лимит подсказывает о направлении прорыва?* | → Мезо |
| **Мезо** (структура, поверхность, интерфейсы) | исчерпан / частично / доступен | *Почему именно этот уровень упёрся?* | *Какую информацию несёт сам предел?* | → Микро |
| **Микро** (молекулы, наноструктура, поля) | исчерпан / частично / доступен | *Что физически/логически ограничивает?* | *Можно ли использовать ограничение как ресурс?* | → Смена PoA |

Если текущий уровень исчерпан — переходить на следующий. Если нет — **не спешить на микро**.

> **Злотин:** «Элементы неизвестности» на каждом уровне — это одновременно и причина задач, и **эволюционный ресурс** для их решения. Сам предел указывает направление прорыва. Пример: предел когнитивной нагрузки водителя → функция управления должна полностью уйти от человека → ресурс для обоснования беспилотного транспорта.

### Шаг 4.0.5: Hybridization Protocol (по Злотину — «Закономерности развития PoA»)

> **Источник:** Злотин Б., Зусман А. — «Закономерности развития принципов действия технических систем»: типовой 6-шаговый сценарий эволюции PoA включает обязательный этап гибридизации.

Перед генерацией кандидатов (раздел 4.4) проверьте три типа гибридов:

| Тип гибрида | Родители | Когда применять | Пример-эталон |
|---|---|---|---|
| **Буксирующая бисистема** | Зрелая система + молодая (слабая, но перспективная) | Молодая технология не может конкурировать одна — зрелая «буксирует» её на рынок | Паровик на парусном судне; реактивный бустер на поршневом самолёте |
| **Альтернативная бисистема** | Две зрелые конкурирующие системы с зеркальными ±достоинствами | Обе системы близки к пределу, но у каждой уникальный профиль | Телескоп Максутова (рефрактор + рефлектор → дёшево + качественно) |
| **Гибрид «проигравших»** | Два ранее отвергнутых варианта PoA | Ресурсы макро-уровня исчерпаны у победителей; «проигравшие» стали актуальны | Ранние ДВС вариации, забытые при доминировании бензинового |

**Порядок работы:**
1. Определите: есть ли в Phase 1/Phase 2 упоминание **отвергнутых / конкурирующих PoA**?
2. Для каждого найденного — примените соответствующий тип гибридизации.
3. Для каждого гибрида укажите: **какой новый конфликт он создаёт** → передайте в `@contradictions`.
4. Добавьте жизнеспособные гибриды в список кандидатов (раздел 4.4) с пометкой `[HYBRID]`.

> **Антипаттерн:** Пропускать гибридизацию «проигравших». Злотин подчёркивает: для успешной гибридизации **не обязательно** выбирать наиболее развитую версию — зачастую выгоднее скрестить простые/дешёвые варианты.

## 📌 Артефакты Phase 4

### 4.1 Root Blockade

Опишите главную причину, по которой система не может достичь IKR. Свяжите её с ключевым конфликтом из Phase 1 (надсистема vs подсистема) и фрикцией из Phase 3. Укажите Evidence.

### 4.2 Technical Contradiction (TC)

Формула: «Если улучшить параметр A, то ухудшится параметр B». Используйте таблицу 39 параметров Альтшуллера (или собственные параметры), вызовите `@contradictions` для получения принципов разрешения. Укажите improving/worsening параметры и принципы (#10, #35 и т. д.).

### 4.3 Physical Contradiction (PC)

Формула: «Параметр X должен быть A для функции 1, и не‑A для функции 2». Опишите параметр и функции. Примените принципы разделения (во времени, пространстве, структуре, условии). Укажите Evidence.

### 4.4 Candidate Generation

Используйте комбинацию TRIZ‑инструментов (локальные skills):

- `@functional_analysis` — карта функций и вредных взаимодействий.
- `@forty_principles` / `@contradictions` — генерация по TC/PC.
- `@trimming` — удаление вредных компонентов/функций.
- `@standards` / `@vepoli` — стойкие вредные взаимодействия (су-поле).
- `@effects` — подбор физ/хим эффектов.
- `@benchmarking` / `@fos` / `@reverse_fos` — аналоги/рынки/функции.
  - **"Шаг назад" (Злотин):** При функциональном поиске (FOS) ищите не только современные аналоги, но и **старые, зрелые технологии** в донорских областях. Старые решения лучше изучены, надёжнее и легче адаптируются. Пример: для новой системы фильтрации — изучите не только нанофильтры, но и классические песчаные фильтры (принцип действия проще, адаптация дешевле).
- `@oas_transfer` — перенос свойства, если упираемся в ограничение.
- `@akts` — ценностный перевод, чтобы не потерять MPV.

Сгенерируйте кандидатов по глубине: **quick ≥5, standard ≥8, deep ≥10**. Для каждого кандидата укажите:

| # | Solution | Principle of Action | Contradiction Resolved | New Harm | Resource Used | KPI Link |
|---|---|---|---|---|---|---|
| 1 | | | | | | |
| … | … | … | … | … | … | … |

Обеспечьте разнообразие по принципам действия: один может быть физический (например, haptics), другой — эволюционный (shadowing), третий — когнитивный (переформулирование), четвёртый — организационный и т. д.

### 4.4.2 Протокол Литвина (для “видения будущего” и настоящих скачков)
Этот протокол нужен, когда “улучшать текущую систему” бессмысленно: есть грязная/дорогая/вредная зона, и именно она держит систему в старом принципе действия.

**Шаги (кратко, но обязательно):**
1) **Найдите “серую зону” (Grey Zone):** что в текущем PoA самое грязное/дорогое/опасное/нестабильное (часто это расходник, “химия”, ручной труд, трение, доверие, бюрократия).
2) **Радикальный trimming:** попробуйте удалить серую зону полностью (а не “улучшить на 10%”). Используйте `@trimming`.
3) **Невозможная команда объекту:** сформулируйте “объект, сделай функцию сам” (пример: “грязь, отделись сама от ткани”).
4) **Найти поле/эффект:** какое физическое/информационное поле заставит команду “сработать” (ультразвук, плазма, ионизация, адсорбция, ферменты, поля, микро‑структура). Используйте `@effects` и при необходимости `@vepoli`.
5) **Скан надсистемы (мост к ресурсам среды):** что уже есть вокруг системы (данные, потоки, биосреда, инфраструктура), что можно “украсть” как ресурс (пример: слёзная жидкость как носитель информации). Используйте `@system_operator` + `@resource_analysis`.
6) **Enabling technologies:** для каждого шага назовите 2–5 технологических условий, без которых это не взлетит (иначе это фантазия).

**Требование к выходу:** минимум 1 кандидат в списке должен быть получен этим протоколом и явно помечен (например, “Litvin‑candidate”).

### 4.4.1 Zero‑System Check (обязательный)
Перед тем как “строить систему”, спросите:
- Можно ли выполнить MPV **без системы**? (сдвиг в надсистему/среду/политику)
- Можно ли убрать звено PoA‑цепочки и сохранить KPI? (свёртывание)
Если да — добавьте хотя бы 1 кандидат “нулевой системы” в список.

### 4.5 Morphological Matrix

Постройте таблицу с как минимум тремя осями (например, **Intervention Point**, **Data Type**, **Form Factor**, **Timing**, **Policy/Mode**). Заполните варианты по каждой оси и создайте не менее трёх интересных комбинаций. Это поможет увидеть неожиданные решения.

### 4.6 Constraint Filter

Используйте Constraints Spec из Phase 0/5 (Hard/Soft/Unknown) и главный лимит из Phase 1. Пометьте, кто ломает ограничение, и укажите обход (перенос функции, смена PoA, смена рынка).

### 4.7 Веер возможностей (Top‑3 Alternative Branches)

> **Правило Metodolog.ru (Веер перспектив):** Тризовское прогнозирование не ищет "один самый вероятный путь", оно прописывает **дерево альтернатив (веер)**. Вы **ОБЯЗАНЫ** сгенерировать 3 кандидата, которые представляют принципиально разные эволюционные пути разрешения противоречия.

Выберите три концепта из Списка (Candidate Generation), которые лежат на совершенно разных ветках эволюции. Например:
- Ветка 1 (Идеализация): Полное свертывание (trimming) узла.
- Ветка 2 (Динамизация): Переход на микроуровень, новые физические эффекты.
- Ветка 3 (Надсистема): Переход к нулевой системе / интеграция со средой.

Для каждого заполните подробный шаблон:

```markdown
#### Candidate #N: [Название]
* **Principle of Action:** [механизм]
* **Contradiction Resolved:** [TC/PC и номер принципа]
* **New Harm Introduced:** [что может пойти не так]
* **Resource Used:** [какой ресурс из Phase 1]
* **KPI Link:** [как влияет на Primary KPI]
* **Stakeholder Fit:** [User/Payer/Blocker: +/–/neutral]
* **Feasibility:** [High/Medium/Low]
* **Evidence:** [tag]
```

Убедитесь, что Top‑3 имеют разные PoA и не дублируют друг друга.

### 4.8 Если Top‑3 не срабатывают
- Укажите главный корень провала (ограничение/контекст/PoA).
- Предложите альтернативный путь: перенос функции в среду, смена рынка/канала, замена системы.
- Хэнд‑офф в TRIZ (Елена): `@system_operator` (новая карта), `@contradictions` (барьер), `@trimming`/`@effects` (замена физики), `@benchmarking`/`@reverse_fos` (альтернативные рынки/аналоги).

### 4.9 Авто‑handoff TRIZ (подсказка)
- Предел/лимит → `@limits_strategy` / `@trimming`
- TC/PC неразрешён → `@contradictions` / `@forty_principles`
- Рынок/PoA не тот → `@benchmarking` / `@reverse_fos` / `@oas_transfer`
- Нужна замена физики/взаимодействия → `@effects` / `@vepoli`
- Нужен патентный набросок → `@patent_claims` (независимый + 2–3 зависимых, риски overbreadth/indefiniteness и что вынести в зависимые)
- Нужен веер будущих концептов по 6 линиям эволюции → `@evolution_radar` (матрица 6×4 горизонта)

### 4.11 AFD‑2 Forecast Stress Test (обязательно для Top‑3)

> **Цель:** Каждый прогнозный кандидат — это гипотеза о будущем. Прежде чем передавать её в Phase 5, "попытайтесь её убить" методом AFD‑2 (Певзнер/Злотин). Это НЕ дублирует AFD в Phase 5: здесь мы тестируем **конкретный прогноз**, а не систему целиком.

Для каждого из Top‑3 кандидатов сформулируйте **инверсную задачу:**

> "Как сделать так, чтобы прогноз `[кандидат N]` **гарантированно провалился**, выглядя при этом правдоподобным?"

Затем заполните таблицу по 3 категориям скрытого брака **прогноза** (не системы!):

| Кандидат | А: Отложенный (дефект в допущениях, невидимый сейчас) | Б: Деградация (что со временем ухудшится и убьёт прогноз) | В: Особые условия (какая комбинация факторов сломает прогноз) | Защита (Пока-ёкэ прогноза) |
|---|---|---|---|---|
| #1 | | | | |
| #2 | | | | |
| #3 | | | | |

**Правила:**
- **Категория А (Отложенный):** Какое допущение [ASSUME] прогноза выглядит надёжным, но на самом деле содержит "закладку"? Пример: "Рынок ёмкий" → а если 80% целевой аудитории уже перешли на альтернативу?
- **Категория Б (Деградация):** Что будет **накапливаться** со временем и сделает прогноз невалидным? Пример: износ технологии, потеря конкурентного преимущества, регуляторное удушение.
- **Категория В (Особые условия):** Какая **неожиданная, но вероятная** комбинация событий (геополитика + технологический сдвиг + регуляция) убьёт прогноз? Свяжите с Bear-сценарием из Phase 2.
- **Защита:** Для каждой найденной уязвимости — ранний индикатор (что измерять) + контрмера (что делать, если сработал). Перенесите критичные пункты в Risk Register (Phase 5).

> **Ресурс для диверсии (Злотин):** Используйте для "диверсии" ресурсы, которые **уже есть** в системе/среде — это делает провал реалистичнее. Не придумывайте "а что если метеорит".
