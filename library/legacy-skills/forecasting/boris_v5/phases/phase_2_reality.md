# 🌍 Phase 2: REALITY CHECK & FORECAST

> **Цель:** проверить состояние рынка/среды, оценить угрозы, тайминг и сценарные развилки. Включает Anti‑System анализ, S‑curve позиционирование, проверку пути к границе (distribution), построение нелинейных ветвей и создание базового прогноза (Base/Bull/Bear) с KPI‑траекториями и ранними индикаторами. Здесь же формируется первоначальный Risk Register.

---

## 📌 Артефакты Phase 2

> **🌐 SEARCH GROUNDING (ОБЯЗАТЕЛЬНО):** Определение стадии S-кривой, вероятностей сценариев и анализ аналогов критически зависят от фактов. Вы обязаны использовать веб-поиск (search tool) для нахождения реальных данных (количество патентов, новостей, доля проникновения технологии, реальные примеры провалов). Без ссылок анализ считается недействительным.

### 2.1 Anti‑System (RBCR)

Используйте `@antisystem` для классификации угроз по четырём типам (**R**eplace, **B**ypass, **C**ommoditize, **R**egulate). Для каждой угрозы укажите:
- Актор (кто/что создаёт угрозу)
- Механизм (как именно)
- Временной горизонт
- Серьёзность (1–5)
- Evidence tag.

Выделите «Top Threat» и предложите предварительную стратегию противодействия.

### 2.2 S‑Curve & Evolution Stage

Вызовите `@s_curve` и, при необходимости, `@zrts` (библиотека линий эволюции) для определения стадии развития главного параметра ценности (MPV). Заполните:
- MPV (что оценивается)
- Текущее значение vs теоретический предел
- % освоения
- Стадия (I – Birth / II – Growth / III – Maturity / IV – Decline)
- Horizon (H1/H2/H3)
- Готовность технологии, рынка и модели монетизации.

**Закон мульти-уровня (Злотин, Зусман):** Развитие систем идёт через комплексное использование ресурсов разных уровней (микро/мезо/макро) одновременно. Если система "застряла" на одном уровне — проверьте возможности на других.

**Anti-pattern (кейс CCS, Минакер):** Эксперты часто ошибаются, принимая зрелые технологии (Stage III) за "растущие". Пример: технологии консервации CO2 находятся на 3-м этапе S-кривой, их потенциал роста ограничен, а не "взлетает".

**Метод патентной динамики:** Определяйте стадию S-кривой через анализ графиков подачи патентных заявок. Рост количества документов → Stage I-II, плато → Stage III, падение → Stage IV.

**Исторические прецеденты (Metodolog):** Для вдохновения и поиска реальных примеров перехода систем по линиям эволюции (например, от макро- к микроуровню, развертывание-свертывание) обязательно используйте поиск по базе: вызовите скрипт `python _agent_shared/scripts/metodolog_lookup.py --db evolution_lines --query "линия эволюции"`. Не пытайтесь прочитать файл `_agent_shared/data/metodolog_evolution_lines.md` целиком.

**Корректность выбора параметров:** Точность прогноза критически зависит от выбора параметров для S-кривой. Неверный параметр (например, объём продаж вместо технического показателя) искажает картину.

**Baseline: инерционный прогноз (66%):** Простейший прогноз "завтра как сегодня" даёт точность 66%. Это ваш baseline — если ваш прогноз не лучше, он бесполезен.

В случае отсутствия данных (например, для персонального сервиса) можно сократить, но обосновать. Минимум: стадия + ≥3 [OBS/DATA] или явные [ASSUME] с планом теста.

### 2.2.3 Сравнительная оценка Идеальности (Злотин)

Оцените идеальность системы **сравнительно** (не абсолютно). Запрещено присваивать произвольные числовые веса — LLM не может калибровать их стабильно. Вместо этого заполните таблицу:

| Параметр | Текущая система | Конкурент / Аналог | Прогноз (будущее) | Тренд |
|---|---|---|---|---|
| **Полезные функции** (перечислить 3-5 ключевых) | есть/нет/частично | есть/нет/частично | есть/нет/частично | ↑↓= |
| **Затраты** (вес, цена, энергия, время, сложность) | значение [OBS/DATA] | значение [OBS/DATA] | значение [DERIVE/ASSUME] | ↑↓= |
| **Вредные эффекты** (шум, износ, риск, побочка) | значение [OBS/DATA] | значение [OBS/DATA] | значение [DERIVE/ASSUME] | ↑↓= |
| **Вердикт Идеальности** | — | лучше/хуже/паритет | лучше/хуже | — |

**Правила:**
- Конкурент/аналог ОБЯЗАТЕЛЕН — используйте веб-поиск для реальных данных.
- Если конкурента нет (новый рынок) — используйте предшественника системы или "нулевое решение" (человек выполняет функцию вручную).
- Прогнозируемое состояние в столбце "Прогноз" должно показывать рост идеальности (больше функций ∧ меньше затрат ∧ меньше вреда), иначе прогноз сомнителен.

### 2.2.4 Patent Cluster Scan (обязательно для depth=deep)

Для определения реального вектора инженерной мысли проведите структурированный патентный поиск:

1. **Поиск:** Используйте search tool с запросами вида `"[технология]" patent site:patents.google.com` или `"[технология]" patent application [год]`.
2. **Кластеризация:** Сгруппируйте найденные патенты по подсистемам (рабочий орган, энергия, управление, материал). В какой подсистеме больше всего активности?
3. **Белые пятна:** В какой подсистеме мало или нет патентов? Это потенциальная зона для инноваций.
4. **Тренд:** Растёт количество патентов (→ Stage I-II) или падает (→ Stage III-IV)?

|---|---|---|---|---|
| Рабочий орган | | | | |
| Энергия/источник | | | | |
| Управление/алгоритм | | | | |
| Материал/вещество | | | | |

> **Для depth=quick/standard:** Достаточно 1-2 поисковых запросов и общего вывода. Для depth=deep — полная таблица обязательна.

### 2.2.1 Горизонт прогноза
Уточните, что прогноз делается на горизонте 1/3/10 лет (из Phase 0). Для 10 лет обязательно рассмотреть “замещение кривой” (другая система).

### 2.2.2 Карта дальнего прогноза (3 оси + enabling technologies)
Чтобы не получить “прогноз внутри системы” (который ломается от изменения надсистемы), соберите прогноз в 3 осях:
1) **Законы развития (ZRTS/S‑curve):** куда вынужденно движется система по линиям эволюции / где предел текущего принципа действия.
2) **MPV (параметры ценности):** какие новые/скрытые MPV появятся и какие станут важнее (качество → скорость → удобство → безопасность и т. п.).
3) **Рыночные/надсистемные тренды:** регуляторика, инфраструктура, каналы, демография, стоимость энергии/вычислений/данных.

Для каждой оси укажите **enabling technologies** (какие технологии/решения обеспечат переход), иначе прогноз остаётся “словами”.

### 2.3 Distribution & Path to Boundary

Анализируйте, доступен ли путь к границе (Boundary) для внедрения решения. Используйте `@flow_analysis` (или пропустите при отсутствии необходимости). Составьте цепочку «Источник → Канал → Boundary» и выявите узкие места. Предложите альтернативные пути.

### 2.4 Scenario Forecast (Base/Bull/Bear + “радикальная среда”)

Сформируйте три вероятных сценария развития:

- **Base** — наиболее ожидаемое развитие. Укажите вероятность (в %), траекторию KPI (рост/падение, плато, числа/диапазон) и ранние индикаторы (например, рост определённого типа приложений).
- **Bull** — оптимистичный сценарий. Вероятность (%), прирост KPI (диапазон), индикаторы (новые технологии, рывок интереса).
- **Bear** — пессимистичный сценарий. Вероятность (%), уменьшение KPI (диапазон), индикаторы (регуляция, фильтры).

Добавьте ветку “радикальная смена среды” (регуляция, канал, температура рынка): что ломается, что приходит на смену (альтернативная кривая/PoA).
Сценарии могут опираться на аналоги/линии эволюции (`@benchmarking`, `@zrts`).

### 2.4.5 Калибровка вероятностей (обязательно)

> Запрещено ставить вероятности "от балды". Каждая цифра должна быть обоснована одним из методов ниже.

**Алгоритм:**

1. **Reference Class Forecasting:** Найдите 3–5 аналогичных систем на **такой же стадии S-curve** (из 2.2). Какой процент из них пошёл по Base/Bull/Bear? Это ваш якорь. Если аналогов нет — укажите [ASSUME] и снизьте уверенность на 15%.

2. **Pre-mortem (для Bear):** "Представьте: прошёл 1 год, система провалилась. Почему?" Составьте список из ≥3 причин. Оцените P(причина) для каждой. Сумма = P(Bear) ± поправка.

3. **Anti-anchoring:** Стандартный сплит 50/30/20 ЗАПРЕЩЁН без обоснования. Если вероятности выглядят как "по умолчанию" — переформулировать через reference class или pre-mortem.

4. **Sensitivity check:** Определите ОДИН фактор, который сдвигает вероятности больше всего. Это ваш "canary" — ранний индикатор для мониторинга. Укажите его в Early Signals Risk Register.

5. **Baseline check (Злотин):** Инерционный прогноз "завтра как сегодня" даёт точность 66%. Если ваш прогноз не лучше — он бесполезен. Укажите, чем ваш прогноз отличается от инерционного и почему он точнее.

**Минимальный evidence:** Для каждого сценария — тег [OBS]/[DATA]/[REF] или явный [ASSUME] с планом верификации.

### 2.4.1 Success Conditions & Failure Context
- Зафиксируйте контекст, где идея точно работает: канал, аудитория, KPI, метрика (“Latency < 0.3s в B2B call”). Обоснуйте [OBS]/[DATA].
- Определите контекст, где она провалится: ограничение/нагрузка/психология/регуляция. Укажите, что ломается и почему.

### 2.4.2 Move Routes & Alternative Curve
- Предложите 2–3 маршрута перехода:
  1. Смена канала (например, Real-time → Recording), что меняется, какой новый KPI, риск.
  2. Смена PoA (например, тренажёр → подсказка “экзоскелет”), почему сработает, ограничения.
  3. Смена аудитории/рынка (массовый B2C → нишевый B2B/госзаказ) — как это убирает ограничение.
- Постройте таблицу “Альтернативная кривая” (PoA/канал/рынок, ограничения, риск, триггер). Это помогает быстро сравнить текущую и новую реализацию.

Сосредоточьтесь на рисках, выявленных в Anti‑System и Branches: утрата навыков, когнитивный конфликт, регуляторные блоки, разрушение доверия и т. д.
Каждый риск должен иметь **порог/триггер** и **ранний маркер**, иначе это не прогнозируемый риск, а “страх словами”.

### 2.6.1 Plausibility check (порядки величин) — только для сильных утверждений
Если в Phase 2 появляются сильные обещания/ограничения (в 10 раз дешевле, 1000 км, “почти бесплатно”, “всем можно”), сделайте 1–2 быстрых проверки порядками величин:
- энергия/мощность/тепло,
- стоимость/время/пропускная способность,
- регуляторика/данные.
Выход: “OK/сомнительно/невозможно” + что нужно проверить данными.
