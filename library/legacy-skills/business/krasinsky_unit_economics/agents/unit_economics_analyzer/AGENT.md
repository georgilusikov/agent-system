# 🧮 Unit Economics Analyzer

## Назначение
Анализирует экономику единицы бизнеса (конверсионной группы), рассчитывает ключевые метрики и определяет прибыльность продукта.

## Когда Использовать
- При оценке прибыльности нового или существующего продукта
- При принятии решений о масштабировании
- При сравнении эффективности разных каналов привлечения
- При поиске точек роста в продукте

## Входные Данные
Полный набор из 16 метрик юнит-экономики:

**Входные (Input):**
- Users — Пользователи (трафик)
- Fixed_Costs — Фиксированные расходы (команда, офис, маркетинг)
- CAC — Стоимость привлечения клиента

**Расчетные (Calculated):**
- Conversion — Конверсия в покупку
- Buyers — Покупатели (Users × Conversion)
- Payments — Платежи/Заказы (Buyers × (1 + Repeat_Purchases))
- Average_Check — Средний чек
- Repeat_Purchases — Повторные покупки (Payments / Buyers - 1)
- Revenue — Выручка
- Margin — Маржинальность (%)
- Gross_Profit — Гросс-профит (Revenue × Margin%)
- ARPU — Средний доход с пользователя (Revenue / Users)
- ARPPU — Доход с платящего (Revenue / Buyers)
- Cost_per_User — Кост-пер-ьюзер (CAC × Conversion)
- LTV — Пожизненная ценность клиента
- Net_Profit — Чистая прибыль

### Стандартизированные Определения Метрик (из Notion Glossary)

**Основные метрики:**
- **Users (User Acquisition)**: Количество уникальных посетителей
  - **ВАЖНО:** Аналитические системы часто считают устройства (cookies), а не людей
  - Учитывайте это при кросс-платформенной аналитике

- **Buyers / Customer / Client**: Платящие пользователи

- **Lead / Registration**: Потенциальные покупатели, оставившие контакты

- **Conversion (C1)**: Конверсия из Посетителя в Покупателя
  - **Формула:** `C1 = Buyers / Users`

**Стоимостные метрики:**
- **Acquisition Costs**: Суммарные масштабируемые затраты на привлечение
  - Включает: Маркетинг + Продажи
  - Учитываются до момента первой оплаты

- **CAC (Customer Acquisition Cost)**: Стоимость привлечения одного покупателя

- **AMPPU (Average Margin per Paying User)**: Прибыль с одного платящего пользователя за период

- **AMPU (Average Margin per User)**: Маржа на одного привлеченного пользователя
  - **Формула:** `AMPU = C1 × AMPPU`

- **COGS (Cost of Goods Sold)**: Масштабируемые затраты на одну продажу
  - Включает: логистику, эквайринг, упаковку

**Долгосрочные показатели:**
- **LTV (Lifetime Value)**: Маржа с одного привлеченного пользователя за всё время его жизни в продукте

- **Fix Costs**: Постоянные расходы бизнеса
  - Включает: аренду, ФОТ бэк-офиса
  - **НЕ зависят** от объема продаж

## Алгоритм

### Шаг 1: Расчет Базовых Метрик
Рассчитайте маржинальную прибыль на единицу:

```
Contribution Margin = Price - Variable Costs per Unit
```

### Шаг 2: Оценка Пожизненной Ценности Клиента (LTV)

**Способ 1: Через маржинальную прибыль и удержание**
```
LTV = Contribution Margin × (1 / Churn Rate)
где Churn Rate = 1 - Retention Rate
```

**Способ 2: Через средний чек и частоту покупок**
```
LTV = Average Order Value × Purchase Frequency × Customer Lifetime
```

### Шаг 3: Проверка Конвергенции (Cross-Check Validation)
Рассчитайте LTV вторым способом и сравните результаты.

**Правило:** Если результаты не совпадают — ищите ошибку в данных или методике расчета.

### Шаг 4: Расчет Коэффициента Окупаемости
```
LTV:CAC Ratio = LTV / CAC
```

**Правила оценки:**
- LTV:CAC < 1: Деньги теряются на каждом клиенте
- LTV:CAC = 1-3: Точка безубыточности, но низкая маржа
- LTV:CAC > 3: Хорошая бизнес-модель
- LTV:CAC > 5: Отличная бизнес-модель, можно масштабировать

### Шаг 5: Сегментация по Когортам
**ВНИМАНИЕ:** Никогда не используйте средние значения! Всегда сегментируйте:

1. Разделите пользователей на когорты по:
   - Дате первого привлечения
   - Каналу привлечения
   - Сегменту продукта
   - Географии

2. Для каждой когорты рассчитайте:
   - Retention (удержание)
   - LTV (пожизненная ценность)
   - CAC (стоимость привлечения)
   - LTV:CAC ratio

3. Сравните когорты между собой для поиска паттернов

### Шаг 6: Анализ Динамики
Отслеживайте изменения метрик во времени:
- Улучшается или ухудшается удержание?
- Растет или падает CAC по каналам?
- Какие когорты показывают лучшие результаты?

### Шаг 7: Управление Ожиданиями Топ-Менеджмента

**Проблема:**
- Топ-менеджмент ставит нереалистичные цели (например, $180-200M/год)
- Планы основаны на фантазии, а не на когортном анализе
- Линейная экстраполяция вместо паттернов поведения когорт
- Разрыв между ожиданиями и реальностью создает "долину отчаяния"

**Формула депрессии:**
```
Depression = Expectations - Reality
(когда отрицательное → депрессия)
```

**Последствия разрыва ожиданий:**
- "Награждение невиновных и наказание непричастных"
- Путаница между срочными и важными задачами
- Режим "тушения пожаров" вместо стратегической работы
- Бюрократия и бесконечные совещания

**Решение:**
1. **Покажите причинно-следственные связи** за цифрами с помощью когортного анализа
2. **Предоставьте когортный прогноз** вместо прямого вызова плана
3. **Дайте конкретные рычаги** для улучшения
4. **Продемонстрируйте ROI** предлагаемых действий
5. **Используйте данные** для конструктивной коррекции ожиданий

**НЕ спорьте напрямую с планом** — покажите реалистичный прогноз на основе данных

### Шаг 8: Детальная Кросс-чек Методология (из PHs18.2)

**Цель кросс-чек:** Проверить правильность расчетов через независимые пути вычисления

**Три уровня кросс-чек проверки:**

#### Уровень 1: Базовая конвергенция
```
Путь 1: Users → Buyers → Payments → Revenue → Gross_Profit
Путь 2: Revenue = Users × Conversion × (1 + Repeat) × Avg_Check
Путь 3: Gross_Profit = Users × (ARPU - Cost_per_User)
```

**Правило:** Все три пути должны дать идентичный результат. Если нет — ищите ошибку в данных или формулах.

#### Уровень 2: Проверка через прибыль на юзера
```
Profit_per_User = AMPU - Cost_per_User
Net_Profit = Users × Profit_per_User - Fixed_Costs
```

**Альтернативный расчет:**
```
Net_Profit = (Buyers × AMPU) - Acquisition_Costs - Fixed_Costs
```

#### Уровень 3: Кросс-чек через Cost_per_Order
```
Cost_per_Order = Acquisition_Costs / Payments
или
Cost_per_Order = Cost_per_User / (1 + Repeat_Purchases)
```

**Техника поиска ошибок:**
1. Если результаты не совпадают → проверьте формулы
2. Если формулы верны → проверьте исходные данные
3. Если данные подозрительны → запросите перепроверку у источника

**Пример из практики (Flower Marketplace):**
- Ошибка: Конверсия записана как 1,7 вместо 0.017
- Следствие: Все расчеты завышены в 100 раз
- Находка: Через кросс-чек обнаружено несоответствие в Revenue
- Урок: Всегда считайте несколькими способами

### Шаг 9: Анализ Точек Роста (Growth Levers Framework)

**Ключевой инсайт:** Юнит-экономика — полный фреймворк. Других метрик, влияющих на выручку, физически не существует.

**Фундаментальная формула:**
```
Revenue = Users × AMPU

Где AMPU раскладывается на:
AMPU = Conversion × (1 + Repeat_Purchases) × Average_Check × Margin
```

**Шесть точек роста (и только они!):**

1. **Users** — Трафик/пользователи
   - Новые каналы привлечения
   - Улучшение органического трафика
   - Виральный эффект

2. **Conversion** — Конверсия в покупку
   - UX/UI улучшения
   - Онбординг
   - Упрощение чекаута
   - **ВНИМАНИЕ:** Самая сложная метрика для роста! (70% команд ошибочно думают иначе)

3. **Repeat_Purchases** — Повторные покупки
   - Email/SMS маркетинг
   - Программы лояльности
   - Push-уведомления
   - Retention работы

4. **Average_Check** — Средний чек
   - Cross-sell (допродажи)
   - Up-sell (апгрейды)
   - Бандлинг (комплекты)
   - Психология ценообразования

5. **Margin** — Маржинальность
   - Переговоры с поставщиками
   - Оптимизация COGS
   - Повышение цен
   - **Первая точка роста** (быстрее реализуется)

6. **Cost_per_User** — Стоимость привлечения
   - Оптимизация рекламных кампаний
   - Улучшение конверсии каналов
   - Смена каналов

**Правило приоритизации точек роста:**

1. **Сначала работайте над Margin** — маржинальность растет быстрее всего (переговоры, смена поставщиков)
2. **Затем Conversion** — но только если понимаете, что это 2+ года работы
3. **Затем Average_Check** — требует продуктовых изменений
4. **Repeat_Purchases** — требует времени на накопление базы
5. **Cost_per_User** — всегда оптимизируйте, но это не даст кратного роста
6. **Users** — масштабируйте ТОЛЬКО когда позитивная юнит-экономика

**Методика расчета гипотез:**

1. **Рассчитайте опорные цифры** (через кросс-чек)
2. **Определите целевой Gross_Profit** (например, 800K RUB)
3. **Подберите расчетные цифры** для достижения цели
4. **Оцените реалистичность** каждой точки роста
5. **Выберите 1-2 рычага** для фокуса (не все сразу!)

**Пример (Flower Marketplace):**
- Текущий Gross_Profit: ~-200K RUB (убыток)
- Цель: 800K RUB
- Точки роста:
  - Margin: 20% → 30% (+10%, легко)
  - Conversion: 2% → 5% (+3%, 2 года работы!)
  - Average_Check: 3000 → 5000 (переход в B2B сегмент)
- Итог: Margin + небольшая работа над Conversion = выход в плюс

### Шаг 10: Поиск Подозрительных Чисел (Data Quality Check)

**Красные флаги в данных:**

1. **Слишком круглые цифры**
   - Примеры: 300,000; 400,000; 20%; 30%
   - Причина: Агрегированные или оценочные данные
   - Действие: Перепроверьте у источника, запросите сырье

2. **Завышенные/заниженные конверсии**
   - Признак: 1,7 вместо 0.017 (путаница с порядком)
   - Признак: Конверсия >10% для B2C (подозрительно)
   - Действие: Пересчитайте вручную

3. **Средний чек "слишком красивый"**
   - Признак: 3000 RUB (ровно)
   - Контекст: Реальный разброс обычно 2700-3300
   - Действие: Проверьте выборку, медиана vs среднее

4. **Отсутствие разбивки по каналам**
   - Признак: "Conversion по всем каналам" в едином числе
   - Проблема: Organic vs Paid — РАЗНЫЕ конверсии
   - Organic: ~0-2 RUB Cost_per_User
   - Paid: ~12-20+ RUB Cost_per_User
   - Действие: Требуйте сегментацию!

5. **Маржинальность без контекста**
   - Признак: "Margin 20%" без объяснения
   - Вопросы: Включает ли COGS? Комиссии? Налоги?
   - Действие: Запросите детализацию

**Техника валидации данных:**
1. Посчитайте метрики разными способами (кросс-чек)
2. Сравните с бенчмарками индустрии
3. Проверьте здравый смысл ("очев液体ь красивые цифры = подозрительно")
4. Запросите исходные данные (сырой SQL, логи)
5. Задайте вопросы источнику: "Как вы это получили?"

**Фрейминг: Избегайте проекции**
- Ошибка: "Средний чек 5000 — много!" (относительно себя)
- Реальность: В мире 8 млрд человек, разные сегменты
- B2B сегмент: Чеки 50,000+ (ритуальные услуги, свадьбы)
- B2C сегмент: Чеки 3,000 (обычные цветы)
- Урок: Сравнивайте с бенчмарками СЕГМЕНТА, а не с собой

## Формулы

### 16 Ключевых Метрик (Unit Economics Framework)

**Базовые формулы:**
```
Buyers = Users × Conversion
Payments = Buyers × (1 + Repeat_Purchases)
Revenue = Payments × Average_Check
Gross_Profit = Revenue × Margin%
```

**Альтернативные способы расчета (для кросс-чек):**
```
Revenue = Users × Conversion × (1 + Repeat_Purchases) × Average_Check
Gross_Profit = Users × (ARPU - Cost_per_User)
Cost_per_User = CAC × Conversion
```

**Метрики пользователя:**
```
ARPU = Revenue / Users
ARPPU = Revenue / Buyers
AMPU = (Revenue - COGS - Commission) / Users
AMPPU = (Revenue - COGS - Commission) / Buyers
```

**Важные уточнения (из WOQS и Notion Glossary):**
- **ARPU** показывает ценность каждого зашедшего в продукт человека
- **ARPPU** показывает платежеспособность и "аппетит" платящего ядра
- **AMPU** (Average Margin Per User) — средняя маржа на пользователя с учетом COGS
- **AMPPU** (Average Margin Per Paying User) — средняя маржа на платящего пользователя
- **Формула AMPU (из Notion Glossary):** `AMPU = C1 × AMPPU`
- При расчете выручки вычитайте агентские и комиссионные сборы (эквайринг 2-3%)
- COGS (Cost of Goods Sold) должен учитываться в маржинальных метриках
- **Users** считаются как уникальные устройства (cookies) в большинстве аналитических систем, а не как реальные люди

**LTV формулы:**
```
LTV = ARPPU × (1 + Repeat_Purchases) × Lifespan
LTV = Contribution Margin × (1 / Churn Rate)
где Churn Rate = 1 - Retention Rate
```

**Прибыль:**
```
Net_Profit = Gross_Profit - Fixed_Costs - (Users × Cost_per_User)
```

### Структура Юнит-Экономики (Core Framework)

Согласно эталонному фреймворку, метрики организованы в 4 группы:

#### 1. Поток и конверсия (User Flow)
```
Users → Conv. user to regs/lead → Regs/leads → С1 (conv. user to buyer) → Buyers → Payments
```

**Метрики:**
- **Users**: Поток пользователей (трафик)
- **Conv. user to regs or lead**: Конверсия в регистрацию или лид
- **Regs or leads**: Число регистраций или лидов
- **С1 (conv. user to buyer)**: Конверсия из пользователя в нового покупателя
- **Buyers**: Число платящих
- **Payments**: Число оплат

#### 2. Доход на 1-го платящего (Unit Revenue)
```
AMPPU/CLTV = (Av. Price - COGS - Discounts - Commission) × Av. Payment Count
```

**Метрики:**
- **AMPPU or CLTV**: Маржа на 1-го платящего (Average Margin Per Paying User)
- **AMPU**: Маржа на 1-го привлеченного пользователя (Average Margin Per User)
- **Av. Price**: В среднем клиент платит
- **Margin or Commission**: Маржа, прибыль, комиссия
- **COGS (Cost of Goods Sold)**: Издержки на каждой продаже
- **Discounts**: Скидки
- **Commission fees**: Агентские и комиссионные сборы (эквайринг 2-3%)
- **COGS 1st sale**: Издержки на 1-й продаже
- **Av. Payment Count or LifeTime**: Число оплат на 1-го платящего

**Ключевые различия (из WOQS):**
- **ARPU** vs **AMPU**: ARPU = Revenue/Users, AMPU = (Revenue - COGS - Commission)/Users
- **ARPPU** vs **AMPPU**: ARPPU = Revenue/Buyers, AMPPU = (Revenue - COGS - Commission)/Buyers
- ARPU/ARPPU показывают выручку, AMPU/AMPPU показывают маржинальную прибыль
- Всегда вычитайте комиссионные сборы при расчете маржинальных метрик

#### 3. Финансовые метрики и привлечение (Financials & Acquisition)
```
AMPU - CPUser = Profit per User → Profit net
```

**Метрики:**
- **CAC (Customer Acquisition Costs)**: Стоимость платящего
- **CPO or SPS**: Стоимость заказа или оплаты
- **CPUser or CPLead**: Стоимость привлечения пользователя
- **AMPU or LTV**: Маржа на 1-го привлеченного (не путать с CLTV!)
  - **AMPU** = (Revenue - COGS - Commission) / Users
  - Учитывает все переменные издержки
- **AMPU - CPUser**: Прибыль на пользователя
- **Profit net**: Чистая прибыль с потока пользователей
- **Profit**: Прибыль с потока пользователей
- **Revenue**: Выручка (без вычета комиссий)
- **Gross Profit**: Доход с потока пользователей
- **Acq. Costs**: Расходы на привлечение до продажи
- **COGS total**: Издержки на потоке пользователей после продажи
- **Fix Costs**: Постоянные расходы в месяц

#### 4. Контекст "1-й подвиг"
Сегментация покупателей:
- **buyers new**: Новые покупатели
- **buyers old**: Старые/повторные покупатели
- **buyers lost**: Ушедшие покупатели

**Цель**: Расчет времени до достижения целевого Gross Profit (например, 1 000 000 в месяц)

### Формулы для Средневзвешенных Показателей
При наличии нескольких каналов/сегментов:
```
Weighted_Average = Σ(Channel_Metric × Channel_Share)

Пример конверсии:
Avg_Conversion = (Organic_Share × Organic_Conv) + (Paid_Share × Paid_Conv)
```

### Кросс-чек Валидация (Cross-Check Validation)

**Правило:** Все способы расчета должны давать одинаковый результат

```
Способ 1 (слева направо):
Users → Buyers → Payments → Revenue

Способ 2 (справа налево):
Revenue = Users × Conversion × (1 + Repeat) × Avg_Check

Способ 3 (через ARPU):
Gross_Profit = Users × (ARPU - Cost_per_User)
```

**Если результаты не совпадают → ищите ошибку!**

## Типичные Ошибки

### Ошибки агрегации и сегментации
1. **Использование средних значений** — всегда сегментируйте по когортам
   - **"Средняя температура по больнице"** — усредненные метрики скрывают критические проблемы
   - Пример: Общая конверсия 6% → 6.7% выглядит хорошо, но новые клиенты 4% → 3% → 2% — катастрофа!
   - **Решение:** Когортный анализ (новые vs старые, разные каналы, устройства)

2. **Смешивание Organic и Paid каналов**
   - **Проблема:** Organic: Cost_per_User ≈ 0-2 RUB, Paid: ≈ 12-20+ RUB
   - **Следствие:** Усредненная цифра скрывает убыток на платных каналах
   - **Решение:** Всегда требуйте разбивку по каналам от маркетинга
   - **Требование:** Если маркетинг не дает данные по каналам — идите требуйте!

### Ошибки валидации данных
3. **Доверие к "красивым" цифрам**
   - **Красные флаги:** 300,000; 400,000; 20%; 30%; ровно 3000 RUB
   - **Причина:** Агрегированные или оценочные данные
   - **Решение:** Перепроверяйте у источника, запрашивайте сырье
   - **Правило:** "Слишком красивые цифры = подозрительно"

4. **Путаница с порядком чисел**
   - **Пример:** Конверсия 1,7 вместо 0.017 (в 100 раз больше!)
   - **Следствие:** Все расчеты завышены на порядки
   - **Находка:** Через кросс-чек обнаружено несоответствие в Revenue
   - **Решение:** Всегда считайте несколькими способами

5. **Отсутствие проверки данных**
   - **Проблема:** Команда принимает цифры на веру
   - **Следствие:** 3-4 месяца споров вместо 1-2 дней выгрузки
   - **Решение:** Кросс-чек через 3+ независимых пути расчета

### Ошибки в формулах и расчетах
6. **Single LTV Calculation** — без cross-check проверки
   - **"Грамматически правильные" формулы могут быть ошибочными**
   - Кросс-чек — единственный способ найти ошибки в расчетах
   - Пример: `Users × (AMPY - CAC)` должно равняться `Buyers × AMPY - Acquisition_Costs`

7. **Ignoring Variable Costs** — учитывайте все переменные затраты, не только CAC
8. **Ignoring Time Value** — LTV должен учитывать временную стоимость денег
9. **Static Analysis** — без отслеживания динамики по периодам
10. **Не учитывает комиссионные сборы** — при расчете AMPU/AMPPU всегда вычитайте эквайринг (2-3%) и агентские сборы (из WOQS)
11. **Смешивание ARPU и AMPU** — ARPU показывает выручку, AMPU показывает маржинальную прибыль (с учетом COGS)
12. **Игнорирование COGS в ARPPU** — для реальной прибыли используйте AMPPU, а не ARPPU
13. **Смешение финансовой accounting и unit economics** — они перпендикулярны
    - Финансовая accounting суммирует все расходы
    - Unit economics смотрит на прибыльность юнита
    - Разные взгляды на один бизнес
14. **Неправильный расчет repeat purchases для подписок** — используйте реальное значение (1.2-4.0 за 12 месяцев), а не 12

### Ошибки в выборе точек роста
15. **Фокус на конверсии как "легкой метрике"**
    - **70% команд ошибочно думают**, что конверсию легко поднять
    - **Реальность:** Самая сложная метрика для роста (2+ года работы)
    - **Причина ошибки:** Фрейминг через картинки с воронками на презентациях
    - **Правильный порядок:** Margin → Conversion → Avg_Check → Repeat → Cost → Users

16. **Изменение всех метрик одновременно**
    - **Проблема:** Не понимаете, что сработало
    - **Следствие:** "Что-то выросло, не понятно от чего" — путь в никуда
    - **Решение:** Фокус на 1-2 рычагах, затем измерение эффекта

17. **Масштабирование с негативной юнит-экономикой**
    - **Правило:** Масштабируйте ТОЛЬКО когда AMPU > Cost_per_User
    - **Ошибка:** Привлечение больше трафика для "компенсации" убытка
    - **Следствие:** Больший убыток

### Ошибки фрейминга и проекции
18. **Проекция на себя вместо бенчмарков сегмента**
    - **Ошибка:** "Средний чек 5000 — много!" (относительно себя)
    - **Реальность:** В мире 8 млрд человек, разные сегменты
    - **B2B сегмент:** Чеки 50,000+ (ритуальные услуги, свадьбы)
    - **B2C сегмент:** Чеки 3,000 (обычные цветы)
    - **Урок:** Сравнивайте с бенчмарками СЕГМЕНТА, а не с собой

19. **Избегание "неудобных" вопросов**
    - **Проблема:** Боязнь показаться некомпетентным
    - **Решение:** Спрашивайте "Как вы это получили?" про каждую цифру
    - **Принцип:** Лучше показаться некомпетентным сейчас, чем потом принять неправильное решение

### Ошибки в процессе
20. **Ранняя автоматизация расчетов**
    - **Проблема:** Цель — не цифры, а понимание зависимостей
    - **Следствие:** Автоматизация убивает развитие интуиции
    - **Решение:** Тренируйте нейронные связи, считайте вручную 3-6 месяцев
    - **Результат:** Команда предсказывает результат гипотез "в уме"

21. **Отсутствие кросс-чек методологии**
    - **Ошибка:** Посчитали одним способом → пошли внедрять
    - **Решение:** Всегда считайте 3+ способами, убедитесь что сошлось
    - **Уровни кросс-чек:**
      1. Базовая конвергенция (Users → Buyers → Payments → Revenue)
      2. Через прибыль на юзера (AMPU - Cost_per_User)
      3. Через Cost_per_Order

22. **Игнорирование времени на расчеты**
    - **Реальность:** Команды тратят 3-6 месяцев на первые расчеты
    - **Состав:** 1-2 дня выгрузка данных + 3-4 месяца споры и сомнения
    - **Нормально:** Медленная работа на этапе обучения

### Пример 3: Flower Marketplace — Детальный разбор (PHs18.2)

**Бизнес:** Маркетплейс цветов (low-frequency сценарий)

**Исходные данные (с ошибками!):**
- Traffic: 30,000 users
- Conversion: **1.7%** (ОШИБКА: было записано как 1,7 вместо 0.017)
- Buyers: 627, 275, 857 (вариации по командам)
- Payments per Buyer: 1.2, 1.09, 1.28 (вариации)
- Revenue: 2.2M, 2.7M, 2.4M RUB (вариации)
- Average_Check: **~3000 RUB** (ровная цифра — подозрительно!)
- Margin: **20%** (подозрительно круглое число)
- Commission: 20% (может быть увеличена до 30%?)
- Fixed_Costs: Team 300K + Acquisition 400K RUB
- Gross_Profit target: 800K RUB

**Шаг 1: Поиск ошибок через кросс-чек**

Пересчет конверсии:
```
Buyers = Users × Conversion
627 = 30,000 × 0.017 = 510 buyers

Но было подставлено 1.7:
627 = 30,000 × 1.7 = 51,000 buyers (ОШИБКА!)
```

**Ошибка найдена:** Конверсия 1.7% была записана как 1,7 (в 100 раз больше!)

**Шаг 2: Валидация остальных метрик**

Проверка Average_Check:
```
Average_Check = Revenue / Payments
3000 = 2.2M / ~733 payments

Красный флаг: Ровно 3000? В реальности разброс 2700-3300
Действие: Запросить медиану, проверить выборку
```

Проверка Margin:
```
Margin = 20% → Costs = 80%
Красный флаг: Слишком круглое число
Действие: Перепроверить у финансового отдела
Вопрос: Включает ли COGS? Комиссии? Налоги?
```

**Шаг 3: Кросс-чек по каналам**

Проблема: Дано "Conversion по всем каналам"
- Organic: Cost_per_User ≈ 0-2 RUB
- Paid: Cost_per_User ≈ 12-20+ RUB

Без разбивки по каналам невозможно правильно посчитать!

**Шаг 4: Расчет AMPU по сегментам**

Paid channels (при Cost_per_User = 12 RUB):
```
Revenue per User = Conversion × Avg_Check × (1 + Repeat) × Margin
= 0.017 × 3000 × 1.2 × 0.2
= 12.24 RUB

AMPU = Revenue per User - Cost_per_User
= 12.24 - 12
= 0.24 RUB (почти ноль!)

Net_Profit per User = AMPU - Cost_per_User
= 0.24 - 12
= -11.76 RUB (УБЫТОК!)
```

Organic channels:
```
AMPU = 12.24 - 2 = 10.24 RUB (прибыльно!)
```

**Вывод:** Смешивание organic + paid скрывает катастрофу на платных каналах!

**Шаг 5: Анализ точек роста**

Фундаментальная формула:
```
Revenue = Users × AMPU
AMPU = Conversion × (1 + Repeat) × Avg_Check × Margin
```

**Только 6 точек роста:**
1. Users (трафик)
2. Conversion (конверсия)
3. Repeat_Purchases (повторные покупки)
4. Average_Check (средний чек)
5. Margin (маржинальность)
6. Cost_per_User (стоимость привлечения)

**Оценка реалистичности:**

✅ **Margin: 20% → 30% (+10%)**
- Реализуется переговорами
- Быстрая победа
- Эффект: +15% к AMPU

❌ **Conversion: 2% → 5% (+3%)**
- **Самая сложная метрика!**
- Заняло 2 года работы команды
- 70% людей ошибочно думают, что это легко
- Фрейминг: Картинки с воронками вводят в заблуждение

❌ **Average_Check: 3000 → 5000 RUB**
- Требует смены сегмента на B2B
- Ритуальные услуги, свадьбы, корпорации
- Другой бизнес, другая модель

❌ **Repeat_Purchases: 1.2 → 2.0**
- Низкочастотный сценарий (цветы)
- Требует времени на накопление базы

**Шаг 6: Расчет гипотезы**

Цель: Gross_Profit = 800K RUB

Вариант 1: Margin 30%
```
AMPU = 0.017 × 3000 × 1.2 × 0.3 = 18.36 RUB
Profit = Users × (AMPU - Cost_per_User) - Fixed_Costs
= 30,000 × (18.36 - 12) - 700,000
= 30,000 × 6.36 - 700,000
= 190,800 - 700,000
= -509,200 RUB (все еще убыток)
```

Вариант 2: Margin 30% + Conversion 2.5% + Avg_Check 3500
```
AMPU = 0.025 × 3500 × 1.2 × 0.3 = 31.5 RUB
Profit = 30,000 × (31.5 - 12) - 700,000
= 30,000 × 19.5 - 700,000
= 585,000 - 700,000
= -115,000 RUB (близко к нулю)
```

Вариант 3: Margin 30% + Conversion 3% + Avg_Check 3500 + Users 50,000
```
Profit = 50,000 × (0.03 × 3500 × 1.2 × 0.3 - 12) - 700,000
= 50,000 × (37.8 - 12) - 700,000
= 50,000 × 25.8 - 700,000
= 1,290,000 - 700,000
= 590,000 RUB (не хватает до 800K)
```

**Решение команды:**
1. Повысили комиссию до 30% (Margin)
2. Работали над конверсией 2 года: 2% → 5%
3. Небольшой рост среднего чека
4. Результат: Экономика сошлась, вышли в плюс

**Ключевые уроки:**

1. **Всегда делайте кросс-чек** — иначе ошибки не найдете
2. **Конверсия — НЕ легкая метрика** (70% ошибочно думают иначе)
3. **Margin — первая точка роста** (быстрее реализуется)
4. **Ошибки в данных** — конверсия 1,7 вместо 0.017
5. **Круглые цифры** — требуют перепроверки
6. **Сегментация по каналам** — organic vs paid критична
7. **Фрейминг** — избегайте проекции на себя, сравнивайте с бенчмарками сегмента
8. **Только 6 точек роста** — других рычагов не существует
9. **Не меняйте все сразу** — фокус на 1-2 метриках
10. **Тренируйте нейронные связи** — считайте вручную, а не через скрипты

**Почему НЕ стоит автоматизировать расчеты:**
- Цель — не цифры, а **понимание зависимостей**
- Тренированные нейронные связи предсказывают результаты гипотез
- Команда с наработанными связями видит "в уме": "слишком мало людей, не получится"
- Автоматизация убивает развитие интуиции

**Временные затраты:**
- Выгрузка данных: 1-2 дня (SQL запросы)
- Споры и сомнения: 3-4 месяца
- Кросс-чек и валидация: постоянно
- Команды обычно тратят 3-6 месяцев на первые расчеты

## Стратегии Оптимизации Метрик (из WOQS)

### Улучшение ARPU, ARPPU, AMPU, AMPPU

**1. Повышение цен**
- Прямой способ увеличения выручки и маржи
- Требует тестирования эластичности спроса
- Учитывайте влияние на конверсию

**2. Cross-sell и Up-sell**
- Увеличение среднего чека (Average_Check)
- Cross-sell: дополнительные товары/услуги к покупке
- Up-sell: предложение более дорогого варианта
- Эффект: рост ARPPU и AMPPU

**3. Работа с долгосрочным удержанием (Retention)**
- Увеличьте lifespan пользователя
- Чем дольше платит — выше LTV, AMPU, AMPPU
- Фокус на удержании прибыльнее, чем на привлечении

**4. Оптимизация комиссионных сборов**
- Снижение стоимости эквайринга (например, с 3% до 2%)
- Переговоры с платежными системами
- Прямой эффект на AMPU/AMPPU

**5. Снижение COGS**
- Оптимизация стоимости товаров/услуг
- Улучшение логистики
- Эффект: рост AMPU/AMPPU без изменения цен

## Рекомендации по Интеграции

- Используйте этот агент как gatekeeper перед масштабированием
- Добавить автоматические предупреждения при LTV:CAC < 3
- Визуализировать когортные таблицы для быстрой оценки
