# A/B Testing Mistakes Framework

**Источник:** ARTICLE_Habr_JUG.txt
**Версия:** 1.0.0

## Суть
Эксперименты в product development часто проводятся с критическими ошибками, которые приводят к ложным выводам, потере данных и принятию неверных решений. Framework описывает основные ошибки и способы их предотвращения.

## Пошаговый Алгоритм Проверки Эксперимента

### 1. Проверка наличия тестирования
**Ошибка #0: Отсутствие тестов**
- Катить всё сразу в продакшн без проверки
- Даже простые тесты предотвращают грубые ошибки

**Действие:** Всегда проводить проверку гипотез перед продакшеном

### 2. Оценка качества экспериментов
**Ошибка #1: Слишком много плохих экспериментов**
- Тестирование "всё подряд" без фокуса
- Потеря времени на незначительные метрики

**Действие:** Фокусироваться на ключевых метриках:
- **Churn rate**: отток пользователей
- **Лояльность**: время отсутствия пользователя и частота посещений

### 3. Проверка логирования
**Ошибка #2: Отсутствие логов для перерасчёта**
- Сырые данные не сохраняются
- Невозможно перепроверить результаты
- Теряется возможность дополнительного анализа

**Действие:**
- Всегда сохранять сырые данные (raw logs)
- Вести полное логирование всех событий
- Обеспечить возможность пересчета метрик

### 4. Проверка зависимости данных
**Ошибка #3: Зависимость данных (Data Dependency)**
- Один пользователь совершает много событий
- Обычные статистические тесты не учитывают зависимость
- Ложные выводы из-за повторных событий

**Действие:**
- Сводить данные к показателям "на пользователя" (per user)
- Агрегировать данные за весь период эксперимента
- Использовать методы для зависимых выборок

## Ключевые Принципы

### Per User Aggregation
```python
# ПЛОХО: тестировать каждое событие независимо
events = [user1_e1, user1_e2, user1_e3, user2_e1, ...]

# ХОРОШО: агрегировать по пользователям
user_metrics = [
  user1_total_events,
  user2_total_events,
  ...
]
```

### Raw Data Preservation
- Сохранять все события в исходном виде
- Не удалять логи после завершения эксперимента
- Должна быть возможность пересчитать любые метрики

### Key Metrics Focus
Вместо сотни метрик фокусироваться на:
- **Retention**: возвращаются ли пользователи
- **Churn**: какой процент пользователей отваливается
- **LTV**: пожизненная ценность клиента

## Типичные Ошибки

| Ошибка | Проблема | Решение |
|--------|----------|---------|
| #0: Нет тестов | Катить в прод без проверки | Даже простые тесты помогают |
| #1: Плохие эксперименты | Тестировать всё подряд | Фокус на Churn/Loyalty |
| #2: Нет логов | Нельзя перепроверить | Сохранять raw logs |
| #3: Зависимость данных | Пользователь = много событий | Агрегировать per user |

## Чек-лист Перед Запуском A/B Теста

- [ ] Определены ключевые метрики (Churn, Лояльность)
- [ ] Настроено сохранение сырых логов
- [ ] Данные агрегируются "на пользователя"
- [ ] Рассчитан MDE
- [ ] Выборка достаточна (≥10K на вариант)
- [ ] Проведен AA тест

## Примеры Применения

### Пример 1: E-commerce
**Ситуация:** Тестируем новую корзину

**Плохо:**
- Тестировать каждую транзакцию независимо
- Один пользователь делает 5 покупок → 5 точек данных

**Хорошо:**
- Агрегировать: средний чек на пользователя
- Количество покупок на пользователя
- Общая сумма на пользователя

### Пример 2: SaaS приложение
**Ситуация:** Тестируем новый onboarding

**Метрики:**
- Churn rate (отток)
- Time to first activation
- Session frequency (лояльность)

**Агрегация:**
- Per user: завершил ли onboarding
- Per user: время до активации
- Per user: количество сессий/неделю
