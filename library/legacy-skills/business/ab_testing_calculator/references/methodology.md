Полная статистическая база скилла `ab_testing_calculator`. Подгружается по запросу из SKILL.md (progressive disclosure). Источник — курс PHs18 (Испытания 3 и 5) + статьи Habr (RetailRocket, JUG).

## §1. Statistical foundations (frequentist framework)

### Что A/B тест на самом деле делает

A/B тест **не доказывает** правильность гипотезы. Он показывает только: **отличаются ли два набора данных?**

> "A/B тесты по своей природе ничего не говорят про ваши гипотезы. Они ничего про это не знают." — PHs18

**Нулевая гипотеза H₀:** в варианте A и B будет одинаково.
**Альтернативная H₁:** есть значимое различие.

Тест отвергает H₀ при достаточном `|Z-score|`, но это не подтверждает бизнес-гипотезу — только различие в данных.

### Метрическая триада (три кита)

При оценке результатов **всегда** смотри три показателя:

1. **Конверсия** — основной показатель.
2. **Средний чек** — критически важен для выручки.
3. **Выручка / user** — итоговый показатель эффективности.

⚠️ **Anti-pattern:** Конверсия выросла на 10%, средний чек упал на 15% → прибыль упала. Решение по одной конверсии = метрическая слепота.

### Confidence interval — это не точность

CI = область наибольшей вероятности, не гарантия. Реальное значение метрики живёт под всей кривой распределения от −∞ до +∞.

> Аналогия: граница поверхности воды не существует с точки зрения квантовой механики, но физик может на неё опереться. CI — такая же "опора" для решений с погрешностью.

**Практический вывод:** деньги всегда на стороне того, кто принимает решения с НЕТОЧНЫМИ данными. Аналитик, ждущий "точности", теряет ~1M ₽/неделю простоя команды (пример из курса).

## §2. Formulas

### Терминология: SD vs SE (важно — частый источник ошибок)

- **SD (standard deviation) одного наблюдения биномиальной величины:** `SD = √(p × (1 − p))`. Не зависит от `n`.
- **SE (standard error) среднего по выборке размера `n`:** `SE = SD / √n = √(p × (1 − p) / n)`.

**CI вокруг среднего (доли) считается через SE, не через SD.** Формула CI = `Mean ± Z × SE`. Не делить на `√n` повторно — это даст в `√n` раз меньший CI и приведёт к ложной уверенности в результате.

### Confidence Interval (95%) для доли

```
CI = p ± Z × SE
SE = √(p × (1 − p) / n)
```

где:
- `Z = 1.96` для 95% доверия (≈2σ). Для 99% `Z = 2.576`. Для 90% `Z = 1.645`.
- `p` — наблюдаемая конверсия в долях (не процентах). Для `p = 0.026` (2.6%): `SE = √(0.026 × 0.974 / n)`.
- `n` — размер выборки.

Например, при `p = 0.05`, `n = 10 000`: `SE = √(0.05 × 0.95 / 10000) = 0.00218`, `CI = 0.05 ± 1.96 × 0.00218 = 0.05 ± 0.00427` (≈ ±0.43 pp).

### Minimum Detectable Effect (MDE)

```
MDE = 2 × CI_width
```

**Правило:** ты НЕ можешь обнаружить эффекты меньше MDE. Если ожидаемое улучшение `< MDE` — тест бесполезен.

### Sample size для заданного MDE

```
n = (Z² × p × (1 − p)) / MDE²
```

где:
- `Z = 1.96` для α = 0.05.
- `p` — ожидаемая baseline конверсия.
- `MDE` — желаемый минимальный эффект (в долях).

**Расширенная версия с power (1−β):**

```
n = (Z_{α/2} + Z_{1-β})² × 2 × p × (1 − p) / MDE²
```

где `Z_{1-β} = 0.84` для power 0.8, `Z_{1-β} = 1.28` для power 0.9.

### Z-score для сравнения двух выборок

```
Z = (p_B − p_A) / √(SD_A² / n_A + SD_B² / n_B)
```

где `SD_A = √(p_A × (1 − p_A))`, `SD_B = √(p_B × (1 − p_B))` — SD одного наблюдения. Деление на `n_A` / `n_B` под корнем превращает SD в SE среднего. Если `|Z| > 1.96` → разница статистически значима при α = 0.05.

### Сегментация увеличивает требуемую выборку

```
n_segmented = n_base × number_of_segments
```

Пример: baseline 10 000, сегменты Desktop+Mobile → нужно 20 000.

## §3. Worked examples

### Пример 1: Недостаточная выборка

**Ситуация:**
- Трафик: 55 000 пользователей/неделю.
- Базовая конверсия `p = 0.26%` = 0.0026.
- `SE = √(p × (1 − p) / n) = √(0.0026 × 0.9974 / 55000) = 0.000217`. Note: это **SE** среднего по выборке (не SD одного наблюдения; per-observation SD = √(p(1−p)) ≈ 0.0509).
- `CI = 1.96 × SE = 1.96 × 0.000217 = 0.000425` ≈ **±0.04 pp**.
- `MDE = 2 × CI ≈ ±0.085 pp` (≈ ±0.085%).

**Проблема:** ожидаемое улучшение `0.01%` < `MDE 0.085%` (в ~8.5 раз меньше).

> Note: исходный AGENT.md цитировал `CI = ±0.11%` (и `MDE = ±0.22%`) с другой формулой/округлением. Корректное значение `±0.04 pp` соответствует конвенции `Z=1.96 × SE`. Историческая цифра сохранена в `_provenance/AGENT.original.md` как archive reference.

**Verdict:** ❌ kill. Тест не способен обнаружить ожидаемый эффект.

**Решение:** собирай больше данных, или запускай без A/B (если риск низкий), или укрупняй scope гипотезы (ожидаемый эффект 1-2 pp вместо 0.01).

### Пример 2: AA-тест (валидация методологии)

**Ситуация:**
- Стоимость прогона: ~$30 000 (упущенный трафик).
- Результат: вариант A = 5.5 ± 0.6%, вариант B = 5.5 ± 0.6%.

**Verdict:** ✅ методология корректна, можно запускать реальный AB.

**Если AA показал разницу** → методология сломана, не запускай AB до фикса (проблема в сегментаторе, IP-фильтрации, или распределении трафика).

### Пример 3: Сегментация маскирует эффект

**Ситуация:**
- Aggregated: разница 0% (без эффекта).
- Desktop: +15% конверсия ✅
- Mobile: −10% конверсия ❌

**Verdict:** iterate. Aggregated решение = неправильное. Реальный signal противоположный по сегментам — нужно смотреть отдельно.

**Critical срезы для сегментации:**
- Устройство: Desktop / Mobile / Tablet.
- География: разные города/страны.
- Источник трафика: organic / paid / social / email.

### Пример 4: Падение прибыли при росте конверсии

**Ситуация:**
- Конверсия: A = 3%, B = 3.3% (+10%, статзначимо).
- Средний чек: A = $50, B = $42.5 (−15%).
- Выручка/user: A = $1.50, B = $1.40 (−6.7%).

**Verdict:** ❌ kill. Статистически значимый рост конверсии маскирует падение прибыли.

**Решение:** не катить B; разбираться, почему чек упал (возможно, B привлёк low-value сегмент).

### Пример 5: CI-only sanity check (не для launch decision)

> **WARNING — quick CI-only sanity check.** Реальный launch требует power-aware формулы (SKILL.md §2.2). Power-aware companion ниже.

**Дано:**
- Baseline `p = 5%` = 0.05.
- Желаемый MDE = 0.5 pp = 0.005.
- α = 0.05, Z = 1.96, power 1−β = 0.8 (Z_{1-β} = 0.84).

**§2.1 Quick CI-only (sanity check, НЕ для launch):**
```
n = (Z² × p × (1 − p)) / MDE²
n = (1.96² × 0.05 × 0.95) / 0.005²
n = (3.8416 × 0.0475) / 0.000025
n = 0.1825 / 0.000025
n ≈ 7 300 на вариант
```

**§2.2 Power-aware (MANDATORY для launch decisions):**
```
n = (Z_{α/2} + Z_{1-β})² × 2 × p × (1 − p) / MDE²
n = (1.96 + 0.84)² × 2 × 0.05 × 0.95 / 0.005²
n = 2.80² × 0.095 / 0.000025
n = 7.84 × 0.095 / 0.000025
n = 0.7448 / 0.000025
n ≈ 29 800 на вариант
```

**Сравнение:** power-aware (~29 800) ≈ 4.08× больше, чем quick CI-only (~7 300). Использовать **только power-aware** для решения о запуске. CI-only годится лишь как первая прикидка достижимости.

**Total (power-aware):** 59 600 пользователей на тест. При трафике 5 000/неделю → ~12 недель. При 5 000/неделю CI-only "прикидка" 3 недели — ловушка underpowered launch.

**Идеальный A/B тест по Retail Rocket (5 шагов):**
1. Выдвигаем гипотезу.
2. Создаём альтернативу (вариант B).
3. Случайно делим трафик.
4. Одновременно замеряем конверсию + другие метрики.
5. Определяем достоверность (статзначимость).

**Требования:**
- Равномерное распределение по всем срезам.
- Исключение сотрудников компании из теста.
- Учёт аннуляций и исполняемости заказов.
- Использование специализированных сегментаторов.

## §5. Common mistakes

### M0. Метрическая слепота (фокус только на конверсии)
**Проблема:** смотришь только на конверсию, игнорируешь чек и выручку.
**Решение:** триада метрик обязательна.

### M1. Паралич анализа (ожидание идеальных данных)
**Проблема:** "данных недостаточно" → ждёшь 4 недели → теряешь ~4M ₽ простоя команды.
**Решение:** прыжок веры обязателен — деньги на стороне тех, кто действует с погрешностью.

### M2. Игнор стоимости ожидания
**Проблема:** считаешь cost A/B теста, не считаешь cost задержки решения.
**Решение:** сравнивай cost теста vs cost ожидания. Иногда ship-without-test выгоднее.

### M3. Отсутствие тестов вообще
**Проблема:** катишь всё в прод без проверки.
**Решение:** даже простые тесты ловят грубые ошибки.

### M4. Слишком много плохих экспериментов
**Проблема:** тестируешь всё подряд без фокуса.
**Решение:** ключевые метрики — Churn rate, лояльность (время отсутствия + частота возвратов).

### M5. Отсутствие сырых логов
**Проблема:** не сохраняешь raw data → не можешь верифицировать выводы.
**Решение:** всегда сохраняй raw logs и пересчитывай метрики при необходимости.

### M6. Data dependency (зависимые наблюдения)
**Проблема:** один пользователь делает 10 покупок → стандартные тесты ломаются.
**Решение:** агрегируй "на пользователя" (per user). Не считай каждую транзакцию независимо.

```python
# ПЛОХО: тестируешь каждую транзакцию
transactions = [u1_t1, u1_t2, u1_t3, u2_t1, ...]

# ХОРОШО: агрегируешь по пользователям
user_metrics = [u1_total, u2_total, ...]
```

### M7. Тест без проверки MDE
**Проблема:** ожидаешь эффект 0.01%, но MDE 0.22% — тест бесполезен.
**Решение:** считай MDE ДО запуска.

### M8. Слишком маленькая выборка
**Проблема:** 1000 на вариант → CI огромный.
**Решение:** минимум 10 000 на вариант.

### M9. Игнор сегментации (агрегированная ловушка)
**Проблема:** Desktop +15%, Mobile −10%, aggregated 0%.
**Решение:** всегда смотри сегменты Desktop/Mobile, география, источник трафика.

### M10. Не учтены выбросы в среднем чеке
**Проблема:** один заказ $10 000 ломает средний.
**Решение:** Байесовская статистика ИЛИ trim 3-5% самых крупных и мелких заказов.

### M11. Сотрудники в выборке
**Проблема:** сотрудники тестируют изменения → их поведение искажает.
**Решение:** исключай по IP, внутренним аккаунтам, специальным сегментаторам.

### M12. Не учтены аннуляции
**Проблема:** считаешь все заказы → растёт конверсия, но реальных денег нет.
**Решение:** учитывай только оплаченные и доставленные. Отдельно — аннулированные.

### M13. Неверная интерпретация AA-теста
**Проблема:** "AA показал разницу → методология плохая" — но AA должен показывать отсутствие разницы.
**Решение:** AA-разница = bug методологии, не "норма".

### M14. Stop тест на первом peek
**Проблема:** sequential testing без α-correction → false positive растёт.
**Решение:** используй sequential тесты (Pocock, O'Brien-Fleming) или фиксированный sample size.

### M15. P-hacking при выборе сегментов
**Проблема:** перебираешь 20 сегментов → найдёшь "значимый" по случайности (Bonferroni не применяется).
**Решение:** заранее определяй гипотезу и сегменты, или применяй multiple comparison correction.

## §6. IS-RICE bridge — когда нет данных

Если нет baseline / нет трафика / нет sample size → **не запускай A/B**, переключись на качественную оценку.

**IS-RICE формула:**

```
IS-RICE = (Impact × Sigma × Confidence) / (RICE_effort × Cost)
```

где:
- **Impact** — потенциальный размер эффекта (1-10).
- **Sigma** — уверенность в impact (0-1, "вера в успех").
- **Confidence** — качество данных (0-1).
- **RICE_effort** — трудозатраты (1-10).
- **Cost** — деньги/риск.

IS-RICE quick-eval (planned skill — currently stub at `_agent_shared/skills/business/isrice_prioritizer/`, только AGENT.md без SKILL.md). Для полной методологии см. PHs18 video provenance (§4) + IS-RICE формулу выше; стаб будет завершён в R9 wave-2.

**Когда переключаться:**
- Sample size < 10 000 на вариант.
- Trafic < 1000/неделю.
- Срочное решение (баг безопасности, комплаенс).
- Низкий риск (best practice, мелкие UI-фиксы).

## §7. Когда НЕ использовать A/B тесты

| Ситуация | Причина |
|---|---|
| Маленькие выборки (<10K на вариант) | CI слишком широкий, MDE слишком большой |
| Эффект меньше MDE | Тест не сможет обнаружить |
| Срочные изменения (баги, безопасность, комплаенс) | Нет времени на тест |
| Низкий риск (best practice, мелкие фиксы) | Cost теста > value |
| Фундаментальные изменения продукта | Не сравниваешь A vs B — меняешь концепцию |

**В таких случаях:** ship-and-monitor, IS-RICE качественная оценка, или прыжок веры с отслеживанием ключевых метрик после релиза.

## §8. Quality checklist (до закрытия задачи)

- [ ] Рассчитан CI (95%).
- [ ] Определён MDE.
- [ ] Выборка ≥10K на вариант.
- [ ] Ожидаемый эффект > MDE.
- [ ] Проведён AA-тест (если возможно).
- [ ] Учтена сегментация (Desktop/Mobile, география, источник трафика).
- [ ] Статзначимость проверена (`|Z| > 1.96` или `p < α`).
- [ ] Сохранены сырые логи для перерасчёта.
- [ ] Данные агрегированы per user (не per transaction).
- [ ] Проверена метрическая триада: конверсия + средний чек + выручка.
- [ ] Исключены сотрудники компании.
- [ ] Учтены выбросы в среднем чеке (trim 3-5% или Байес).
- [ ] Проверена равномерность распределения по срезам.
- [ ] Учтены аннуляции и исполняемость заказов.

## §9. Принципы из ProductDo (для контекста)

- **70% тестов должны быть зелёными** — цель A/B в крупных компаниях: предотвращать деградацию, ловить 100-500 мелких негативов.
- **A/B не доказывает гипотезу** — только показывает различие наборов данных.
- **Статреальность ≠ физреальность** — все измерения с ошибкой; реальное значение от −∞ до +∞.
- **Данные всегда недостаточны** — прыжок веры обязателен.
- **Cost ожидания > cost ошибки** часто.
- **Гауссиана — приближение** — нормальное распределение работает не везде (особенно для денег).
