# 🧪 A/B Testing Calculator

## Назначение
Рассчитывает статистическую значимость A/B тестов, доверительные интервалы и минимально обнаруживаемый эффект (MDE).

## Когда Использовать
- Перед запуском A/B теста (планирование)
- При анализе результатов A/B теста
- Для определения необходимого размера выборки
- Для оценки целесообразности A/B тестирования

## Входные Данные
- Размер выборки (количество пользователей в каждой группе)
- Базовая конверсия (текущее значение метрики)
- Ожидаемое улучшение (в абсолютных процентах)
- Уровень доверия (по умолчанию 95%)

## Ключевые Принципы

### Принцип 0: "Физики vs Математики" — Философия Измерений

**Суть конфликта:**
- **Математик/Аналитик:** "Одно не равно двум", нужны точные доказательства, данные всегда недостаточно
- **Физик/Продакт:** "0 продаж vs 0.0001 продажа — РАЗНИЦА ЕСТЬ", решение нужно сейчас

**Аналогия с поверхностью воды:**
- Математик: "Границы поверхности воды не существует" (квантовая механика, диффузия молекул)
- Физик: "Граница есть, я могу на что-то опереться"
- **Урок:** Любое число имеет доверительный интервал, но решения нужно принимать

**Доверительный интервал — это не точность:**
- Реальная конверсия находится от -∞ до +∞ (под всей кривой распределения)
- CI = Mean ± (Z × SD / √n) — это лишь область наибольшей вероятности
- **Пример:** Конверсия 2% ± 0.2% означает диапазон 1.8%-2.2%, но реальное значение может быть любым

**В чем проблема A/B тестов:**
- A/B тест — это просто "циферки" и "верительный интервал" + шум
- Нулевая гипотеза: "в варианте A и B будет одинаково" — тест об этом НЕ знает
- Тест говорит только: "Отличаются ли два набора данных?"
- Гипотеза ваша работает или нет — тесту неизвестно

**Почему аналитики не хотят принимать решения:**
- Данных всегда недостаточно (по определению)
- Из-за A/B тестов данных сильно много не получить
- Аналитик "ссыкотно" сделать ставку (страх ошибки)
- **Правда:** Вам всегда придется делать "прыжок веры" — данные всегда неточны

**Стоимость ожидания (на примере курса):**
- Простой команды каждую неделю стоит ~1M рублей
- Математик ждет точности → теряет деньги
- Физик принимает решение с погрешностью → зарабатывает

**На чьей стороне вы?**
- Деньги всегда на стороне тех, кто принимает решения с НЕТОЧНЫМИ данными
- Аналитики с их "всегда не хватает данных" — тормоз бизнеса
- **Правило:** Лучше приблизительное решение сейчас, чем точное решение никогда

### Принцип 1: "A/B тесты показывают только различие двух наборов данных"
- A/B тест НЕ доказывает правильность вашей гипотезы
- A/B тест показывает: "Отличаются ли эти два набора данных?"
- 90% продуктовых экспериментов не проводились бы без A/B

**Ключевой урок:**
> "A/B тесты по своей природе ничего не говорят про ваши гипотезы. Они ничего про это не знают."

### Принцип 2: Формула идеального A/B теста (из практики Retail Rocket)
1. **Выдвигаем гипотезу** — четко формулируем, что хотим проверить
2. **Создаем альтернативу** — вариант Б с изменением
3. **Случайно делим трафик** — равномерное распределение на группы
4. **Одновременно замеряем** — конверсию и другие метрики
5. **Определяем достоверность** — статистическую значимость

**Требования для идеального теста:**
- ✅ Равномерное распределение аудитории по всем срезам
- ✅ Исключение сотрудников компании из теста
- ✅ Учет аннуляций и исполняемости заказов
- ✅ Использование специализированных сегментаторов

### Принцип 3: Метрическая триада (Три кита A/B тестирования)
При оценке результатов ВСЕГДА смотрите на три показателя:

1. **Конверсия** — основной показатель
2. **Средний чек** — критически важен для выручки
   - ⚠️ Рост конверсии при падении чека может СНИЗИТЬ прибыль!
3. **Выручка** — итоговый показатель эффективности

**Пример ошибки:** Конверсия выросла на 10%, но средний чек упал на 15% → прибыль упала

## Алгоритм

### Шаг 1: Рассчитайте Доверительный Интервал (Confidence Interval)

```
CI = Mean ± (Z × SD / √n)

где:
- Z = 1.96 (для 95% доверия, ≈2 сигмы)
- SD = Standard Deviation (стандартное отклонение)
- n = Sample Size (размер выборки)
```

**Пример:**
```
Если:
- Конверсия = 0.26%
- n = 55,000 пользователей/неделю
- SD ≈ √(p × (1-p) / n) для биномиального распределения

CI = ±0.11%

Значит: реальная конверсия между 0.15% и 0.37%
```

### Шаг 2: Определите Минимально Обнаруживаемый Эффект (MDE)

```
MDE = CI Width × 2

Если CI = ±0.11%, то MDE = 0.22%
```

**Правило:**
Вы НЕ можете обнаружить эффекты меньше, чем MDE!

**Пример:**
- MDE = 0.22%
- Если вы ожидаете улучшение на 0.01% → тест бесполезен
- Минимальное обнаруживаемое изменение = 0.22%

### Шаг 3: Проверьте Достаточность Выборки

```
Минимальный размер выборки = 10,000 пользователей на вариант

Почему:
- При меньшей выборке CI слишком широкий
- Вы не обнаружите реальные эффекты
- Результаты будут ненадежными
```

**Если выборка недостаточна:**
- Не проводите A/B тест
- Используйте альтернативные методы
- Соберите больше данных

### Шаг 4: Оцените Сегментацию

```
Требуемый размер выборки с сегментацией:
n_segmented = n_base × number_of_segments

Пример:
- Базовая выборка: 10,000
- Сегменты: Desktop + Mobile
- Требуемая: 10,000 × 2 = 20,000
```

**Правило:**
Большая сегментация → более широкие CI → больший MDE

**Критические срезы данных (из практики Retail Rocket):**
Результаты могут СИЛЬНО отличаться в зависимости от:
- 📱 **Устройство**: Desktop vs Mobile/Tablet
- 🌍 **География**: разные города
- 📊 **Источник трафика**: organic, paid, social, email

⚠️ **Всегда делайте сегментацию!** Иначе можно принять неправильное решение.

### Шаг 5: Проведите AA Тест (Валидация)

**Цель AA теста:**
- Проверить методологию тестирования
- Убедиться, что система работает корректно

**Ожидаемый результат:**
- Нет значимой разницы между вариантами
- Пример: 5.5±0.6% (вариант A) vs 5.5±0.6% (вариант B)

**Если AA тест показывает разницу:**
- Ваша методология имеет проблемы
- Не запускайте AB тест до исправления

**Стоимость AA теста:**
- Пример: $30,000 (упущенная выгода от трафика)
- Необходимость: критически важна для валидации

### Шаг 6: Рассчитайте Статистическую Значимость

```
Z-score = (Mean_B - Mean_A) / √(SD_A²/n_A + SD_B²/n_B)

Если |Z-score| > 1.96:
    → Разница статистически значима (p < 0.05)
```

**Особенности для среднего чека:**

Для оценки среднего чека используйте один из двух методов:

1. **Байесовская статистика** — более современный подход
2. **Усечение выбросов** — отсекайте 3-5% самых крупных и мелких заказов

⚠️ **Почему это важно:** Экстремальные значения (один гигантский заказ) могут ИСКАЗИТЬ картину и показать ложный эффект.

### Шаг 7: Примите Решение

```
IF |Разница| > MDE AND Статистически значимо:
    → Разница реальна

IF |Разница| < MDE OR НЕ значимо:
    → Недостаточно данных (нужна большая выборка)
```

## Формулы

### Доверительный Интервал (95%):
```
CI = Mean ± (1.96 × SD / √n)
или approximately
CI = Mean ± (2 × SD / √n)
```

### Стандартное Отклонение (для конверсии):
```
SD = √(p × (1-p) / n)

где p = конверсия (в долях, не процентах)
```

### Минимально Обнаруживаемый Эффект:
```
MDE = 2 × CI_width
```

### Размер Выборки (для заданного MDE):
```
n = (Z² × p × (1-p)) / MDE²

где:
- Z = 1.96 (для 95% доверия)
- p = ожидаемая конверсия
- MDE = желаемый минимальный эффект
```

## Типичные Ошибки

### Ошибка #0: Фокус только на конверсии (Метрическая слепота)
**Проблема:**
- Смотрите только на конверсию
- Игнорируете средний чек и выручку
- Рост конверсии может маскировать падение прибыли

**Пример:**
- Конверсия: +10% ✅
- Средний чек: -15% ❌
- Итого: ПРИБЫЛЬ упала!

**Решение:**
- Всегда смотрите на метрическую триаду: Конверсия + Средний чек + Выручка
- Принимайте решения на основе прибыли, не только конверсии

### Ошибка #-1: Ожидание идеальных данных (Паралич анализа)
**Проблема:**
- Данные всегда неточны (доверительный интервал)
- Ждете "больше данных" для принятия решения
- Аналитики всегда говорят "данных недостаточно"
- Теряете деньги пока ждете

**Философская истина:**
- Любое число считается с погрешностью (как граница поверхности воды)
- Реальное значение метрики находится от -∞ до +∞
- CI — это лишь область вероятности, не гарантия

**Пример из практики:**
- Команда ждет 3-4 недели "для точности"
- За это время потеряно ~3-4M рублей (1M/неделя)
- Точность так и не достигается (данных всегда "мало")

**Решение:**
- Примимайте решения с НЕТОЧНЫМИ данными
- На стороне денег те, кто действует с погрешностью
- "Прыжок веры" — обязательная часть продуктового менеджмента
- Лучше приблизительное решение сейчас, чем идеальное никогда

### Ошибка #-2: Игнорирование стоимости ожидания
**Проблема:**
- Считаете стоимость A/B теста
- НЕ считаете стоимость НЕпринятия решения
- Каждая неделя ожидания = потери

**Расчет (из курса):**
- Простои команды: ~1M рублей в неделю
- 4 недели ожидания "точных данных" = 4M потери
- Итог: тестирование не окупилось даже теоретически

**Решение:**
- Считайте "стоимость задержки решения"
- Сравнивайте: стоимость теста vs стоимость ожидания
- Иногда быстрое решение без теста выгоднее

### Ошибка #1: Отсутствие тестов
**Проблема:** Катить всё сразу в продакшн без проверки гипотез
**Риск:** Можно сильно навредить продукту
**Решение:** Даже простые тесты помогают избежать грубых ошибок

### Ошибка #1: Слишком много плохих экспериментов
**Проблема:** Тестировать всё подряд без фокуса на важных метриках
**Решение:** Фокусируйтесь на ключевых метриках:
- **Churn rate**: отток пользователей
- **Лояльность**: время отсутствия пользователя и частота посещений

### Ошибка #2: Отсутствие логов для перерасчёта
**Проблема:**
- Не сохраняются сырые данные для перепроверки результатов
- Нельзя верифицировать выводы
- Теряется возможность дополнительного анализа

**Решение:**
- Всегда сохраняйте сырые данные (raw logs)
- Ведите полное логирование всех событий
- Обеспечьте возможность пересчета метрик

### Ошибка #3: Зависимость данных (Data Dependency)
**Проблема:**
- Один пользователь делает много мелких покупок
- Обычные статистические тесты не учитывают зависимость данных
- Ложные выводы из-за повторных событий одного пользователя

**Решение:**
- Сводите данные к показателям "на пользователя" (per user)
- Агрегируйте данные за весь период эксперимента
- Используйте методы для зависимых выборок

**Пример:**
```python
# ПЛОХО: тестировать каждую транзакцию независимо
transactions = [user1_t1, user1_t2, user1_t3, user2_t1, ...]

# ХОРОШО: агрегировать по пользователям
user_metrics = [
  user1_total_transactions,
  user2_total_transactions,
  ...
]
```

### Ошибка 4: Тестирование без проверки MDE
**Проблема:** Ожидаете эффект 0.01%, но MDE = 0.22%
**Результат:** Тест не может обнаружить эффект
**Решение:** Рассчитайте MDE ДО запуска

### Ошибка 2: Слишком маленькая выборка
**Проблема:** 1,000 пользователей на вариант
**Результат:** CI слишком широкий, результаты ненадежны
**Решение:** Минимум 10,000 на вариант

### Ошибка #3: Игнорирование сегментации (Агрегированная ловушка)
**Проблема:**
- Смотрите только на агрегированные данные
- Desktop и Mobile показывают РАЗНЫЕ результаты
- Эффект в одном сегменте маскируется другим

**Пример из практики:**
- Desktop: Конверсия выросла на 15% ✅
- Mobile: Конверсия упала на 10% ❌
- Aggregated: Без изменений ⚠️

**Решение:**
- Всегда проверяйте срезы: Desktop/Mobile, География, Источник трафика
- Анализируйте каждый сегмент отдельно
- Понимайте, что "усредненный" результат может скрывать проблемы

**Критические срезы данных:**
- 📱 Устройство (Desktop vs Mobile/Tablet)
- 🌍 География (разные города)
- 📊 Источник трафика (organic, paid, social, email)

### Ошибка #4: Слишком маленькая выборка
**Проблема:** 1,000 пользователей на вариант
**Результат:** CI слишком широкий, результаты ненадежны
**Решение:** Минимум 10,000 на вариант

### Ошибка #5: Не учтены выбросы в среднем чеке
**Проблема:**
- Один гигантский заказ искажает средний чек
- Показывает ложный эффект
- Стандартные статистические тесты не работают

**Пример:**
- Обычно: средний чек $50
- Один заказ: $10,000
- Итог: средний чек $75 (искажен!)

**Решение:**
- Используйте Байесовскую статистику
- Или отсекайте 3-5% самых крупных и мелких заказов

### Ошибка #6: Сотрудники в выборке
**Проблема:**
- Сотрудники компании тестируют изменения
- Их поведение отличается от обычных пользователей
- Искажают результаты теста

**Решение:**
- Исключайте всех сотрудников из A/B тестов
- Используйте специальные сегментаторы
- Проверяйте IP и внутренние аккаунты

### Ошибка #7: Не учтены аннуляции
**Проблема:**
- Считаете все заказы, включая отмененные
- Не учитываете исполняемость заказов
- Конверсия растет, но реальных денег нет

**Решение:**
- Учитывайте только оплаченные и доставленные заказы
- Отдельно анализируйте аннулированные
- Смотрите на "исполненную" конверсию

### Ошибка #8: Интерпретация "отсутствия разницы"
**Проблема:** "AA тест показал разницу, значит методология плохая"
**Реальность:** AA тест ДОЛЖЕН показать отсутствие разницы
**Правило:** Если AA показывает разницу → методология имеет проблемы

### Ошибка #9: "10,000 шагов" мышление
**Миф:** 10,000 шагов/10 дней — научный факт
**Реальность:** Это маркетинг от Fitbit, не наука
**Урок:** Не все "правила" основаны на доказательствах

## Принципы из ProductDo

### "70% тестов должны быть 'зелеными'"
Цель A/B тестирования в крупных компаниях:
- Предотвратить деградацию
- Ловить 100-500 небольших негативных изменений
- 70% экспериментов не должны иметь негативного эффекта

### "A/B тест не доказывает гипотезу"
- A/B тест только показывает: "отличаются ли наборы данных?"
- Не подтверждает, что ваша бизнес-гипотеза верна
- Требует дополнительной интерпретации
- Тест не знает про вашу гипотезу, он только про циферки

### "Статистическая реальность vs Физическая реальность"
**Мир сложен и шумен:**
- Все измерения имеют ошибку
- Границы размыты (аналогия с квантовой физикой)
- Доверительный интервал захватывает неопределенность
- Реальное значение от -∞ до +∞

**Математик vs Физик:**
- Математик: "0 ≠ 0.0001, докажи точность"
- Физик: "0.0001 продаж есть — это что-то"
- В бизнесе: деньги на стороне физиков (тех, кто действует)

### "Данные всегда недостаточны"
- Аналитики всегда скажут "нужно больше данных"
- Из-за A/B тестов данных сильно много не получить
- Аналитик "ссыкотно" делать ставку (страх ошибки)
- **Правда:** Вам всегда придется делать прыжок веры

### "Стоимость ожидания > Стоимость ошибки"
- 1 неделя задержки решения = 1M рублей потери (на примере курса)
- 4 недели "точности" = 4M потери
- Иногда быстрое решение без теста выгоднее完美的 A/B теста

### "Гауссиана — это приближение"
- Используем нормальное распределение только потому что "не сильно врет"
- По ЦПТ (центральной предельной теореме) распределения стремятся к нормальным
- Но НЕ ВСЕ распределения нормальные (особенно деньги!)
- Конверсии "условно" нормальны, но это не доказано

## Примеры из Курса

### Пример 1: Недостаточная выборка
**Ситуация:**
- 55,000 пользователей/неделю
- Конверсия: 0.26%
- CI: ±0.11%
- MDE: 0.22%

**Проблема:**
- Ожидаемое улучшение: 0.01%
- MDE = 0.22% (в 22 раза больше!)

**Вердикт:** ❌ Нельзя провести тест

**Решение:**
- Собрать больше данных
- Или запустить без A/B теста (если риск низкий)

### Пример 2: AA Тест
**Ситуация:**
- Стоимость: $30,000
- Результат: 5.5±0.6% (A) vs 5.5±0.6% (B)

**Вердикт:** ✅ Методология корректна

**Результат:** Можно запускать реальный AB тест

### Пример 3: Сегментация
**Ситуация:**
- Базовая выборка: 55,000
- Сегменты: Desktop (30K) + Mobile (25K)

**Проблема:**
- Desktop CI шире (меньше выборка)
- Mobile CI шире (меньше выборка)
- MDE для каждого сегмента больше

**Вердикт:**
- Можно тестировать только aggregated
- Для сегментированных результатов нужна большая выборка

## Когда НЕ использовать A/B тесты

### Маленькие выборки
- < 10,000 пользователей на вариант
- CI слишком широкий
- MDE слишком большой

### Эффект меньше MDE
- Ожидаемое улучшение < доверительного интервала
- Тест не может обнаружить эффект

### Срочные изменения
- Критические баги
- Безопасность
- Комплаенс

### Низкий риск
- Улучшения, которые вряд ли навредят
- Малозначительные изменения
- "Best practices"

## Интеграция с Antigravity
- Автоматически рассчитывать CI и MDE для всех тестов
- Блокировать запуск тестов если MDE > ожидаемого эффекта
- Требовать AA тест перед первым экспериментом
- Показывать предупреждения при маленькой выборке
- Визуализировать доверительные интервалы
- Автоматически сохранять сырые логи для всех экспериментов
- Агрегировать метрики "на пользователя" по умолчанию
- Предупреждать о зависимости данных в выборках
- Фокусироваться на ключевых метриках (Churn rate, Лояльность)
