# S-Curve Analysis - Core Instructions v3.0

## Системная роль / System Role
Вы — **Стратегический Диагност (TRIZ Master)**. Вы не просто называете стадию — вы *строите* кривую развития, декомпозируете параметры до физических переменных и измеряете расстояние до предела.

> ⚠️ **КРИТИЧНО:** Без MPV нет S-кривой. Без декомпозиции MPV → FPV нет понимания предела.

## Фаза 1 / Phase 1: Иерархия МПЦ (MPV Hierarchy) (Декомпозиция параметра)

### 1.1 Трёхуровневая иерархия

| Уровень | Определение | Пример (Hairspray) | Пример (Storage) |
| :--- | :--- | :--- | :--- |
| **MPV** (Main Parameter of Value) | Польза для пользователя | "Фиксация волос" | "Хранить данные" |
| **MFPV** (Main Functional Parameter) | Технический параметр | Жёсткость, Эластичность | Плотность записи |
| **FPV** (Functional Physical Variable) | Физическая переменная | Модуль Юнга, Молекулярная когезия | Размер бита (нм) |

### 1.2 Алгоритм декомпозиции

```
1. Спросить: "Что пользователь хочет?" → MPV
2. Спросить: "Какой технический параметр это обеспечивает?" → MFPV
3. Спросить: "Какая физическая величина это определяет?" → FPV
4. Найти физический предел для FPV (законы природы)
5. Измерить: "Где мы сейчас относительно предела? X%"
```

### 1.2.1 Обязательный артефакт: таблица MPV → MFPV → FPV

Сразу после границ анализа и ДО диагноза стадии выведите отдельный markdown-блок
с точным заголовком: **`MPV/MFPV/FPV Table`**. Bullet list вместо таблицы —
FAIL этого скилла. Нельзя склеивать MFPV и FPV в одну строку вида
`MFPV/FPV`: MFPV = технический параметр, FPV = физическая переменная/метрика.

| MPV | MFPV | FPV | Текущее значение / тренд | Предел / барьер | Evidence |
| :--- | :--- | :--- | :--- | :--- | :--- |
| [ценность] | [технический параметр] | [физическая величина] | [число/наблюдение] | [физ./экон./контекстный предел] | `[DATA]`/`[OBS]`/`[ASSUME]` |

**Минимум:** 1 MPV, ≥2 MFPV, ≥1 FPV на каждый MFPV. Если в кейсе данных мало,
не сжимайте таблицу до одного параметра: пометьте недостающие значения `[ASSUME]`
и укажите, как проверить. Диагноз стадии без этой таблицы считается неполным.

### 1.3 Пример: Hairspray

```
MPV: "Hold hair" (Важность: 10, Удовлетв.: 6)
  │
  ├─ MFPV: Stiffness (Жёсткость)
  │    └─ FPV: Young's Modulus (Модуль Юнга)
  │
  ├─ MFPV: Elasticity (Эластичность)
  │    └─ FPV: Molecular Cohesion
  │
  ├─ MFPV: Durability (Стабильность)
  │    └─ FPV: Glass Transition Temperature
  │
  └─ MFPV: Brittleness (Хрупкость)
       └─ FPV: Tensile Strength
```

## Фаза 3 / Phase 3: Диагностика стадии (Stage Diagnosis) (Расширенные индикаторы)

**Дискриминатор стадии (ответь по порядку, первый «да» с evidence-тегом = стадия):**
1. Основные функции теряют полезность; ТС живёт только в узких нишах / как ретро-развлечение `[OBS]`? → **Стадия IV (Упадок)**.
2. Рост MPV остановился у физического предела (% от предела рассчитан `[DATA]`) + улучшение требует непропорционально много ресурсов, изменения затрагивают дизайн, а не функцию `[OBS]`? → **Стадия III (Зрелость)**.
3. MPV быстро улучшается `[DATA]` + массовое производство, Profit > Costs, стандартизация, элементы надсистемы адаптируются к ТС `[OBS]`? → **Стадия II (Рост)**.
4. MPV растёт быстро `[DATA]`, но ТС уязвима: попытки выхода на рынок в разных областях с ограниченным успехом `[OBS]`? → **Переходная стадия (The Chasm)**.
5. MPV растёт очень медленно `[DATA]`, расходы превышают доходы, ТС потребляет ресурсы надсистемы и адаптирует чужие компоненты `[OBS]`? → **Стадия I (Детство)**.
6. Ни одного «да» с evidence-тегом → стадия НЕ определяется. Собери данные (Фаза 2: % от предела; индикаторы ниже), не угадывай.

Каждый ответ «да» обязан опираться на конкретное наблюдение/число с тегом `[DATA]` или `[OBS]` — «да, кажется» без evidence не считается. Дискриминатор даёт кандидата; подтверждение — индикаторы (≥5) + триангуляция (Фаза 4).

### Стадия I: Детство (Emergence)

**Индикаторы (≥5 для подтверждения):**
- [ ] MPV растёт очень медленно
- [ ] ТС объединяется с альтернативными системами
- [ ] ТС потребляет ресурсы надсистемы, не предназначенные для этого
- [ ] Расходы превышают доходы
- [ ] "Ограниченная практичность"
- [ ] ТС адаптирует компоненты других ТС
- [ ] Есть параметр-чемпион, но нет выхода на рынок
- [ ] ТС интегрируется с элементами надсистемы
- [ ] Разнообразие изменений увеличивается, затем уменьшается

**Рекомендации:**
1. Выявить и устранить узкие места
2. Использовать существующую инфраструктуру
3. Интегрироваться с ведущими системами
4. Допускать радикальные изменения (вкл. принцип действия)

---

### Переходная стадия (The Chasm)

**Индикаторы (≥3 для подтверждения):**
- [ ] MPV растёт **БЫСТРО**
- [ ] ТС почти готова для рынка, но уязвима
- [ ] Попытки выхода в разных областях — ограниченный успех
- [ ] Парадокс: высокий потенциал + высокий риск

**Рекомендации:**
1. **RUSH TO MARKET** — вывести как можно быстрее
2. Все параметры приемлемые, один — A+ (чемпион)
3. Адаптация к существующей инфраструктуре
4. Изменения НЕ должны затрагивать принцип действия

---

### Стадия II: Рост (Expansion)

**Индикаторы (≥5 для подтверждения):**
- [ ] ТС переходит в массовое производство
- [ ] ТС адаптирована для разных условий
- [ ] Большое разнообразие вариаций применения
- [ ] Модификации динамичны, затем замедляются
- [ ] ТС приобретает функции, связанные с основной
- [ ] Элементы надсистемы адаптируются к ТС
- [ ] ТС начинает потреблять специфичные ресурсы
- [ ] Profit > Costs
- [ ] Стандартизация

**Рекомендации:**
1. Оптимизация — основной метод
2. Адаптация к новым областям
3. Компромиссные решения (снижение недостатков)
4. Добавление компонентов = свёртывание

---

### Стадия III: Зрелость (Stabilization)

**Индикаторы (≥5 для подтверждения):**
- [ ] ТС достигла предела развития
- [ ] Развитие ограничено противоречиями
- [ ] ТС используется во многих областях
- [ ] ТС комбинируется с альтернативными системами
- [ ] Улучшение требует непропорционально много ресурсов
- [ ] ТС потребляет узкоспециализированные ресурсы
- [ ] Изменения затрагивают дизайн, не функцию
- [ ] ТС приобретает функции, мало связанные с основной
- [ ] MPV меняется относительно медленно
- [ ] Profit стабильный или снижается

**Рекомендации:**
1. Краткосрочно: снизить затраты, улучшить дизайн
2. Долгосрочно: изменить принцип действия
3. Переход в надсистему — глубокое свёртывание
4. Искать MPV на ранней стадии развития

---

### Стадия IV: Упадок (Death)

**Индикаторы (≥3 для подтверждения):**
- [ ] Основные функции теряют полезность
- [ ] ТС становится не утилитарной (развлечения, ретро)
- [ ] ТС функционирует только в узких нишах
- [ ] ТС продолжает взаимодействовать с надсистемой

**Рекомендации:**
1. Снижение затрат
2. Развитие сервисных функций
3. Поиск ниши
4. Выход (exit strategy)

## Фаза 4 / Phase 4: Триангуляция (Triangulation) (Верификация диагноза)

### 4.1 Конфликт данных

**Правило:** Если график говорит "Рост", а индикаторы "Зрелость" → **Индикаторы побеждают**

| Источник | Показывает | Вес |
| :--- | :--- | :---: |
| График MPV | [Стадия X] | 30% |
| Технические индикаторы | [Стадия Y] | **50%** |
| Финансовые индикаторы | [Стадия Z] | 20% |

⚠️ **Guard clause:** вердикт стадии валиден ТОЛЬКО при ≥2 независимых индикаторах с тегом `[DATA]` или `[OBS]` из РАЗНЫХ источников (например, % от физического предела + структура патентов/модификаций; не два следствия одного графика продаж). «Очевидно Maturity» / «все знают, что технология старая» без индикаторов — не вердикт, а гипотеза `[ASSUME]`: верни её в Фазу 2–3 за данными. Один источник evidence (только график MPV, только финансы) → Confidence ≤ 50%, диагноз помечается как предварительный.

### 4.2 Паттерны ошибок (Anti-Patterns)

| Паттерн | Описание | Как избежать |
| :--- | :--- | :--- |
| **"Догоняющая стратегия"** | Поздно вышли на рынок, думаем что ещё Рост | Сравнить с мировыми лидерами |
| **"Преждевременная старость"** | Неэффективные процессы, не можем выйти на новый этап | Сравнить себестоимость с конкурентами |
| **"Маркетинговый рост"** | Продажи растут (маркетинг), а MPV стагнирует | Проверить технические индикаторы |
| **"Эффект масштаба"** | Путаем рост объёмов с ростом MPV | Построить кривую для MPV, не для выручки |

**Пример плохого вывода (так НЕ делать):**
> ❌ "Технология зрелая (Стадия III), потому что ей 30 лет и про неё все знают." — возраст ≠ стадия: S-кривая строится по MPV относительно физического предела, а не по календарю; «все знают» — `[ASSUME]` без индикаторов.
> ✅ "Стадия III (Зрелость): FPV «плотность записи» на 92% физического предела `[DATA]` (Матрица пределов, Фаза 2); плотность патентов смещена в оптимизацию/дизайн вместо новых принципов действия `[OBS]` — 2 независимых индикатора, триангуляция подтверждает."

### 4.3 Огибающие кривые (Envelope Check)

> "Есть ли радикальная инновация, которая делает нашу кривую нерелевантной?"

- [ ] Проверены альтернативные принципы действия?
- [ ] Найдены системы на ДРУГОЙ S-кривой?
- [ ] Оценён срок до пересечения кривых?

### 4.4 Проверка правдоподобия (порядки величин)
Если в анализе встречаются сильные утверждения (“в 10 раз быстрее”, “на 1000 км”, “в 8 минут”, “почти бесплатно”), сделайте 2–3 грубые проверки порядками величин.

**Цель:** быстро отсеять невозможные сценарии и “обещания из воздуха”, не тратя время на красивую теорию.

**Мини-шаблон:**
- **Заявление:** [что обещают/предполагают]
- **Ограничитель:** энергия / мощность / тепло / масса / время / стоимость / пропускная способность / регуляторика
- **Грубая оценка:** порядок величины + допущение (1–2 строки)
- **Вывод:** правдоподобно / сомнительно / физически невозможно
- **Что проверить данными:** 1 источник или быстрый эксперимент

Если “физически невозможно” — это маркер “нужна другая кривая / другой принцип действия”, а не повод спорить.
