# TRIZ Feature-Discovery Audit Standard

**Дата создания:** 2026-05-29
**Класс:** method-standard (тяжелее микро-стандартов; по типу `universal-matrix-standard.md`).
**Контекст:** первый Ultimate-аудит `nikita-video-engine` дал ценный метод, но (а) повторяемые
дефекты (пустой RTM, bare-числа, расхождение счёта гэпов, неверифицированный код), (б) был
реактивным аудитом, а реальная цель владельца — **находить отсутствующие фичи, которые
закрывают непокрытые джобы и улучшают продукт**. Стандарт фиксирует метод так, чтобы каждый
прогон выдавал приоритизированный **бэклог фич**, а не только список поломок.

> **Что это.** Воспроизводимый пайплайн обнаружения фич: перечислить все джобы → найти
> **непокрытые** → сгенерировать фичи-кандидаты (ТРИЗ как генератор идей) → привязать к
> реальному коду → приоритизировать. **Выход = ранжированный бэклог фич**, каждая фича
> привязана к конкретной непокрытой джобе и к точке в коде.

---

## §0. When to use / NOT

| Используй этот стандарт | Используй `_agent_shared/standards/universal-matrix-standard.md` |
|---|---|
| Поиск **отсутствующих фич** в построенной системе под непокрытые джобы. | Выбор **что строить с нуля**: матрица доноров-кандидатов. |
| Выход = бэклог фич, привязанных к джобам и коду. | Выход = component ontology + build-решения. |

ТРИЗ — **набор генераторов идей**, не самоцель (определения линз — скиллы `_agent_shared/skills/triz/`).
Каждая линза обязана родить **фичу-кандидата или job-инсайт**, иначе не применяется.

## §0.5. Input checklist (ДО запуска)

- [ ] Доступ к репо (Read/grep/ls на `src/`, `docs/`, `tests/`).
- [ ] **Прочитаны существующие аудиты** (`docs/audits/*`) и живой `docs/BACKLOG.md` — чтобы не ре-деривить известные гэпы. Это **инкрементальный** метод, не «с нуля».
- [ ] Известны роли/пользователи продукта (для S2/S7).
- [ ] Названный список конкурентов или матрица доноров (для S9) — иначе teardown выдуман.
- [ ] Дата последнего аудита vs дата HEAD: код двигался → приоритет RTM drift-check (S8) над повторным S2/S9.
- [ ] Source-of-truth = код и логи, не память агента (R8; anti-bias `[O/I/S/A]`).

**Если ≥1 пункт пуст — добери данные до S1. Жёстко: не начинай S2 (джобы), не прочитав существующие `docs/audits/` — иначе прогон дублирует прошлый аудит вместо дельты.**

## §1. Пайплайн (спина = джобы → фичи)

```text
S1 MPV          боль → измеримый параметр (current/target/unit + provenance)
S2 Job Coverage перечислить ВСЕ джобы → covered / partial / uncovered / latent
S3 RCA+         почему джоба не покрыта (причинные цепочки + оператор отрицания)
S4 Feat Sources генераторы фич: ресурсы + тренды эволюции ТС + ИКР + ФА (≥20 модулей)
S5 Contradict   trade-off фич (40 приёмов / разделение)
S6 Feat Cands   на каждую непокрытую джобу ≥2 фичи-кандидата
S7 Role-Gap     N-ролевая матрица: severity + Effort + Actor + deps
S8 RTM          фича/джоба → реальные файлы кода + статус (что есть/частично/нет)
S9 Competitors  teardown фич названных конкурентов под те же джобы
S10 ISRICE      ранжированный бэклог фич + DoD на каждую
```

Каждая стадия имеет hard-gate. Стадия без обязательного артефакта = прогон неисполнен.

## §2. S1 — MPV (боль → измеримый параметр)

Таблица: `Жалоба | MPV-параметр | Ед.изм | Current | Target | Источник[O/I/S/A]`.

**Hard:**
- Каждое `Current`/`Target`: unit + тег провенанса `[O]` замер / `[I]` вывод / `[S]` со слов / `[A]` допущение (cross-ref `.claude/rules/anti-bias.md`).
- На каждый MPV — **как мерить сегодня** (проба/команда). Таргет без метода замера = нефальсифицируем.
- `[A]` на ключевом параметре → «требует замера», не выдавать как факт. Bare-число запрещено.

---

## §3. S2 — Job Coverage Map (СПИНА метода)

Перечислить **все джобы** по ролям (формат JTBD: «когда `<ситуация>`, хочу `<прогресс>`, чтобы `<выгода>`»), затем статус покрытия.

**Таблица:** `J-ID — джоба | Роль | Статус | Чем покрыта (файл/—) | Доказательство покрытия`.
Статус: `covered` / `partial` / `uncovered` / **`latent`** (джоба, которую пользователь ещё не озвучил, но она реальна — JTBD-ядро).

**Hard:**
- Каждая `uncovered`/`partial` строка → кандидат на фичу в S6. Это источник бэклога.
- **`latent` джобы обязательны** (≥3): метод не сводится к пересказу озвученных жалоб. Латентные ищутся через тренды (S4) и competitor teardown (S9).
- Джобы из **реальных** источников (интервью/аналитика/own-usage), не выдуманные персоны. Источник помечен `[O/S/A]`.
- `J-ID — имя`, голый ID запрещён (R5).

**Role fan-out (для широты покрытия).** Перечисление джоб ведётся **по ролям**, и для систем с N≥4 ролей **здесь спавнятся субагенты — один на роль-кластер** (Storyteller / Operator / Auditor / Sound / Legal / Localization / SRE …). Каждый агент:
- **блайнд к другим** — перечисляет джобы **только со своей ролевой точки зрения**, чтобы не было ложного консенсуса и groupthink;
- ищет **свои latent-джобы** (Sound видит ритмику/foley, Legal — лицензии/safe-area, Localization — RTL/длину строк — то, что Storyteller-only пропускает);
- возвращает **частичный Job Coverage Map** своей роли с `[O/S/A]`.
Затем — **синтез (соло, §17 шаг 3)**: dedupe джоб по смыслу, объединить в один реестр, сверить счёт. Транспорт и scope-разделение — по `.claude/rules/parallel-agents.md` и §17 (один scope = один агент, scope не пересекается). Малая система (≤10 модулей, ≤3 роли) → соло-перечисление, fan-out избыточен.

## §4. S3 — RCA+ (почему джоба не покрыта)

Для критичных непокрытых джоб: дерево причин **И/ИЛИ** → ключевой недостаток → **оператор отрицания** («как дать прогресс, ПРИ УСЛОВИИ что недостаток есть?») → направление фичи.

**Hard:**
- Каждый узел обоснован файлом/логом/коммитом (cross-ref `root-cause-analysis-standard.md`; R8).
- НЭ нумеруются с 01 без пропусков. Линейная цепочка → `/why`; ≥3 причин → `/triage`.

---

## §5. S4 — Источники фич (генераторы)

ТРИЗ-генераторы, каждый рождает фичи-кандидаты:

1. **Ресурсный анализ.** Инвентарь **уже доступных свободных ресурсов** (idle CPU, побочные продукты рендера, метаданные ассетов, существующий кэш/индекс, данные соседних модулей, **built-but-not-wired модули** — код есть, нет вызова). Фича из существующего ресурса дешевле — приоритет.
2. **Тренды эволюции ТС.** Применить законы развития (динамизация, дробление, переход в надсистему, согласование/рассогласование ритмики, повышение управляемости) → **латентные фичи**, которые пользователь не просил, но которые двигают продукт по S-curve.
3. **ИКР.** Для топ-барьеров 3 формулы (Система САМА; Элемент `X` САМ; полная: `X` в опер-зоне в опер-время без затрат `ресурс`). ИКР = эталон фичи **до** генерации решения.
4. **Функциональный анализ** *(обязателен для систем ≥20 модулей; иначе опционален).* Прогнать `@functional_analysis` (скилл `_agent_shared/skills/triz/functional_analysis`) на 2–3 критичных подсистемах: тег функций `[P/S/C/T/M/L]`, найти **insufficient / harmful / corrective** функции → каждая такая функция = направление фичи (усилить недостаточное, убрать вредное, свернуть костыль). FA ловит фичи, которые ресурсы/тренды/ИКР пропускают, потому что смотрит на **взаимодействия компонентов**, а не на джобы.

**Hard:** каждый генератор даёт ≥1 именованную фичу-кандидата или явно «пусто, причина». ФА обязателен при ≥20 модулей.

## §6. S5 — Противоречия (trade-off фич)

Для конфликтных требований фич (крупный шрифт vs safe-area; строгий preflight vs offline-dev; качество vs стоимость): формулировка ТП → разрешение (разделение во времени/пространстве/отношениях или приём из 40).

**Hard:** нумерация с 1 без пропусков; указан конкретный приём + точка инъекции `файл → функция → что` (≤50 симв, R12). Определения линз — скиллы `_agent_shared/skills/triz/{contradictions,functional_analysis,system_operator,trimming}`, не дублировать (вторично: `_agent_shared/standards/universal-matrix-standard.md` §6.5).

## §7. S6 — Feature Candidates (главный выход)

На каждую `uncovered`/`partial`/`latent` джобу — **≥2 фичи-кандидата** (не одно решение).

**Таблица:** `F-ID — фича | Закрывает J-ID | Источник (resource/trend/ИКР/competitor) | Effort(0-100) | Actor | Зависит от F-ID`.

**Hard:**
- Минимум 2 варианта на джобу → выбор, а не первый пришедший (anti-bias).
- Каждая фича явно мапится на `J-ID`. Фича без джобы = scope creep, выкинуть.
- `Effort(0-100)` (любой клик owner ≥50) + `Actor(agent/owner/both)` обязательны (R6).
- Граф зависимостей `Зависит от` → обоснование порядка в S10.

---

## §8. S7 — Role-Gap матрица

N ролей (прямые + скрытые регуляторы + специализированные: SRE/Legal/Sound/Localization).
Таблица: `G-ID — имя | R1..RN (0-3) | Hits | Sum Severity | Effort | Actor`.

**Hard (gate расхождения счёта):**
- Заявленное число гэпов = число строк. Recount перед публикацией. Пропуски ID (нет G06/G10/...) → устранить или **явно** объяснить отбраковку.
- `G-ID — имя`, голый ID запрещён. 🔥-порог объявлен явно (напр. `Hits≥5 И Sum≥12`) и применён единообразно.
- Колонки `Effort`+`Actor` обязательны (R6). Severity взвешена частотой/важностью роли (owner ≠ гипотетическая роль).
- Скиллы: `/jobs-to-be-done`, `/user-story-mapping`.

---

## §9. S8 — RTM (фича/джоба → код) — НИКОГДА не плейсхолдер

Таблица: `J-ID/F-ID | Требование (источник) | Файл(ы) | Статус | Метод верификации`.
Статус: `Fully Wired` / `Seam-Mock` / `Blocked` / `Missing`.

**Hard (gate пустого RTM — главный дефект исходника):**
- RTM **физически в документе**. Ссылка «см. таблицу выше/ниже» на самоё себя = прогон неисполнен.
- Каждая строка → существующий путь (проверен `ls`/Read), не имя по памяти.
- Статус `Missing`/`Seam-Mock` уровня Critical → **верифицирован Read файла**. Субагент-аудиты ~30% false-positive на Critical/High, AG врёт про «green» → спот-проверь ≥2-3 цитируемых файла (cross-ref память `feedback_multi_agent_audit`).
- Метод верификации per-row (`Read X-Y`/`pytest`/`grep`), не «доверено субагенту».

---

## §10. S9 — Competitor Feature Teardown

Под каждую критичную джобу — **какие фичи у названных конкурентов** её закрывают.

**Таблица:** `J-ID | Конкурент (назван) | Их фича | Источник[O/S] | У нас есть? | Идея для нас`.

**Hard:**
- Конкуренты **названы** (CapCut/Opus/Submagic/…) + источник claim `[O]` (видел) / `[S]` (со слов). Bare «Средний AI-софт» без имени и источника запрещён (survivorship/выдумка).
- Teardown питает `latent` джобы (S2) и фичи-кандидаты (S6).

---

## §11. S10 — ISRICE Backlog + DoD

Скоринг фич и фазовый план.

**Hard:**
- Показаны **входы** I/S/R/I/C/E, не только score (`11.20` без разбивки = не аудируемо).
- Каждая фича → `F-ID`, `J-ID`, точка инъекции в код, **Definition-of-Done** = критерий «джоба теперь делается» (приёмочный тест).
- Порядок фаз обоснован графом зависимостей (S6/S7), не только числом.
- **Cost of inaction** на топ-фичи: что теряем если не строим.
- Скилл: `/prioritize`.

---

## §12. Guardrails выбранных фич (перед стройкой)

Для фич, попавших в Фазу 1:
- **Blast radius** (R11): что сломается? Регрессионная поверхность переписей (`donor_ledger.py`, `caption_translate.py` и т.п.).
- **Rollback**: необратимые фичи (auto-delete >48ч, блокирующий pre-commit) → план отката + что при ложном срабатывании.
- **Threat model**: фичи, трогающие ключи/внешние загрузки/исполнение manifest → path traversal, утечка ключа, malicious/injection. Security-фича = фича.

## §13. Required artifacts

Прогон не засчитан без всех:
1. MPV-таблица с provenance + методом замера (§2).
2. **Job Coverage Map** с ≥3 latent-джобами (§3).
3. ≥1 RCA+ дерево с fact-basis (§4).
4. Источники фич: ресурсы + тренды + ИКР (+ ФА при ≥20 модулей), каждый дал кандидата (§5).
5. ≥1 разрешённое противоречие с точкой инъекции (§6).
6. **Feature Candidates** ≥2 на джобу, мапятся на J-ID, с Effort/Actor (§7).
7. Role-Gap матрица со сверенным счётом + Effort/Actor (§8).
8. **Непустой** RTM с верифицированными Critical (§9).
9. Competitor teardown с названными конкурентами (§10).
10. ISRICE бэклог с входами + DoD + cost-of-inaction (§11).
11. Финальная калибровка уверенности (`/pizdej` + anti-bias до→после).

## §14. Validation checklist (binary gates)

- [ ] Каждый MPV: unit + current + target + `[O/I/S/A]` + метод замера?
- [ ] Job Coverage Map есть, ≥3 latent-джобы, джобы из реальных источников?
- [ ] Каждая uncovered/partial джоба → ≥2 фичи-кандидата?
- [ ] Каждая фича мапится на J-ID (нет фич без джобы)?
- [ ] Все генераторы (ресурсы/тренды/ИКР + ФА при ≥20 модулей) дали выход?
- [ ] Счёт гэпов = число строк? Пропуски ID объяснены?
- [ ] Каждый J-ID/F-ID/G-ID = `код — имя`?
- [ ] Матрицы содержат Effort(0-100) + Actor?
- [ ] RTM физически присутствует (нет self-reference)?
- [ ] Все Critical code-claims прошли Read-верификацию?
- [ ] Competitor teardown — конкуренты названы + источник?
- [ ] ISRICE показывает входы + DoD + cost-of-inaction?

**Хоть один `[ ]` пуст → прогон не готов.**

## §15. FORBIDDEN / Hard fail

**FORBIDDEN:**
- Фича без привязки к джобе (scope creep).
- Одно решение на джобу вместо ≥2 кандидатов.
- Раздел-плейсхолдер, ссылающийся сам на себя.
- Bare-число без unit + provenance; bare «Средний AI-софт» без названного конкурента.
- Голый `J01`/`F01`/`G01`/`НЭ-03` без имени и без объяснения пропусков.
- Code-claim Critical без Read-верификации.
- Копирование определений ТРИЗ-линз вместо cross-ref.

**Hard fail (прогон непостроен):**
- Нет Job Coverage Map или нет latent-джоб → метод выродился в пересказ жалоб.
- Фичи-кандидаты не мапятся на джобы.
- Отсутствует/пуст RTM.
- Счёт гэпов не сходится и пропуски не объяснены.
- Нет финальной калибровки уверенности.

## §17. Execution (как запускать)

Стандарт = **контракт** (ЧТО на выходе). Эта секция = **харнесс** (КАК исполнять).

**Канонический режим — multi-agent fan-out → синтез → верификация:**

1. **Discovery (параллельно).** Субагенты с **непересекающимися scope** (per `.claude/rules/parallel-agents.md`): дели по **кластерам ролей** (напр. agent-1 = R1-R4 продакшн, agent-2 = R9-R12 спец-роли) или **по стадиям** (S1 MPV / S2 джобы / S3 RCA+). Один scope = один агент, чтобы не дублировали находки.
2. **Generation (параллельно).** На каждый кластер непокрытых джоб — агент генерит фичи-кандидаты (S4-S7). Каждый блайнд к другим → разные углы.
3. **Synthesis (соло, главный контекст).** Свести в единый реестр: dedupe фич/джоб, сверить счёт гэпов (§8 gate), построить граф зависимостей, ISRICE-бэклог (S10).
4. **Verification (соло, ОБЯЗАТЕЛЬНО).** Перед выдачей: **Read-проверка** всех Critical/High code-claims (§9). Агенты завышают severity ~30%, AG врёт про «green» (память `feedback_multi_agent_audit`). Raw agent output ≠ факт — синтезируй и проверь сам.

**Hard:**
- Scope субагентов **не пересекается** — иначе дубли и ложный консенсус.
- После fan-out — **СТОП**, синтез + верификация Critical перед показом владельцу. Не передавать сырой вывод агентов как готовый бэклог.
- Малая система (≤10 модулей) → соло-прогон допустим, fan-out избыточен.
- Транспорт субагентов — по `.claude/rules/parallel-agents.md`; ролевые сценарии = **линза покрытия**, не обязательно 1 роль = 1 агент.

## §18. Runbook (конкретный запуск)

§17 = харнесс (логика). Эта секция = **рецепт** (команды). Пример на agy CLI; любой агент-CLI с доступом к файлам подойдёт.

### §18.0. Реши режим (по §0.5)
```bash
ls <repo>/docs/audits/        # есть прошлые аудиты?
```
Есть → **инкрементальный** (дельта: RTM drift-check + новые latent + ФА). Нет → полный с нуля.

### §18.1. Запуск (фон, read-only)
```bash
cd <repo>
agy --add-dir <repo> \
    --add-dir _agent_shared/standards \
    --add-dir _agent_shared/skills/triz \
    --add-dir _agent_shared/skills/jtbd \
    --dangerously-skip-permissions \
    --print-timeout 45m \
    -p "$(cat /tmp/run_prompt.md)" > /tmp/run.log 2>&1 &
```
Фон + 45m: прогон read-heavy (S8 читает каждый цитируемый файл). add-dir: репо + стандарт + ТРИЗ/JTBD скилы.

### §18.2. Драйв-промпт (`/tmp/run_prompt.md`)
```text
READ-ONLY. Не меняй код. Один write — отчёт.
Исполни этот стандарт в ИНКРЕМЕНТАЛЬНОМ режиме на <repo>.
§0.5 ПЕРЕД S2: прочитай docs/audits/* + docs/BACKLOG.md, НЕ ре-деривь известное.
Дельта: (1) RTM drift-check гэпов vs HEAD; (2) ≥3 latent jobs; (3) ФА на 2-3
критичных подсистемах; (4) ISRICE — НОВЫЕ фичи + safety-холы в одной таблице.
Гейты §14. Сохрани: docs/audits/YYYY-MM-DD-triz-delta.md
```

### §18.3. После прогона — ВЕРИФИКАЦИЯ (обязательно, = §17 шаг 4)
Не отдавай сырой вывод. Спот-проверь Read'ом **каждый Critical / `closed`-вердикт**:
```bash
sed -n '<L1>,<L2>p' <cited_file>     # claim верен?
grep -rn "def <cited_test>" tests/   # цитируемый тест существует?
```
Агенты завышают severity ~30%, врут про «green». Фабрикация ловится Read'ом.

### §18.4. Solo vs fan-out
- Один agy-прогон (solo) тянет систему ~150 модулей — проверено.
- Fan-out (§17) — когда нужно широкое ролевое покрытие за раз; дороже.
- **JTBD↔ТРИЗ мост НЕ подключай** — стандарт самодостаточен (S3/S4/S5). Мост — для JTBD↔ТРИЗ вне стандарта.

## §19. Self-orchestration — триггер «запусти стандарт»

Когда пользователь говорит **«запусти стандарт»** / **«run this standard»** (агенту с subagent-tool — Cursor Composer, Antigravity Cascade, Claude Code; НЕ agy CLI — он субагентов не плодит), агент исполняет §17-харнесс САМ, без внешнего bash-цикла, и **создаёт НОВЫЙ авто-именованный отчёт**. Параллельные оркестраторы не конфликтуют — у каждого свой run-id.

**Агент выполняет ровно это:**

```text
# ШАГ 0 — авто-имя (анти-коллизия). В shell:
RUNID=$(date +%Y%m%d-%H%M%S)-$$
OUT=<repo>/docs/audits/${RUNID}-triz-delta.md   # уникален даже при N параллельных оркестраторах (PID в имени)

# ШАГ 1 — §0.5: прочитай docs/audits/* + docs/BACKLOG.md (НЕ ре-деривь известное).

# ШАГ 2 — спавни 5 субагентов ПАРАЛЛЕЛЬНО, scope НЕ пересекается, каждый READ-ONLY.
#   ВАЖНО: субагенты возвращают находки ТЕКСТОМ в твой контекст — файлы НЕ пишут.
#   sub1 RTM drift  : сверь still-open/closed прошлых аудитов с кодом на HEAD.
#   sub2 latent+конк: ≥5 новых джоб (тренды + роли Sound/Legal/Localization) + фичи названных конкурентов.
#   sub3 ФА         : functional_analysis на 2-3 критичных подсистемах → insufficient/harmful/corrective.
#   sub4 dormant    : built-but-not-wired модули + свободные ресурсы + точка wiring + Effort.
#   sub5 safety     : дыры устойчивости/секретов/CSRF/XSS/schema.

# ШАГ 3 — СИНТЕЗ (сам): dedupe по смыслу (отметь «N агентов подтвердили»), единый Job Coverage +
#   Feature Candidates (≥2/джоба, мапь J-ID) + ОДНА ISRICE-таблица (safety+фичи, входы
#   Impact·Confidence·Reach/Effort; Conf: непрототип 4-5 / dormant 7 / баг·safety 9) + DoD+cost топ-3.

# ШАГ 4 — ВЕРИФИКАЦИЯ (сам, ОБЯЗАТЕЛЬНО, §17 шаг 4): Read'ом проверь топ-6 Critical/closed claims
#   субагентов (завышают ~30%). Опровергнутые — вычеркни из бэклога.

# ШАГ 5 — запиши ЕДИНСТВЕННЫЙ отчёт в $OUT. Соблюдай §13 артефакты + §14 гейты.
```

**Hard:**
- Run-id с `$$` (PID) → N параллельных оркестраторов (даже кросс-платформенно Cursor×2 + Antigravity×2) пишут в РАЗНЫЕ файлы. Никаких ручных путей.
- Субагенты read-only + НЕ пишут файлы. В рабочее дерево репо — ноль записи (кроме финального отчёта). → worktree не нужен, конкурентные reads безопасны.
- Шаг 4 не пропускать: без Read-верификации сырой вывод субагентов ≠ бэклог.
- N оркестраторов разом × 5 субагентов → следи за rate-limit общих API; стартуй платформы с лагом.
