# Rules Validation Standard

**Класс:** micro

## Цель
Гарантировать, что правила агента выполняют свои функции, даже если их текст изменился.

## Функциональные требования

### 1. Калибровка уверенности
**Файлы:** `core-pizdej.mdc`, `core-auto.mdc`, `core-anti-bias.mdc`

**Функция:** Агент должен указывать свою уверенность после каждого вывода.

**Маркеры:** `Уверенность: [до]% → [после]%`, `Confidence`

---

### 2. Lawful Design
**Файлы:** `core-pizdej.mdc`

**Функция:** Агент должен проверять соответствие решения законам и правам пользователей.

**Маркеры:** `Lawful Design`, `Согласие`, `Анонимизация`, `Compliance`, `закон`, `регулятор`

---

### 3. Запрет постфиксов
**Файлы:** `core-auto.mdc`, `core-clean.mdc`

**Функция:** Агент не должен создавать файлы с постфиксами `_fixed`, `_final`, `_FINAL`.

**Маркеры:** Явное упоминание запрета этих постфиксов.

---

### 4. Challenge Protocol
**Файлы:** `core-check.mdc`, `core-anti-bias.mdc`

**Функция:** Агент должен фальсифицировать свои выводы и гипотезы.

**Маркеры:** `Фальсифицируй`, `Протокол челлендж`, `Challenge`

---

### 5. Последовательные шаги
**Файлы:** `core-pizdej.mdc`

**Функция:** Агент должен выполнять шаги строго последовательно (0→1→2→3).

**Маркеры:** `после пункта 0`, `после пункта 1`, `после пункта 2`

---

### 6. Валидные пути
**Файлы:** Все

**Функция:** Все ссылки на `.mdc` файлы должны вести к существующим файлам.

**Проверка:** Скрипт `shared/scripts/rules_moderator.py` (лежит в корне монорепо, **не** в `_agent_shared/scripts/`) проверяет существование каждого пути.

---

## Процедура валидации

```bash
python3 shared/scripts/rules_moderator.py _agent_shared/versions/stable/
```

**Критерий успеха:** Все файлы должны иметь статус `PASS`.

> **NB (открытый вопрос владельцу):** скрипт `rules_moderator.py` живёт в `shared/scripts/`
> (корень монорепо), а не в `_agent_shared/scripts/` рядом с `compile_rules.py`. Кандидат на
> перенос в `_agent_shared/scripts/` для консистентности — решение за владельцем, в рамках
> этой работы скрипт не двигаем.

## 7. Backup options (перед изменением правил)

Три равнозначных варианта бэкапа:
1. `git add _agent_shared/rules/ && git commit -m "Бэкап перед изменением [правило]"`
2. `git tag rules-backup-$(date +%Y-%m-%d-%H%M%S)`
3. `cp _agent_shared/rules/<file>.mdc _agent_shared/versions/$(date +%Y-%m-%d-%H%M%S)/`

## 8. Fixed-state per-section template

При фиксации текущего состояния правила указывай размер по ключевым секциям:
```
ПРАВИЛО: [файл]
ДАТА: [YYYY-MM-DD HH:MM]
РАЗМЕР: [строк всего]
КЛЮЧЕВЫЕ СЕКЦИИ:
  - [секция 1]: [N строк]
  - [секция 2]: [N строк]
ОБЯЗАТЕЛЬНЫХ ИНСТРУКЦИЙ: [N]
ССЫЛОК НА ДРУГИЕ ПРАВИЛА: [N]
```

## 9. Testing a modified rule (4-step mini-protocol)

После изменения правила выполни:
1. **Read as agent:** прочитай результирующий текст глазами агента, понятен ли он без контекста.
2. **Try to execute:** попытайся выполнить правило на реальной задаче (sandbox/scratch).
3. **Check trigger fire:** убедись, что фразы-триггеры из frontmatter активируют правило.
4. **Check no conflicts:** прогонкой по другим правилам проверь, что нет противоречий и циклических ссылок.

**Почему:** [причина / источник запроса]

## Generic-методы верификации → отдельный стандарт

Бывшие §11-13 (3-method cross-check, what-to-test-by-change-type, when-tests-fail) — это
**generic-методы верификации, не про валидацию правил**. Вынесены в
`verification-methods-standard.md`. Процесс верификации (expected-state-first, gap-таблица) — в
скилле `/check`. Этот стандарт (§1-10) остаётся про **валидацию правил агента**.
