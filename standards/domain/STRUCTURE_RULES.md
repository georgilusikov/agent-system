# 📐 Правила структурирования стандартов

## 🧬 Три класса стандартов

Не каждый стандарт — микро-чек-лист. В каноне три класса, у каждого свой лимит и форма:

| Класс | Лимит | Что это | Эталон |
| :--- | :--- | :--- | :--- |
| **micro** | ≤ 100 строк | Рождён из конкретной ошибки. Структура по `TEMPLATE.md` (правило → что было не так → root cause → как предотвратить). | `safe-deletion-standard.md` |
| **method** | ≤ 400 строк | Воспроизводимый пайплайн со стадиями, hard-гейтами и required artifacts. Не чек-лист, а метод. | `triz-gap-closure-audit-standard.md` |
| **contract** | ~150 строк | Контракт инструмента: инварианты + CLI surface + verification matrix. | `agent_loops/ralph_loop.md` |

**Правило выбора класса:**
- Фиксируешь одну ошибку одним правилом → **micro** (используй `TEMPLATE.md`).
- Описываешь повторяемый многостадийный процесс с гейтами → **method**.
- Описываешь контракт переиспользуемого инструмента (`tools/…`) → **contract**.

Указывай класс в шапке стандарта строкой `**Класс:** micro | method | contract`.

---

## 🎯 Принципы

### 1. Компактность (по классу)
- Лимит зависит от класса: **micro ≤ 100**, **method ≤ 400**, **contract ~150** строк.
- Превышение лимита класса → либо разбей на несколько стандартов, либо проверь, что класс выбран верно (micro раздулся до method? — переклассифицируй, не режь смысл).
- Удаляй устаревшие части при обновлении.

### 2. Фундаментальность
- Включай только **правила, которые предотвращают повторение ошибки**
- Не включай детали конкретных случаев
- Не дублируй информацию из других стандартов

### 3. Структура
Используй шаблон `TEMPLATE.md`:
- **Фундаментальное правило** (1-2 предложения)
- **Что было не так** (3-5 пунктов)
- **Почему это произошло** (2-3 пункта)
- **Как предотвратить** (3-5 пунктов)
- **Примечания** (опционально)
- **История изменений**

---

## 📋 Процесс создания стандарта

### Шаг 1: Анализ ошибки
1. Опиши ошибку (что было не так)
2. Найди root cause (почему это произошло)
3. Определи фундаментальное правило (как предотвратить)

### Шаг 2: Создание стандарта
1. Используй `TEMPLATE.md`
2. Заполни только необходимые разделы
3. Будь кратким и конкретным

### Шаг 3: Проверка
- [ ] Класс определён и указан в шапке (micro / method / contract)?
- [ ] Длина в пределах лимита класса (micro ≤100 / method ≤400 / contract ~150)?
- [ ] Содержит только фундаментальные правила (micro) либо воспроизводимые стадии/контракт (method/contract)?
- [ ] Не дублирует другие стандарты (только cross-ref)?
- [ ] Структура соответствует образцу класса?

---

## 🚫 Что НЕ включать в стандарт

- ❌ Детали конкретных случаев (создай отдельный документ)
- ❌ Примеры кода (если не критично для понимания)
- ❌ Длинные объяснения (краткость важнее)
- ❌ Дублирование информации из других стандартов
- ❌ Временные решения (только фундаментальные правила)

---

## ✅ Что включать в стандарт

- ✅ Фундаментальное правило (1-2 предложения)
- ✅ Root cause ошибки (2-3 пункта)
- ✅ Конкретные действия для предотвращения (3-5 пунктов)
- ✅ Критически важные детали (если без них правило непонятно)

---

## 🔄 Обновление стандарта

### Когда обновлять:
- Обнаружена новая ошибка в той же области
- Правило оказалось неполным
- Нужно уточнить формулировку

### Как обновлять:
1. Добавь запись в "История изменений"
2. Обнови только необходимые разделы
3. Удали устаревшие части
4. Проверь, что стандарт все еще в пределах лимита своего класса

### Когда НЕ обновлять:
- Если это новый тип ошибки → создай новый стандарт
- Если это детали конкретного случая → создай отдельный документ
- Если правило уже работает → не трогай

---

## 📊 Примеры хороших стандартов

### ✅ Хорошо (компактно, фундаментально):
```markdown
## 🎯 Фундаментальное правило
Всегда проверяй реальные данные перед выводами.

## ⚠️ Что было не так
- Делал выводы без проверки файлов
- Предполагал структуру данных

## ✅ Как предотвратить
1. Открывай каждый файл перед выводом
2. Показывай schema перед анализом
```

### ❌ Плохо (слишком детально):
```markdown
## 🎯 Фундаментальное правило
[50 строк примеров кода и детальных объяснений...]
```

---

**Помни:** micro-стандарт — это **компактный чек-лист**, а не документация. Примеры выше (✅/❌) относятся к классу **micro**; для method/contract эталоны — `triz-gap-closure-audit-standard.md` и `agent_loops/ralph_loop.md` соответственно.
