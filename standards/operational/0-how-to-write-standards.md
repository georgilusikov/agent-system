# Standard 0 — How to Write Standards (мета-стандарт)

Корневой стандарт для ОБОИХ слоёв стандартов. Применять ВСЕГДА перед созданием
нового стандарта или major refactor существующего.

**Канон-схема:** этот файл = полная мета. Workspace-краткая версия —
`_agent_shared/standards/STRUCTURE_RULES.md` (та же таксономия классов, сжатая).
Противоречие между ними = баг, чинить оба файла одним коммитом.

## §1. Решение: нужен ли стандарт?

```
Хочешь создать стандарт по теме X?
├── Какой incident-trigger?
│   ├── Compile-trigger: ≥3 правила в rules/ по одной теме → ✅ создавай
│   ├── Repeat-trigger: одна ошибка повторилась 2+ раз → ✅ создавай
│   ├── Context-switch: каждый раз в области вспоминаешь то же → ✅ создавай
│   ├── Onboarding: новый агент должен быстро понять область → ✅ создавай
│   └── Нет trigger → ❌ НЕ создавай (over-engineering)
└── Если trigger есть:
    ├── Используется в 1 skill? → references/ ВНУТРИ skill, не стандарт
    ├── Используется в ≥2 skills ИЛИ explicit invocation → ✅ standards/{name}.md
    └── Совсем короткое (1-3 строки) → rules/, не стандарт
```

**Запрет:** стандарт без зафиксированного `incident_trigger` в frontmatter.

## §2. Класс определяет форму (хребет таксономии)

| Класс | Лимит | Что это | Эталон |
|---|---|---|---|
| **micro** | ≤ 100 строк | Рождён из одной ошибки. Компактный чек-лист: правило → что было не так → root cause → предотвращение | `_agent_shared/standards/safe-deletion-standard.md` |
| **method** | ≤ 400 строк | Воспроизводимый пайплайн: JTBD + Точка G + стадии с hard-гейтами + артефакты | `triz-gap-closure-audit-standard.md` |
| **contract** | ~150 строк | Контракт инструмента: инварианты + CLI surface + verification matrix | `agent_loops/ralph_loop.md` |

**Правило выбора:**
- Одна ошибка → одно правило → **micro**.
- Повторяемый многостадийный процесс с гейтами → **method**.
- Контракт переиспользуемого инструмента (`tools/…`) → **contract**.

Класс указывать в шапке строкой `**Класс:** micro | method | contract`.
Micro раздулся за 100 строк → переклассифицируй в method, не режь смысл.

## §3. Scope определяет место и строгость (вторая ось)

| Scope | Где живёт | Что добавляется к классу |
|---|---|---|
| `personal` | `~/.claude/standards/` | Ничего: минимум секций класса |
| `project` | `<repo>/.claude/**`, проектный CLAUDE.md | + Expected State / Validation |
| `shared` | `_agent_shared/standards/` | + owner, известные инциденты, регистрация в README-индексе |

Класс = структура и лимит. Scope = где лежит и сколько обвязки.
Personal micro = 20-100 строк; shared method = до 400 + индекс.

## §4. Обязательные секции по классу

| Секция | micro | method | contract |
|---|---|---|---|
| frontmatter: name, description, version, created, incident_trigger | ✅ | ✅ | ✅ |
| Фундаментальное правило (1-2 предложения) | ✅ | — | — |
| Что было не так / root cause / как предотвратить | ✅ | — | — |
| JTBD-сценарии (≥3, canvas Красинского для сложных) | — | ✅ | — |
| Точка G (бинарные camera-test критерии) | — | ✅ | опц. |
| Стадии §1..§N с гейтами (шаг = команда/чек-лист, не голый текст) | — | ✅ | — |
| Инварианты + surface (CLI/API) + verification matrix | — | — | ✅ |
| Когнитивные искажения области (≥3, Симптом + Защита) | — | ✅ | — |
| FORBIDDEN + Hard fail | опц. | ✅ | ✅ |
| Связанные скиллы/стандарты (cross-ref) | ✅ | ✅ | ✅ |
| Changelog / История изменений | ✅ | ✅ | ✅ |

Шаблоны: micro — `_agent_shared/standards/TEMPLATE.md`;
method — `~/.claude/standards/_TEMPLATE.md` (JTBD + Точка G + §-методология).

## §5. Принцип отбора контента (главный)

**Каждая строка предотвращает ошибку или меняет поведение агента.**
Убрал строку — ничего не изменилось → строки не должно быть.

Запрещено: очевидное для senior; TBD/placeholder; дублирование других
стандартов (только cross-ref); обоснования из головы (только из реальных
incidents/git/code/data); детали конкретного случая (это в memory/incidents).

## §6. Naming и версионирование

- Имя: `{kebab-case}-standard.md` (workspace) или `{kebab-case}.md` (personal).
  Числовой префикс `0-` — только мета-файлы.
- Версии (SemVer-like): clarification = none; новый шаг/биас = patch;
  новая секция/breaking структура = minor; **major (1.0) — только после 5+
  реальных применений**. False maturity запрещён.

## §7. Workflow создания (итерационно, не из головы)

1. Compile pass: собери rules/incidents по теме, прочитай ВСЕ источники.
2. Выбери класс (§2) и scope (§3).
3. First draft 0.0.1 по секциям класса (§4).
4. Self-review: `/check` против Точки G (method) или чек-листа STRUCTURE_RULES (micro).
5. Negative test: `/falsify` — может ли агент выполнить шаги без контекста сессии?
6. Apply: 1 реальное применение → собери gaps → bump patch.
7. Commit в git слоя (`~/.claude` или workspace) с «что + почему».

**Запрет:** объявлять стандарт готовым после first draft. Минимум 1 реальное
применение перед commit.

## §8. Обновление и чистка

- Новый инцидент в области → добавь биас/шаг/запрет, bump patch, changelog.
- Раз в 1-2 месяца: `grep -rl "standards/" ~/.claude/skills/ _agent_shared/` —
  стандарт без единого потребителя за месяц = мёртвый, удалить.
- Два стандарта пересекаются >50% → merge или явно разнести scope в frontmatter.
- Ревизия/удаление → сначала `git log -5 --oneline -- <file>` (причина создания
  в коммите); свежий (<2 недель) без замера эффекта не трогать.

## Когнитивные искажения при написании стандартов

### Premature standard creation
**Симптом:** «тема может пригодиться» → стандарт без incident_trigger, никогда не используется.
**Защита:** §1 decision tree обязателен.

### Format-source ambiguity (новый, v0.1.0)
**Симптом:** в системе два мета-документа с разными лимитами; агент следует тому, что прочитал первым.
**Защита:** канон-схема в шапке; противоречие мет = баг, чинить оба одним коммитом.

### Copy-paste from rules
**Симптом:** стандарт = копия правил без expansion.
**Защита:** стандарт расширяет rules (методология/JTBD/биасы); контент <2x от исходных rules → не нужен.

### Abstract checklist syndrome
**Симптом:** «Точка G: высокое качество, читаемый код» — не camera-проверяемо.
**Защита:** каждый пункт проходит camera test. «pytest passes» ✅, «код хороший» ❌.

### Class inflation
**Симптом:** micro-случай оформлен как 300-строчный method «для солидности»; ритуальные секции.
**Защита:** §2 правило выбора; одна ошибка = micro, точка.

### Version inflation
**Симптом:** 1.0 после first draft.
**Защита:** major только после 5+ реальных применений.

## FORBIDDEN

- Стандарт без `incident_trigger` (over-engineering)
- Micro с ритуальными секциями JTBD/биасов «для полноты» (class inflation)
- Method без Точки G с бинарными критериями
- Превышение лимита класса вместо переклассификации или split на references/
- Правка одной меты без сверки со второй (STRUCTURE_RULES.md)
- Bump 1.0 без 5+ реальных применений

## Hard fail

- Нет `incident_trigger` → стандарт создан без причины, удалить
- Класс не указан и не выводится из структуры → формат не верифицируем
- Нет Changelog → эволюция не отслеживаема
- method без ≥3 искажений области → не закрывает петлю эволюции
