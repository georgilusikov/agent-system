# Standards — слой контекстуальной методологии

## Двухуровневая архитектура

```
┌─────────────────────────────────────────────────┐
│  УРОВЕНЬ 1 — МЕТА (всегда работает)             │
│                                                  │
│  CLAUDE.md         — стиль, autonomy, principles │
│  ~/.claude/skills/ — общие узкие навыки          │
│                     (/check, /clean, /falsify…)  │
│  ~/.claude/rules/  — операционные эвристики      │
│                                                  │
│  Триггер: автоматически по trigger phrases       │
│  ИЛИ всегда (CLAUDE.md autoload)                 │
└─────────────────────────────────────────────────┘
                      ↓ может загрузить ↓
┌─────────────────────────────────────────────────┐
│  УРОВЕНЬ 2 — КОНТЕКСТ (по запросу)              │
│                                                  │
│  ~/.claude/standards/ — методология области X   │
│                                                  │
│  Триггер: явный запрос пользователя             │
│  («работаем по deploy-стандарту»)                │
│  ИЛИ Skill сам подгружает через Read            │
│  когда понимает что задача в этой области        │
└─────────────────────────────────────────────────┘
```

**Аналогия:** стандарт = `init` для конкретной темы. Когда садишься делать задачу в области X — подгружаешь стандарт X, чтобы вспомнить методологию, типичные ошибки, готовые шаги.

## Global skills vs Project skills (правило размещения)

**Правило:**

- **Global** (`~/.claude/skills/`) — **только мета-протоколы**, работающие в любом проекте: `/check`, `/pizdej`, `/falsify`, `/clean`, `/why`, `/triage`, `/anti-bias`, `/bouncer`, `/go`, `/commit`, `/init-project`, `/prioritize`, `/handoff`, `/guard`, `/deep-research`, `/find-skills`
- **Project** (`{project}/.claude/skills/`) — **узкие доменные действия** специфичные для проекта (например `realt-scraper-collect`, `budget-monthly-import`, `landing-analysis`)

**Исключения (остаются global несмотря на доменность):**

| Skill | Почему global |
|---|---|
| `/agentnet` | Используется в нескольких проектах через cross-project orchestration. Управляет Mac Mini runtime — нужен везде где есть AgentNet integration |
| `/stitch` | UI generation tool, переиспользуется в разных design tasks |
| Симлинки `/moai-domain-uiux`, `/tremor-design-system` | UI references, удобнее держать global |

**Когда выносить skill в project:**
- Skill узкий и специфичный для одного проекта
- Не нужен в других проектах
- Использует project-specific paths/configs
- Имеет сильное coupling с project codebase

**Migration triggers (сигналы что skill пора в project):**
- Skill вызывает абсолютные paths внутри одного проекта
- Skill редактирует файлы только в одном проекте
- Skill использует .env переменные одного проекта

## Чем отличается каждый уровень

| | Уровень 1: CLAUDE.md | Уровень 1: Skills | Уровень 1: Rules | Уровень 2: Standards |
|---|---|---|---|---|
| **Когда работает** | Всегда (autoload) | По trigger phrases или явному вызову | Зависит от scope (project/global) | По запросу пользователя или Read из skill |
| **Содержание** | Стиль, autonomy levels, ключевые принципы | «Что сделать» — узкий процесс | Операционная эвристика (1-3 строки) | «Как именно в области X» — методология + cognitive biases для области |
| **Размер** | ≤200 строк (компактный) | ≤500 строк | 1-30 строк | До 30KB (большие) |
| **Специфичность** | Общая | Общая (узкий процесс, любая область) | Операционная (узкая, конкретная) | Доменная (методология области) |
| **Пример** | «Говори по-русски», «не используй mock в integration tests» | `/check`, `/clean`, `/why` | «Python 3.9 на Mac Mini», «runner-safety guard» | `mac-mini-deploy.md`, `realestate-scraper.md`, `data-research.md` |

## Когда создавать стандарт (правило)

**НЕ создавай стандарт ради стандарта.** Триггеры для создания:

1. **Incident-trigger:** одна и та же ошибка повторилась 2+ раза в одной предметной области → значит у тебя нет фундамента в этой области → создавай стандарт
2. **Контекст-switch trigger:** ты регулярно работаешь в области X (deploy, scraper, ML) и каждый раз вспоминаешь одно и то же → лучше зафиксировать в стандарте чем держать в голове
3. **Compile-trigger:** у тебя в `~/.claude/rules/` накопилось ≥3 правила по одной теме → пора компилировать в полноценный стандарт
4. **Onboarding-trigger:** новый агент / новая сессия должны быстро понять «как мы работаем в области X» → стандарт = onboarding doc

## Decision tree для каждой потенциальной методологии

```
Нужна ли методология по теме X?
├── [O] Сработал ли incident-trigger / context-switch / compile / onboarding?
│   ├── НЕТ → не создавай стандарт
│   └── ДА → продолжай
│
├── Используется ли методология в ≥2 skills?
│   ├── НЕТ (только в одном skill, например /check) →
│   │   references/ ВНУТРИ skill:
│   │   ~/.claude/skills/check/references/quality-criteria.md
│   │   (не создавай отдельный стандарт)
│   │
│   └── ДА (используется в /check, /why, /falsify) →
│       Отдельный слой:
│       ~/.claude/standards/{name}.md
│       Skills подгружают через Read когда нужно
```

## Workflow создания стандарта (итерационно, не из головы)

Из системы Красинского (адаптировано под Claude Code):

```
Шаг 1. Сделай задачу обычным способом → получи первый (плохой) результат
Шаг 2. Запусти /check + /pizdej → найди гэпы
Шаг 3. Запусти /why или /falsify → найди корневые причины + Design Injection
Шаг 4. Скопируй _TEMPLATE.md → {область}.md, версия 0.0.1
        Заполни на основе найденных корневых причин и cognitive biases
Шаг 5. На каждой следующей ошибке в этой области → апдейти стандарт, бампай версию
```

После 4-6 итераций (по Красинскому) стандарт становится зрелым (1.0+).

## Как поддерживать

- **Кто записывает изменения:** агент сам перезаписывает файл при инциденте, ты — оператор который инициирует команду «обнови стандарт X»
- **Когда обновлять:** каждый раз когда нашёл новую ошибку в этой области (см. шаг 5 workflow)
- **Версионирование:** SemVer-like — patch (0.0.1 → 0.0.2) для мелких правок, minor (0.0.x → 0.1.0) для нового шага, major (0.x → 1.0) для рабочего baseline
- **Чистка:** раз в 1-2 месяца → `/clean` по standards/, удалить устаревшие шаги, объединить дубли

## Как использовать (3 способа в Claude Code)

В отличие от Cursor (`@имя_стандарта` autoindex), у Claude Code три способа:

### Способ 1: Read из skill (рекомендуемый)
В нужном скилле (например `/why`) добавь шаг §0:
```markdown
## §0. Pre-load standard
Если задача в области deploy → Read ~/.claude/standards/mac-mini-deploy.md перед §1
```
Skill сам решает когда подгружать стандарт.

### Способ 2: Явный вызов в промпте (по запросу пользователя)
```
Прочитай ~/.claude/standards/mac-mini-deploy.md и сделай deploy на Mac Mini по этому стандарту.
```
Это твой основной use case по модели «уровень 2 = по запросу».

### Способ 3: Ссылка из CLAUDE.md (только для самых частых)
В `~/.claude/CLAUDE.md` добавь:
```markdown
@~/.claude/standards/mac-mini-deploy.md
```
**Не злоупотреблять** — каждый autoload расходует context. Только если работаешь в этой области каждый день.

## Связь между уровнями

Стандарт может ссылаться на скилл (через текст) — но **не наоборот в frontmatter**. Skill может Read стандарт, но не объявляет его в metadata.

Пример:
```
/why (skill, уровень 1)
   §0 Pre-load: если задача про deploy → Read standards/mac-mini-deploy.md
   §1-§N: применяет 5 Whys
   В §3.5 Design Injection: возможно предлагает обновить standards/mac-mini-deploy.md
```

## FORBIDDEN

- Создавать стандарт «на всякий случай» без incident-trigger (повторившейся ошибки или другого реального повода)
- Копировать стандарт Красинского 1-в-1 без адаптации под мою работу
- Делать стандарт > 500 строк — разбивать на references/ или подстандарты
- Дублировать содержимое из rules/ или skills/ в стандарт (если это короткое правило — оставь в rules/)
- Загружать стандарт через CLAUDE.md autoload без проверки что работаешь в этой области каждый день

## Hard fail

- Стандарт без версии в frontmatter → невалиден
- Стандарт без `incident_trigger` поля → создан без причины, удалить
- Стандарт без раздела «когнитивные искажения» → не закрывает петлю эволюции (главная функция стандарта по Красинскому)
- Стандарт нигде не используется (никакой skill его не Read, никакой пользователь не вызывает) → удалить через 1 месяц
